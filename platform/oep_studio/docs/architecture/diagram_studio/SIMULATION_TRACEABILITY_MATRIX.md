# Simulation Traceability Matrix

**Architecture Phase:** AP-DS-005. For every significant capability found in `platform/reference/legacy_simulation_engine_v2/` during the mandatory review (`SIMULATION_REFERENCE_REVIEW.md`), this matrix records the decision made and where the concept lands in the new architecture — demonstrating every capability was consciously evaluated, not silently dropped or blindly copied.

| Legacy capability | Original purpose | Decision | Engineering justification | Modern implementation location |
|---|---|---|---|---|
| `GraphTraversal` (BFS/DFS/shortest-path/all-paths), `apps/simulator/js/graph/graph-traversal.js` | Core graph algorithms underlying every other subsystem | **Replace** | Superseded by `oep_engine`'s existing `KnowledgeGraphEngine`/`GraphAlgorithms` (WP-EKE-002) — reimplementing graph traversal a second time would repeat the legacy project's own self-documented architectural mistake (two competing traversal implementations in one codebase) | `oep_engine`'s existing `GraphAlgorithms`, extended only for simulation-specific gated traversal in the new `SimulationEngine` |
| `CircuitGraph.islands()` / `DisconnectedCircuitValidator` (duplicate connected-component logic) | Detect disconnected wiring islands | **Reject** (as separate implementations) / **Retain** (as a concept) | The duplication itself is exactly what to avoid; connected-component detection as a verification check is genuinely useful | `VerificationEngine`'s Connectivity Verification, calling `GraphAlgorithms.connected_components` once |
| `VoltagePropagator` (flood-fill multi-source BFS with per-edge gating) | Determine which nodes are powered | **Improve** | The concept (propagate power outward from sources, gated by component behavior) is sound; the one-voltage-per-node model and hardcoded battery-voltage constants are not | Simulation Engine's Signal Propagation module (Power signal type), per-terminal state |
| `GroundPropagator` (independent boolean reachability from ground sources) | Determine which nodes are grounded | **Retain** | Power/ground as two independent propagations, combined as `functional = powered && grounded`, is a real, correct, retainable engineering pattern | Simulation Engine's Signal Propagation module (Ground signal type) |
| `ContinuitySolver` (resistance across all simple paths, minimum taken) | "Virtual ohmmeter" — compute continuity/resistance between two points | **Retain**, reimplemented | The concept of a continuity/resistance query as a first-class diagnostic primitive is sound and maps directly to the spec's "Continuity Verification" requirement | Verification Engine's Continuity Verification + Diagnostics measurement queries |
| `DependencyTracker` (`dependenciesOf`/`dependentsOf`/`whatFailsIf`/`sharedGrounds`/`sharedPower`) | Behavioral/electrical dependency analysis beyond raw connectivity | **Improve** | Genuinely valuable capability; the legacy `whatFailsIf`'s single-power-source bug (only checks the first source, under-reporting redundancy) must not be repeated | Dependency Verification (Simulation Engine) + existing `AnalysisEngine.analyze_dependencies`/`analyze_impact` (EIP, WP-EKE-006) for the reasoning layer |
| `RelayBehavior` (coil-energization-gated contact resistance, pickup/dropout hysteresis) | Model a stateful component whose connectivity depends on another signal's state | **Retain** | The exact "behavioral, not just wiring, dependency" pattern the spec explicitly asks to extract; a relay is the canonical example | Signal Propagation's state-gated edge behavior model, keyed by component/relationship metadata |
| `PathFinder` (`findPowerPath`/`findGroundPath`/`describePath`) | Trace how power/ground reaches a specific point, for diagnosis and diagram highlighting | **Retain** | Path-finding as a named, reusable diagnostic primitive (not just an internal detail) is directly reusable and directly maps to the spec's "path finding" requirement | Diagnostics module (Propagation Report) + Diagram Studio's Analysis Overlay (highlighting) |
| `MeterEngine` / `ElectricalSolver`'s dual measurement paths (live solver vs. static-JSON fallback, reconciled only by a code comment) | Compute a displayable measurement value | **Reject** (the dual-source pattern) / **Retain** (the concept of a measurement query) | Two disagreeing sources of truth for one measurement is a genuine maintenance hazard the legacy code itself exhibits inconsistently between its own files | One measurement computation path in the Simulation Engine; Diagram Studio overlays read it, never compute independently |
| `FaultInjector` (fault-as-overlay, keyed by target, never mutating the base graph) | Inject and clear faults without corrupting the design graph | **Retain** | A genuinely good pattern — keeps the base graph pristine, makes fault scenarios trivially resettable | Fault Injection System (Simulation Engine), overlay on Simulation Session state, never mutates `EngineeringGraph` |
| `FailureModes` catalog (open/short-to-ground/short-to-power/high-resistance/bad-ground/blown-fuse/corrosion/failed-relay/failed-sensor) | Enumerate injectable fault types | **Retain**, as vocabulary | A reasonable, real-world-grounded fault taxonomy; directly maps to the spec's own Fault Injection list (Open Circuit, Short Circuit, Disconnected Connector, Broken Wire, etc.) | Fault Injection System's fault-type enum |
| `models/fault.js`'s `EKEFault` class (a second, differently-shaped fault representation coexisting with `FaultInjector`'s plain objects) | (Unclear — appears to be an alternate/earlier fault model) | **Reject** | Representation drift within the same subsystem — exactly the kind of inconsistency a fresh design must avoid by having one fault representation, not two | N/A — the new engine has exactly one fault data model |
| `FaultLocator.diagnose()` (path-based root-cause explainer with fixed confidence literals) | Explain "why does this component have no power/ground" | **Improve** | The path-based reasoning approach (no power path → no ground path → open wires on path → upstream dependency) is sound; the fixed decimal "confidence" literals presented as calibrated values are not | Diagnostics module (Fault Report) for the facts; ranking/explanation-quality improvements deferred to EIP's `ReasoningEngine` consumption, not reinvented with fabricated precision |
| `FaultReasoner`/`FaultLibrary` (free-text symptom matching against a hand-authored library, with a hand-tuned probability formula) | Symptom-to-cause diagnostic reasoning | **Replace** | This is exactly the class of reasoning EIP's `ReasoningEngine`/`AnalysisEngine` (WP-EKE-006) already does properly (deterministic, evidence-referenced) — reimplementing a second, cruder version inside the Simulation Engine would violate AP-DS-005's own "no engineering logic inside Diagram Studio... Engineering Intelligence Platform remains responsible for Reasoning" principle | `EngineeringIntelligencePlatform`/`ReasoningEngine`, consumed via `DiagramIntelligenceService`, never reimplemented |
| `DiagnosticEngine` (flat isolated-component/active-fault scan, second engine) | Produce basic findings from graph state | **Replace** | Far shallower than EIP's existing `ValidationEngine`/rule system; no reason to build a second, weaker version | EIP's `ValidationEngine` (WP-EKE-005), consumed via `DiagramIntelligenceService.validate()` |
| `SystemRecognizer`/`TopologyRecognizer` (pattern-match graph against system/topology templates) | Classify "what kind of system/topology is this" | **Reject** (from the Simulation Engine's scope) | Out of scope for AP-DS-005's Simulation Engine entirely — this is analysis/classification reasoning, not deterministic execution/propagation; belongs to EIP if pursued at all, and was not requested by this phase | Not implemented this phase; would be `AnalysisEngine`/`ReasoningEngine` territory if pursued later |
| `GraphValidators` (orphan wire, missing terminal, duplicate wire, floating ground, disconnected circuit) | Static design-correctness checks independent of simulation | **Retain**, reimplemented | Directly maps to the spec's Engineering Verification list (Connectivity/Continuity/Ground/Relationship/Dependency Verification) | Verification Engine (Simulation Engine module) |
| `docs/wiring-diagram-design-rules.md`'s 40-rule plausibility rulebook | Guide OCR-extraction plausibility scoring | **Reject** (as OCR-extraction tooling — out of scope) / **Retain** (rules as domain knowledge) | This platform has no OCR-extraction pipeline in scope for AP-DS-005; the rules themselves (e.g. "fuses are always in series, never parallel," "ground nodes are highly connected") are useful domain knowledge for Verification Engine rule authoring, referenced conceptually not copied | Verification Engine's rule set (where applicable), as manually-authored domain rules, not ported code |
| `diagram/renderer.js` (374-line monolithic SVG/DOM renderer, category color-coding, striped wire-color table, minimap, flow animation) | Render the wiring diagram and simulation state visually | **Reject** (implementation) / **Retain** (visual conventions) | Diagram Studio's `GraphViewPanel` (frozen since AP-DS-001) is the only renderer; no legacy rendering code is reused. The color/category conventions are useful reference for overlay styling | Diagram Studio's existing canvas + new simulation overlay layer (Power/Ground/Signal/Fault/Warning/Propagation/Dependency/Recommendation overlays, per AP-DS-005's own Visualization section) |
| `diagram/path-highlighter.js` (highlight a path's nodes/wires on the diagram) | Visually show a traced path | **Retain**, reimplemented | Directly maps to AP-DS-005's Propagation/Dependency overlay requirements | Diagram Studio's Analysis/Propagation Overlay, consuming Simulation Engine path results |
| Key position (0/1/2/3) + switch-toggle interaction, stateless "solve for current conditions" | Interactive electrical-state exploration | **Improve** | Genuinely the right interaction model conceptually, but stateless "recompute everything on every change" has no time/history dimension — the spec explicitly requires Timeline/Playback/Bookmarks/Replay, which the legacy simulator never had at all | Simulation Engine's Session/Timeline/Playback/History/Bookmarks/Replay (an entirely new capability, not present in the legacy project in any form) |
| Multimeter UI (`ui/meter-panel.js`, mode selection, LCD-style readout) | Present measurement values to the user | **Retain**, as an interaction concept | Reasonable interaction pattern for inspecting simulation state at a point | Diagram Studio's simulation overlay/inspector UI (Studio-side, presentation only) |
| Editor toolkit (`editor/wire-editor.js`, `undo-redo.js`, `clipboard.js`, etc.) | Diagram editing | **Reject** (out of scope) | AP-DS-005 is a simulation/verification phase; diagram editing is Diagram Studio's own frozen, already-complete editing architecture (AP-DS-001) — not something the Simulation Engine touches or duplicates | N/A — Diagram Studio's existing, unrelated editing system |
| Manual console-log/console-assert "test scripts," no automated framework | Ad hoc verification during development | **Reject** (the practice) / **Retain** (the scenarios as regression sources) | No CI-worthy test infrastructure existed; but the actual scenario content (state transitions, fault injection + re-diagnose, multi-symptom diagnosis) is a real, valuable regression-scenario source | New automated test suite (`flutter test`), with legacy-derived regression scenarios (see below) |
| `tests/simulator-test.js` scenario (key-off→on→cranking; diagnose baseline; inject open-circuit fault; re-diagnose) | Demonstrate the simulator's core state-transition + fault workflow | **Retain**, as a regression scenario | Directly re-derivable as an automated test against the new engine, proving equivalent behavior without porting any code | `test/simulation/` regression scenario (Simulation Engine) |
| `tests/fault-reasoner-test.js` scenarios (multi-symptom diagnosis, empty-symptom baseline) | Demonstrate symptom-based reasoning | **Retain**, as a regression scenario, **Replace** as implementation | The scenario shape (given symptoms, expect specific candidate findings) is reusable even though the reasoning itself moves to EIP | `test/simulation/` regression scenario, exercised against `DiagramIntelligenceService`-mediated diagnostics where applicable |

## Summary

Of the significant capabilities identified: **9 Retained** (conceptually or with reimplementation), **6 Improved** (retained with a specific, named correction to a real legacy flaw), **4 Replaced** (superseded by an existing, more capable platform component — mostly EIP), **6 Rejected** (either an anti-pattern, out of scope, or dead/unused code). No capability was adopted by porting, copying, or migrating legacy code — every "Retain"/"Improve" decision above is a fresh implementation inside `oep_engine`, operating on Engineering Objects/Relationships, per this platform's frozen architecture.
