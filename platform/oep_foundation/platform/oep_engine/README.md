# Engine

Status: Foundation (WP-EKE-001 — Engineering Knowledge Runtime Core; WP-EKE-002 — Engineering Knowledge Graph Engine; WP-EKE-003 — Engineering Query Engine; WP-EKE-004 — Engineering Rules Engine; WP-EKE-005 — Engineering Validation Engine; WP-EKE-006 — Engineering Analysis & Reasoning Engine; WP-EKE-007 — Engineering Intelligence Platform). WP-EKE-007 is the seventh and, per `docs/tasks/` (no WP-EKE-008 exists at the time of writing), final planned work package of the WP-EKE series — its own spec text names the platform as consumed by "Studio, Engineering Acquisition, Engineering Exchange, external SDKs, and future Engineering AI systems," so this closes out the Engineering Knowledge Engine's core architecture without implying those consumer integrations or future AI systems are themselves complete.

Purpose: The **Engineering Knowledge Runtime (EKR)** — a new architectural layer sitting ABOVE Foundation, responsible for engineering *semantics* (graph queries, traversal, relationship classification) rather than storage. Per WP-EKE-001's own Architectural Position:

```
Engineering Acquisition
        |
Foundation Repository
        |
Engineering Knowledge Runtime   <-- this module
        |
Knowledge Graph
        |
Reasoning
        |
Engineering Intelligence
```

Unlike `platform/runtime`, which manages persistence, transactions, trust, and package installation, `platform/oep_engine` manages what Engineering Objects and Relationships *mean* once they already exist inside an open Foundation Repository. This is the first work package in the WP-EKE series, distinct from the WP-REP series (WP-REP-001 through WP-REP-008) that built the Foundation Repository Runtime this module now sits on top of.

## Principles

Per WP-EKE-001's own specification, the EKR **SHALL NOT**:

- manage storage
- modify transactions
- install packages
- manage trust

Those remain exclusively Foundation's (`platform/runtime`'s) job — see "What this module deliberately does not implement" below.

The EKR **SHALL**:

- load Engineering Objects
- construct runtime graphs
- expose semantic queries
- provide traversal services
- provide object context

**Reached exclusively through `oep::runtime::RuntimeService`.** Every component in this module consumes Foundation through `RuntimeService` alone — never through `FoundationRuntime`'s `object_store()`/`relationship_store()` accessors directly, never by opening a Repository Transaction, never by touching `ObjectStore`/`RelationshipStore` itself. This mirrors the RuntimeService-exclusivity pattern WP-REP-007/WP-REP-008 already established for newer Foundation capabilities (uninstall/update/merge), applied here to an entirely new consumer rather than a new Foundation capability.

## Architecture

Six components, `include/oep/engine/` + `src/`:

- `runtime_graph.hpp/.cpp` — `RuntimeGraph`: the Engine's OWN in-memory graph (nodes = Engineering Objects, edges = Relationships), built from a snapshot of data already loaded through `RuntimeService` — never from a live `ObjectStore`/`RelationshipStore`. Deliberately a separate concept from the pre-existing `oep::repository::GraphEngine` (a Foundation/Repository-layer class built directly against persistence and owned by `FoundationRuntime`): same general shape (nodes, edges, adjacency, traversal), different architectural layer, different owner, no shared code. Supports indexes by `ObjectType` and by tag — "find by domain" is implemented as a documented mapping onto Engineering Objects' existing `tags` field, since Engineering Objects have no dedicated "domain" field and CLAUDE.md's Five Primitive Rule forbids adding one without architectural approval. A relationship whose source or target is missing from the object snapshot is excluded from the graph, mirroring `GraphEngine`'s own documented dangling-reference behavior. `build` fully replaces prior content; nothing is ever mutated or persisted.
- `object_loader.hpp/.cpp` — `ObjectLoader`: lazy single-object loading (`load_object`, cached for the lifetime of the loader instance) and batch/hydration loading (`load_all`, fetching every object and relationship currently in the open repository), both exclusively through the `RuntimeService` reference supplied at construction. Implements no persistence of its own — every load is a read-through against `RuntimeService`.
- `relationship_engine.hpp/.cpp` — `RelationshipEngine`: static, read-only classification of an already-loaded `RuntimeGraph`'s edges touching one object, per OEP-SPEC-005's `RelationshipType` vocabulary — `parents` (`Contains` edges where the object is the target), `children` (`Contains` edges where the object is the source), `neighbors` (any edge, either direction), `references` (`References` edges where the object is the source), `dependencies` (`DependsOn` edges where the object is the source). Never queries Foundation or `RuntimeService` directly — by the time a caller has a `RuntimeGraph` to pass in, it was already built via `ObjectLoader`.
- `query_engine.hpp/.cpp` — `QueryEngine`: static, pure functions over an already-loaded `RuntimeGraph` — `find_by_id`, `find_by_type`, `find_by_domain` (via the tag mapping documented above), `find_by_relationship`, `shortest_path` (BFS, unweighted, treats every relationship as bidirectional for connectivity, extending `GraphEngine::path_exists`'s own convention to also reconstruct the path), `connected_component` (undirected reachability), `subgraph` (the induced subgraph over a requested id set — nonexistent ids are silently skipped, not an error).
- `traversal_engine.hpp/.cpp` — free function `traverse()`: deterministic BFS/DFS over a `RuntimeGraph`, with an optional relationship-type filter and an optional max-depth limit (the start node itself is depth 0). Cycle-safe via a visited-set — a graph containing a cycle back to an already-visited node does not infinite-loop or revisit it, an explicit WP-EKE-001 test requirement. At every node, neighbors are visited in the graph's own deterministic edge ordering, so the same graph and options always produce the same traversal order.
- `engineering_context.hpp/.cpp` — `EngineeringContext`: the top-level facade combining all of the above behind the six-method Public Runtime API WP-EKE-001 specifies — `load_object()` (lazy, does not require the graph to be built), `load_graph()` (batch-loads and (re)builds the `RuntimeGraph`; must succeed before any of the methods below), `query()` (a single discriminated `QueryRequest`/`QueryKind` covering every `QueryEngine` operation), `traverse()`, `related_objects()` (`RelationshipEngine::neighbors`), and `dependency_graph()` — the full transitive closure of an object's outgoing `DependsOn` relationships. `dependency_graph()` is an **entirely different thing** from Foundation's WP-REP-005 Dependency Resolution Engine: this one walks Engineering Object `DependsOn` *relationships* (an engineering-semantics concept) to build a knowledge graph; WP-REP-005's resolver evaluates *package manifest* dependency declarations before an install is allowed to proceed. The two share a name in English only — worth stating plainly since a reader could otherwise conflate them. `EngineeringContext` is constructed from a `RuntimeService&` and never touches `FoundationRuntime` directly, never opens a transaction, never verifies trust, never resolves package dependencies.

Consumed by `platform/api`'s Public C API (`oep_engine_load_object`/`_load_graph`/`_query`/`_traverse`/`_related_objects`/`_dependency_graph`, WP-EKE-001) and, through it, `platform/cli`'s `oep engine` command group — this module, like every Engine-layer or Foundation-layer subsystem in OEP, is reached exclusively through the layer immediately above it.

## What this module deliberately does not implement

Named explicitly, straight from WP-EKE-001's "The EKR SHALL NOT" list, rather than silently absent:

- **Storage** — this module owns no on-disk representation of anything. `RuntimeGraph` is purely in-memory and is discarded when the owning `EngineeringContext`/handle goes away; nothing here writes to `<repository>/repository/objects` or `<repository>/repository/relationships`. That remains `platform/repository`'s (`ObjectStore`/`RelationshipStore`'s) job, reached only indirectly through `RuntimeService`.
- **Transactions** — the EKR never begins, commits, or rolls back a Repository Transaction. It is entirely read-only against whatever `RuntimeService` returns; it has no mutation surface at all.
- **Package installation** — the EKR does not install, uninstall, update, or merge packages. It has no dependency on `platform/installer` and never touches the Repository Registry, Trust Store, or Dependency Resolution Engine.
- **Trust management** — the EKR performs no signature verification and holds no `TrustStore` reference. Content the EKR operates on is assumed to already be legitimately present in the open repository; verifying how it got there is entirely out of this module's scope.

**Studio UI screens not yet built.** WP-EKE-001's original specification named five Studio screens — Engineering Workspace, Graph Explorer, Relationship Viewer, Object Inspector, and Traversal View. **None of these were built in this work package.** Only the underlying Foundation Bridge FFI bindings (`oep_api_native_types.dart`/`oep_api_bindings.dart`/`oep_api_types.dart`/`foundation_bridge.dart` gaining bindings and convenience methods for all six C API functions) were added, verified via `flutter analyze`/`flutter test`. This mirrors how every prior WP-REP work package's "Studio integration" was scoped — a Bridge/binding layer, not new UI screens — and is flagged here as remaining, not yet started, future work, not something silently skipped.

## Engineering Knowledge Graph Engine (WP-EKE-002)

WP-EKE-002 adds a second, complementary set of components, still entirely inside `platform/oep_engine`, still consuming `EngineeringContext` only. Where WP-EKE-001's `RuntimeGraph`/`QueryEngine`/`traverse()` gave the EKR its first in-memory graph and traversal primitives, WP-EKE-002 builds the **canonical Knowledge Graph** on top of them — the graph WP-EKE-001's own Architectural Position diagram names as the layer immediately above the Engineering Knowledge Runtime (`Foundation Repository -> Engineering Knowledge Runtime -> Knowledge Graph -> Reasoning -> Engineering Intelligence`). Six new files, `include/oep/engine/` + `src/`:

- `knowledge_graph.hpp/.cpp` — `KnowledgeGraph`: the canonical node/edge structure, with seven maintained indexes — by Object ID, Object Type, Knowledge Domain (the same tag-mapping convention `RuntimeGraph` already established), Relationship Type, Relationship Direction (outgoing/incoming), Publisher, and Package. `add_object`/`remove_object`/`add_relationship`/`remove_relationship` keep every index synchronized incrementally — none of the seven ever requires a full reindex on a single mutation, though an explicit `reindex()` exists as a "trust the indexes less" recovery path.
- `graph_validator.hpp/.cpp` — free function `validate_graph(nodes, edges)`: detects `MissingEndpoint`, `DuplicateRelationship`, `SelfReference`, `BrokenReference`, `Cycle` (deterministic DFS), and `InvalidRelationshipType` (defensive), producing an **immutable** `GraphValidationReport` (const-accessor class, no setters). Deliberately operates on the *raw* input node/edge lists rather than an already-built `KnowledgeGraph` — a built graph silently excludes dangling edges, which would hide exactly the kind of issue this validator exists to catch. Never mutates anything.
- `graph_algorithms.hpp/.cpp` — static `GraphAlgorithms`: `connected_components` (a full partition of the graph into every component, not just one seed's reachable set), `shortest_path` (unweighted BFS), `reachable`, `neighborhood` (radius-bounded BFS), `subgraph` (the induced subgraph over a requested id set), `expand_relationships` (every relationship of a given type touching an object). All deterministic.
- `graph_statistics.hpp/.cpp` — free function `compute_statistics`: object count, relationship count, connected component count, density (`2E / (N(N-1))`), maximum depth (graph diameter, computed via BFS-from-every-node — an `O(V(V+E))` operation, documented as a known cost rather than optimized away), average degree (`2E / N`), relationship-type distribution, and domain distribution.
- `graph_serialization.hpp/.cpp` — `to_json` (a complete, deterministic JSON document via the existing `oep::repository::json` serializer, with objects and relationships always emitted in sorted-id order regardless of internal container order) and `to_graphml_placeholder` (explicitly a **placeholder**, per this work package's own spec: a minimal, well-formed `<graphml>` document with correct node/edge identity but no full attribute schema — not suitable for real GraphML tooling, and left as a documented extension point for a future work package). Both are read-only exports for diagnostics; neither is a save/load mechanism, and neither is ever persisted by this module.
- `knowledge_graph_engine.hpp/.cpp` — `KnowledgeGraphEngine`: the top-level facade, constructed from an `EngineeringContext&` (never `RuntimeService`/`FoundationRuntime` directly). `build_graph()`/`refresh_graph()` pull objects/relationships from `EngineeringContext` and resolve each object's package/publisher ownership via a new `EngineeringContext::find_owner()` method — itself routed through a new `RuntimeService::find_package_owner` read-only method (see `platform/runtime/README.md`), preserving the documented chain `KnowledgeGraphEngine -> EngineeringContext -> RuntimeService -> FoundationRuntime` without skipping a layer. `validate_graph()`, `graph_statistics()`, `connected_components()`, `shortest_path()`, `subgraph()`, and the incremental-update methods below round out the engine's public surface.

**Incremental updates are caller-driven — a documented architectural limitation, not an oversight.** `KnowledgeGraph::add_object/remove_object/add_relationship/remove_relationship` and `KnowledgeGraphEngine::object_added/object_removed/relationship_added/relationship_removed` never require rebuilding the entire graph. However, since `RuntimeService`/`EngineeringContext` have no event-subscription mechanism (WP-REP-006 shipped Repository Events as publish-only, with no subscribers — see `platform/runtime/README.md`), the Knowledge Graph Engine has no way to detect a Foundation-side mutation automatically. A caller that just performed, or otherwise learned of, a mutation elsewhere in the repository must explicitly invoke the matching `object_added`/`object_removed`/`relationship_added`/`relationship_removed` method itself to keep the Knowledge Graph synchronized — the graph does not self-update, and nothing pushes it a notification. `refresh_graph()`/`reindex()` remain available as an explicit full-resync fallback when a caller doesn't want to track individual deltas.

**What this component deliberately does not do**, beyond the EKR-wide "SHALL NOT" list already stated above: it never communicates with the Repository directly, never performs persistence, never modifies packages, and never opens a transaction — the seven responsibilities above (Builder, Index, Validator, Incremental Updates, Algorithms, Statistics, Serialization) are all read/query/diagnostic operations over an in-memory structure that is discarded, like `RuntimeGraph`, whenever its owning handle goes away.

**Public C API / CLI / Studio.** See `platform/api/README.md`'s "Engineering Knowledge Graph Engine (WP-EKE-002)" section for the ten new `oep_kge_*` functions (`OEP_API_VERSION` 13 → 14) and `platform/cli/README.md`'s `oep engine build|validate|stats|components|export` entries. Studio gained Foundation Bridge FFI bindings for exactly the five items this work package's spec named (Graph Statistics, Validation Report, Connected Components, Subgraph Preview, Graph Export) — verified via `flutter analyze`/`flutter test` — with **no new UI screens**, consistent with the spec's own explicit "UI implementation remains out of scope" statement and with how WP-EKE-001's Studio integration was scoped immediately above.

## Engineering Query Engine (WP-EKE-003)

WP-EKE-003 adds a third set of components, still entirely inside `platform/oep_engine`, consuming `EngineeringContext` and the Knowledge Graph Engine only — concretely, `EngineeringQueryEngine`'s constructor takes a `KnowledgeGraphEngine&`, which itself only holds an `EngineeringContext&`, never `RuntimeService`/`FoundationRuntime` directly at this layer. The Engineering Query Engine (EQE) is a purely deterministic lookup/filter/traversal layer over already-materialized Knowledge Graph data — it never communicates with the Repository, never persists, never modifies Engineering Objects, never opens transactions, and never performs reasoning or inference. Five new files, `include/oep/engine/` + `src/`:

- `query_types.hpp/.cpp` — the shared vocabulary: `QueryCategory` (ten values — Object, Relationship, Domain, Type, Dependency, Neighborhood, Path, Reference, Metadata, Composite), `QueryFilter` (Object Type, Knowledge Domain, Relationship Type, Publisher, Package, Tags, Depth, Direction — every filter field named in this work package's spec, combinable, i.e. "multiple filters may be combined"), and `QueryRequest`/`QueryStatistics`.
- `query_planner.hpp/.cpp` — `QueryPlanner::plan(request, engine) -> QueryPlan`: builds an immutable `QueryPlan` (query type, filters, traversal strategy, indexes used, estimated cost, execution order) by consulting only the Knowledge Graph's already-maintained indexes' sizes/membership — every check is O(1)/O(log n). Planning never walks an edge or materializes a result, satisfying "Planning shall never execute the query" directly, not just by convention. Deterministic — replanning identical input always produces byte-identical plans.
- `query_executor.hpp/.cpp` — `QueryExecutor::execute(plan, engine) -> EngineeringQueryResult`: executes an already-built plan, read-only, tracking objects/relationships examined and traversal depth as it goes for `QueryStatistics`. Deterministic.
- `query_cache.hpp/.cpp` — `QueryCache`: caches immutable `QueryPlan`s and `EngineeringQueryResult`s, keyed by a canonical `cache_key(request)` derived from every `QueryRequest` field (category, ids, every `QueryFilter` field). See the caller-driven invalidation limitation below.
- `engineering_query_engine.hpp/.cpp` — `EngineeringQueryEngine`: the top-level facade, constructed from a `KnowledgeGraphEngine&`, exposing the five-method Public Runtime API this work package specifies: `plan_query()`, `execute_query()` (a plan-based overload plus a convenience request-based overload that plans then executes), `query_statistics()` (the most recently executed query's stats), `query_cache()`, `clear_query_cache()`.

**Six responsibilities, one intentionally folded rather than a separate module.** The work package names six responsibilities — Query Planner, Query Executor, Query Optimizer, Query Result Builder, Query Statistics, Query Cache. The first, second, fifth, and sixth are the four components above. The **Query Result Builder** is the immutable `EngineeringQueryResult` class itself (see the naming note below). The **Query Optimizer** was **folded into the Planner** rather than built as a separate module or file — strategy/index/cost selection during planning *is* the optimization step for this work package's scope, and no separate optimizer pass was needed or built. This is stated here plainly rather than left to be inferred, since a reader could otherwise expect a `query_optimizer.hpp` that does not exist.

**`EngineeringQueryResult`, not `QueryResult` — a deliberate naming disambiguation.** The immutable query-result class is named `EngineeringQueryResult` rather than the more obvious `QueryResult`, to avoid a symbol collision with WP-EKE-001's pre-existing `oep::engine::QueryResult`. This is the same disambiguation pattern already used for WP-EKE-002's `GraphPathResult`/`GraphSubgraphResult` (to avoid colliding with WP-EKE-001's `PathResult`/`SubgraphResult`), applied again here for the same reason.

**Ten query categories, all implemented in `QueryExecutor`:** Object (direct id lookup), Relationship (by relationship-type index), Domain (by domain/tag index), Type (by object-type index), Dependency (transitive `DependsOn` closure, BFS, with a direction filter supporting "what do I depend on" vs. "what depends on me"), Neighborhood (radius-bounded BFS), Path (shortest path via BFS), Reference (direct `References` edges, direction-filterable), Metadata (full scan matching publisher/package/tags — **all** tags required, AND not OR), Composite (full scan combining object_type + domain + publisher + package + tags, exercising "multiple filters may be combined").

**Query Statistics.** `QueryStatistics{execution_time_ms, objects_examined, relationships_examined, traversal_depth, indexes_used, result_count}`, exposed both embedded in every `EngineeringQueryResult` and via `EngineeringQueryEngine::query_statistics()` for the most recently executed query.

**Query Cache invalidation is caller-driven — a documented architectural limitation, the same pattern already established for WP-EKE-002's incremental updates.** The work package's own text says "Cache invalidation shall occur only when `EngineeringContext` refreshes," but since `EngineeringContext`/`RuntimeService` still have no event-subscription mechanism (WP-REP-006 remains publish-only), `QueryCache` has no way to detect a Knowledge Graph rebuild automatically. `EngineeringQueryEngine::clear_query_cache()` is a **caller-driven trigger** — a caller must explicitly invoke it after `KnowledgeGraphEngine::build_graph()`/`refresh_graph()` if subsequent queries should reflect the rebuilt graph. The cache does not self-invalidate and nothing pushes it a notification.

**What this component deliberately does not do**, beyond the EQE-wide "SHALL NOT" list already stated in this file's Principles section: it never communicates with the Repository directly, never performs persistence, never modifies Engineering Objects, never opens a transaction, and performs no reasoning or inference — every one of its ten query categories is a deterministic lookup/filter/traversal over an already-materialized `KnowledgeGraph`.

**Public C API / CLI / Studio.** See `platform/api/README.md`'s "Engineering Query Engine (WP-EKE-003)" section for the new `oep_eqe_*` functions (`OEP_API_VERSION` 14 → 15) and `platform/cli/README.md`'s `oep engine explain|cache|profile|clear-cache` entries plus the `--category` mode added to the existing `oep engine query` subcommand. Studio gained Foundation Bridge FFI bindings for exactly the five items this work package's spec named (Query execution, Query plans, Query statistics, Query profiles, Query cache) — verified via `flutter analyze`/`flutter test` — with **no new UI screens**, consistent with the spec's own explicit "UI implementation remains out of scope" statement and with how WP-EKE-001/WP-EKE-002's Studio integration was scoped above.

## Engineering Rules Engine (WP-EKE-004)

WP-EKE-004 adds a fourth set of components, still entirely inside `platform/oep_engine`, consuming `EngineeringContext`, the Knowledge Graph Engine, and the Engineering Query Engine — concretely, `RulesEngine`'s constructor takes references to all three, never `RuntimeService`/`FoundationRuntime`/repository storage directly. The Engineering Rules Engine (ERE) evaluates declarative engineering rules against the Knowledge Graph. **It does not perform validation itself — it provides the reusable rule evaluation framework a future Validation Engine and future reasoning systems are meant to consume.** It never modifies Engineering Objects, never opens a transaction, never performs persistence, and never performs AI inference. Six new files, `include/oep/engine/` + `src/`:

- `rule_types.hpp/.cpp` — the shared vocabulary: `RuleConditionKind` (the ten condition primitives, see below), `RuleCategory` (Structural, Connectivity, Dependency, Reference, Documentation, Metadata, Package — the seven categories the work package names), `RuleSeverity`, `RuleScope`/`RuleScopeKind` (AllObjects/ByObjectType/ByDomain/ByPackage/SingleObject), an immutable `RuleCondition` (kind plus its parameters — relationship type, tag, count threshold, as relevant to the kind), an immutable `EngineeringRule` (rule_id, name, description, category, severity, scope, a vector of `RuleCondition`, message, recommendation), `RuleDiagnostic` (`object_id`, `detail` — `object_id` empty for a graph-level diagnostic such as a cycle, since it isn't about one object), `RuleEvaluationStatus` (`Passed`/`Failed`/`NotApplicable`/`Error`), and the immutable `RuleEvaluationResult` (rule, status, message, affected_objects — sorted and deduplicated, diagnostics).
- `rule_registry.hpp/.cpp` — `RuleRegistry`: register/remove/enable/disable/enumerate rules, in-memory only. Rules exist for the lifetime of the process/handle that registered them — the registry performs no persistence of its own.
- `rule_context.hpp` — `RuleEvaluationContext`: immutable, giving the evaluator access to exactly the five things the work package names — `EngineeringContext`, the Knowledge Graph, the Query Engine, Graph Statistics (a snapshot taken at evaluation time via WP-EKE-002's `compute_statistics`), and Configuration (`RuleConfiguration`, a free-form string map reserved for future tunable thresholds; nothing in this work package's own rule set reads it yet).
- `rule_evaluator.hpp/.cpp` — `RuleEvaluator::evaluate(rule, context)`: the sole interpreter of condition primitives. First resolves the rule's `RuleScope` to a deterministic, sorted set of object ids (reusing `KnowledgeGraph`'s existing indexes from WP-EKE-002 — by type, by domain/tag, by package, or a single id), then checks each per-object condition against every scoped object, and separately checks graph-level conditions (`NoCycles`, `NoIsolatedObjects`) exactly once regardless of scope size, never once per object.
- `rules_engine.hpp/.cpp` — `RulesEngine`: the top-level facade, constructed from `EngineeringContext&`, `KnowledgeGraphEngine&`, and `EngineeringQueryEngine&`, exposing the exact five-method Runtime API this work package specifies — `register_rule()`, `evaluate_rule()`, `evaluate_all()`, `enabled_rules()`, `disabled_rules()` — plus the natural registry completions `remove_rule()`/`enable_rule()`/`disable_rule()`/`all_rules()`, and a `graph_ready()` precondition check callers can use before evaluating.

**The central design constraint: rules are data, not code — "No engineering rules shall be hardcoded into the engine."** This is the most architecturally important idea in this work package, so it is worth stating precisely rather than merely asserted. `RuleEvaluator`'s own source code contains no `if`/`switch` case for any *specific* engineering policy — nothing in it knows what a "Component" is, or that a Component must reference a Specification. It only knows how to interpret a small, fixed set of **~10 condition primitives** (`RuleConditionKind`: `RequiresRelationship`, `ForbidsRelationship`, `MinRelationshipCount`, `MaxRelationshipCount`, `RequiresTag`, `ForbidsTag`, `HasDescription`, `HasAuthor`, `NoCycles`, `NoIsolatedObjects`) generically, against whatever scope and parameters a caller supplies. An `EngineeringRule` that expresses an actual engineering policy — e.g. "every Component must have a `RequiresRelationship` condition targeting a Specification via `DependsOn`" — is constructed **purely as data** at the call site: CLI flags (`oep rules register`), the Public C API's `oep_rules_register` struct input, or a future rule-loading mechanism (not part of this work package). The evaluator never grows a new code path when a new policy is authored; only new data is supplied. This is the load-bearing distinction between "data-driven" and "hardcoded" for this module.

**The `HasDescription`/`HasAuthor` cross-reference — an honest implementation detail.** These two conditions need `EngineeringObject::description`/`author`, but `KnowledgeGraph`'s own lightweight nodes (WP-EKE-002) carry only `object_id`/`type`/`name`/`domains`/`package`/`publisher` — not `description`/`author`. Rather than extend `KnowledgeGraph`'s node shape just for these two conditions, `RuleEvaluator` resolves them by looking the object up in `EngineeringContext`'s own fuller `RuntimeGraph` (WP-EKE-001, which does carry the complete `EngineeringObject` record) via `EngineeringContext::graph().find_object(id)`. This is a small but real cross-reference between two of this module's own graph representations — worth explaining plainly so a future reader understands why `RuleEvaluator` reaches into `EngineeringContext` directly for exactly these two conditions, rather than only ever consulting `KnowledgeGraphEngine`.

**Scope resolution and graph-level conditions, briefly.** `RuleScope` resolves to a deterministic, sorted object-id set using `KnowledgeGraph`'s existing indexes — no new indexing was added for this work package. `NoCycles` performs a deterministic DFS cycle check restricted to one relationship type, reusing the same algorithm shape as WP-EKE-002's `graph_validator.cpp`'s own cycle detection rather than reimplementing it independently. `NoIsolatedObjects` requires every scoped object to have at least one edge. Both graph-level conditions are evaluated exactly once per rule evaluation, never once per scoped object — they are properties of the graph (or the scoped subgraph), not of any individual object.

**Rule evaluation is deterministic and read-only.** `RuleEvaluator::evaluate` never mutates the Knowledge Graph, the Runtime Graph, or any Engineering Object; two independent `RulesEngine` instances evaluating the same rule against the same graph always produce identical `RuleEvaluationResult`s (an explicit test requirement, verified — see below). `RuleEvaluationStatus::Error` is reserved for a genuinely malformed rule — e.g. a `RequiresTag` condition with no tag value set — not for "the rule failed"; a rule whose conditions are well-formed but not satisfied is `Failed`, and a rule whose scope matched zero objects (with no graph-level condition in play) is `NotApplicable`, never silently treated as `Passed`.

**What this component deliberately does not do**, beyond the EKR-wide "SHALL NOT" list already stated above: it never communicates with the Repository directly, never performs persistence, never modifies Engineering Objects, never opens a transaction, and never performs AI inference. It also, per its own stated purpose, does not decide what a repository's overall validity means or aggregate rule results into a pass/fail verdict for a repository — that is future Validation Engine work, deliberately left undone here.

**Public C API / CLI / Studio.** See `platform/api/README.md`'s "Engineering Rules Engine (WP-EKE-004)" section for the new `oep_rules_*` functions (`OEP_API_VERSION` 15 → 16) — including this API's first array-of-structs input, and the `oep_engineering_rule_t` input/output asymmetry — and `platform/cli/README.md`'s `oep rules list|register|enable|disable|evaluate|info` entries, including the CLI's documented process-local, non-persistent rule registry limitation. Studio gained Foundation Bridge FFI bindings for exactly the four items this work package's spec named (Rule Registry, Rule Evaluation, Rule Results, Rule Diagnostics) — verified via `flutter analyze`/`flutter test` — with **no new UI screens**, consistent with the spec's own explicit "UI implementation remains out of scope" statement and with how WP-EKE-001/WP-EKE-002/WP-EKE-003's Studio integration was scoped above.

## Engineering Validation Engine (WP-EKE-005)

WP-EKE-005 adds a fifth set of components, still entirely inside `platform/oep_engine`, consuming `EngineeringContext`, the Knowledge Graph, the Query Engine, and the Rules Engine — concretely, `ValidationEngine`'s constructor takes references to all four, never `RuntimeService`/`FoundationRuntime`/repository storage directly. The Engineering Validation Engine (EVE) executes engineering rules against Engineering Objects, Packages, and complete Engineering Contexts, producing immutable Validation Reports. It never modifies Engineering Objects, never opens a transaction, and never performs persistence. Two new files, `include/oep/engine/` + `src/`:

- `validation_types.hpp/.cpp` — the shared vocabulary: `ValidationProfile` (`Structural`/`Connectivity`/`Documentation`/`Metadata`/`Complete` — the exact five the work package names), `ValidationTarget`/`ValidationScope` (the five validation scopes: Single Object, Multiple Objects, Complete Engineering Context, Installed Package, Arbitrary Query Result), an immutable `ValidationSession` (session_id — a UUIDv4 via the same `oep::repository::generate_uuid_v4()` Foundation already uses elsewhere, start_time_utc, end_time_utc, target, active_rule_ids, profile, statistics), an immutable `ValidationFinding` (finding_id — deterministically `"FIND-" + rule_id`, rule_id, severity, category, message, recommendation, affected_objects, diagnostics), `ValidationStatistics` (rules_evaluated/passed/failed/not_applicable/errored, execution_time_ms), and an immutable `ValidationReport` (session, findings, statistics, pass_count, warning_count, error_count, critical_count, execution_time_ms) — every field named in the work package's spec, exactly.
- `validation_engine.hpp/.cpp` — `ValidationEngine`: the facade, constructed from `EngineeringContext&`, `KnowledgeGraphEngine&`, `EngineeringQueryEngine&`, and `RulesEngine&`, exposing the six-method Runtime API this work package specifies — `create_validation_session()`, `validate_object()`, `validate_package()`, `validate_context()`, `validation_report()`, `validation_statistics()` — plus the natural completions `validate_objects()` (Multiple Objects scope) and `validate_query_result()` (Arbitrary Query Result scope), covering all five named Validation Scopes. Sessions are held in-memory for the lifetime of the owning `ValidationEngine`, never persisted — the same in-memory-only model WP-EKE-004's `RuleRegistry` already established.

**The central design constraint, a direct continuation of WP-EKE-004's own principle: the Validation Engine never embeds engineering rules — it only composes the Rules Engine.** The *only* rule-category policy this module contains anywhere is `profile_includes()` in `validation_engine.cpp` — the small, fixed `ValidationProfile -> RuleCategory` mapping (Structural/Connectivity/Documentation/Metadata each select the identically-named `RuleCategory`; Complete selects every enabled rule regardless of category). `ValidationEngine` never constructs, evaluates, or interprets a single `RuleCondition` itself — every actual rule check happens inside WP-EKE-004's `RuleEvaluator`, reached exclusively through `RulesEngine::evaluate_rule`. Where WP-EKE-004's own central constraint was "rules are data, not code" inside the evaluator, WP-EKE-005's is the layer above it: "validation is composition, not a second rule engine." A future reader should recognize this as the same architectural discipline applied one layer up.

**The second architecturally interesting design choice: target-narrowing composition instead of re-implementing scope resolution.** Rather than re-deriving which objects a rule concerns for a specific validation target (e.g. "does object X specifically violate this rule"), `ValidationEngine` evaluates every profile-selected enabled rule **in full** via `RulesEngine::evaluate_rule` — using that rule's own `RuleScope`, exactly as WP-EKE-004 already resolves it — then **narrows** each result's `affected_objects`/`diagnostics` down to whatever the requested `ValidationTarget`'s object set intersects. A rule whose full evaluation failed, but whose failure did not touch any object inside a narrower target, is treated as **Passed** for that specific target — no finding is produced. This is the precise, correct answer to "does THIS target violate the rule," achieved entirely through composition and filtering over `RuleEvaluator`'s existing output, rather than duplicating its scope-resolution logic in a second place. One Finding is produced per rule whose narrowed evaluation is Failed or Error; Passed/NotApplicable rules produce no finding but are still counted in `ValidationStatistics`. Graph-level diagnostics (e.g. a `NoCycles` violation, which has an empty `object_id` since it isn't about one object) are only included for whole-context (`EngineeringContext`) validation, never narrowed into a single-object/package/query-result target — a graph-level fact cannot be meaningfully attributed to a narrower target.

**What this component deliberately does not do**, beyond the EVE-wide "SHALL NOT" list already stated in this file's Principles section: it never communicates with the Repository directly, never performs persistence, never modifies Engineering Objects, never opens a transaction, and never implements reasoning or AI — it produces no rule logic of its own, only a category-selection policy and a target-narrowing filter over `RulesEngine`'s output.

**Public C API / CLI / Studio.** See `platform/api/README.md`'s "Engineering Validation Engine (WP-EKE-005)" section for the new `oep_validation_*` functions (`OEP_API_VERSION` 16 → 17) — including the deliberately omitted `affected_objects`/`diagnostics` fields on `oep_validation_finding_t` and the deliberately omitted `oep_validation_validate_query_result` function — and `platform/cli/README.md`'s `oep evalidate profiles|object|package|context|report` entries, including the CLI's naming-collision decision (`evalidate`, not `validate` — see below) and its documented process-local, non-persistent session/rule-registry limitation. Studio gained Foundation Bridge FFI bindings for exactly the five items this work package's spec named (Validation Session, Validation Report, Validation Findings, Validation Statistics, Validation Profiles) — verified via `flutter analyze`/`flutter test` — with **no new UI screens**, consistent with the spec's own explicit "UI implementation remains out of scope" statement and with how WP-EKE-001/WP-EKE-002/WP-EKE-003/WP-EKE-004's Studio integration was scoped above.

**CLI naming — `oep evalidate`, not `oep validate` — the same kind of collision decision WP-EKE-001 already made for `oep engine` vs. `oep graph`.** The work package's literal spec text says `oep validate object/package/context/report/profiles`, but `oep validate [repository]` already exists in this CLI as a long-standing, unrelated command — Repository Validation via `FoundationRuntime::validator()`, checking Foundation Repository structural integrity, not engineering rules. Reusing that name for the Engineering Validation Engine would shadow or break the existing command, so the new group was named `oep evalidate` (Engineering VALIDATE) instead, keeping every subcommand name from the spec exactly as written. This is the same pattern WP-EKE-001 already established when it named its command group `engine` rather than `graph` to avoid colliding with the pre-existing WP-016 `oep graph` command — worth recognizing as a recurring pattern in this series, not a one-off. **Process-local limitation:** every `oep evalidate` CLI invocation starts with a fresh, empty, in-memory `RulesEngine`/`ValidationEngine` — no persistence across invocations, exactly the same documented limitation `oep rules` (WP-EKE-004) already carries, so `object`/`package`/`context` validate against zero registered rules (a trivial, vacuous pass) unless rules were registered earlier in the SAME process, and `report <session-id>` can never resolve a session_id from an earlier invocation. See `platform/cli/README.md` for the full statement of this limitation.

## Engineering Analysis & Reasoning Engine (WP-EKE-006)

WP-EKE-006 adds a sixth set of components, still entirely inside `platform/oep_engine`, consuming `EngineeringContext`, the Knowledge Graph, the Query Engine, the Rules Engine, and the Validation Engine only — concretely, `ReasoningEngine`'s constructor takes references to all five, never `RuntimeService`/`FoundationRuntime`/repository storage directly. The Engineering Analysis & Reasoning Engine (EARE) analyzes engineering knowledge, derives deterministic conclusions, explains those conclusions, and produces reusable engineering analyses. It never modifies Engineering Objects, never opens a transaction, never performs persistence, and never calls external AI services — every result is deterministic. Four new files, `include/oep/engine/` + `src/`:

- `analysis_types.hpp` — the four immutable Report classes: `DependencyReport`, `ImpactReport`, `ReachabilityReport`, `RootCauseReport`, each carrying an `evidence()` string naming exactly which algorithm/traversal produced it.
- `analysis_engine.hpp/.cpp` — `AnalysisEngine`: four PURE, deterministic structural algorithms over the Knowledge Graph, reusing WP-EKE-002's `GraphAlgorithms`/`KnowledgeGraph` directly rather than reimplementing graph traversal — `analyze_dependencies` (transitive OUTGOING `DependsOn` closure, BFS), `analyze_impact` (transitive INCOMING `DependsOn` closure — the reverse direction: "what would be affected if this object changes"), `analyze_reachability` (shortest path via `GraphAlgorithms::shortest_path`), `analyze_root_cause` (takes a symptom object plus a caller-supplied set of "objects with findings," ranks the symptom's own transitive dependencies that appear in that set by ascending BFS depth — closest first — as root-cause candidates, and computes the shortest `DependsOn` path from the top candidate to the symptom as the "failure chain").
- `reasoning_types.hpp/.cpp` — the reasoning vocabulary: immutable `ReasoningSession` (session_id — a UUIDv4 via the same `oep::repository::generate_uuid_v4()` Foundation already uses elsewhere, start_time_utc, end_time_utc, objective, starting_objects, queries_executed, rules_applied, validation_results, conclusions, evidence), `EvidenceGraph`/`EvidenceNode`/`EvidenceRelationship` (a TEMPORARY, per-session graph — never the Knowledge Graph itself, discarded when the session ends, never mutating anything), `EvidenceKind` (5 values: an Engineering Object, a Relationship, a rule evaluation, a validation finding, or a derived conclusion), immutable `EngineeringConclusion` (conclusion_id, statement, confidence, supporting_evidence_ids, referenced_objects, referenced_rules, referenced_findings, explanation), immutable `EngineeringRecommendation` (5 kinds, always evidence-referenced), and immutable `ReasoningReport` (session + recommendations + execution_time_ms).
- `reasoning_engine.hpp/.cpp` — `ReasoningEngine`: the deeper, evidence-based reasoning apparatus, built ON TOP OF `AnalysisEngine` plus `RulesEngine`/`ValidationEngine`, exposing the exact eight-method Runtime API this work package specifies (`analyze_dependencies`/`analyze_impact`/`analyze_root_cause`/`analyze_reachability`/`create_reasoning_session`/`execute_reasoning`/`reasoning_report`/`engineering_recommendations`).

**Two analysis/reasoning primitives split across two classes — worth explaining clearly why.** `AnalysisEngine`'s four public methods alone satisfy the work package's 8-item "Analysis Engine" responsibilities list (Dependency Analysis, Impact Analysis, Reachability Analysis, Change Propagation [= Impact Analysis's own affected-object set], Root Cause Analysis, Failure Chain Analysis [= `RootCauseReport`'s own `failure_chain` field], Dependency Tree Generation [= `DependencyReport`'s own flattened closure], Affected Object Discovery [= `ImpactReport`'s own `affected_object_ids`]) — the 8 items map onto the 4 public methods+report fields, not 8 separate API entries, matching the work package's own Runtime API section, which names only `analyze_dependencies`/`analyze_impact`/`analyze_root_cause`/`analyze_reachability` (4 entries), confirming this consolidation is the correct reading of the spec. `ReasoningEngine` is the deeper apparatus where "every conclusion must reference its supporting evidence" is actually enforced. `ReasoningEngine::analyze_root_cause(symptom_object_id)` is a DIFFERENT, self-validating overload from `AnalysisEngine`'s two-argument version — it runs its own validation pass internally via `ValidationEngine`, then delegates to `AnalysisEngine`, so callers don't need to pre-compute the finding set themselves; `create_reasoning_session`/`execute_reasoning`/`reasoning_report`/`engineering_recommendations` are the main flow.

**The central design of `execute_reasoning` — the most architecturally interesting part of this work package.** For each starting object, it (1) runs `analyze_dependencies`/`analyze_impact` (recording each as a "query executed"), (2) validates the starting object PLUS its full transitive dependency set in ONE shared `ValidationEngine` pass (Complete profile — avoiding redundant re-validation per object), (3) builds a temporary, session-scoped `EvidenceGraph` where every `EvidenceNode` names exactly where its content came from (an Engineering Object, a Relationship, a rule evaluation, or a validation finding — `EvidenceKind`'s 5 values), deduplicating object-evidence nodes across the session via a small id-keyed map so the same object referenced by multiple conclusions gets exactly one evidence node, (4) derives `EngineeringConclusion`s (a dependency-count conclusion, an impact conclusion if non-empty, and — if any validation findings touch the object or its dependencies — a findings/root-cause conclusion), each with a NON-EMPTY `supporting_evidence_ids` list (enforced as an invariant, verified directly in the C++ test suite by checking that every referenced evidence id resolves to a real node in that session's own `EvidenceGraph`), and (5) derives `EngineeringRecommendation`s of all 5 kinds the work package names (`SimilarComponent` — objects sharing a domain/tag; `ConnectedSystem` — direct graph neighbors; `RelatedProcedure` — a direct neighbor whose `ObjectType` is `Procedure`; `FollowUpValidation` — recommended re-validation when findings exist; `AdditionalInspection` — recommended inspection of the top root-cause candidate when findings exist), each ALSO carrying non-empty evidence.

**Confidence is deterministic arithmetic, never probabilistic/AI-derived.** The exact documented formula, defined in `reasoning_engine.cpp`'s own doc comment: `confidence = min(1.0, 0.5 + 0.1 * evidence_count)`. Since every conclusion has at least one piece of evidence, confidence is always >= 0.6.

**What this component deliberately does not do**, beyond the EARE-wide "SHALL NOT" list already stated in this file's Principles section (never accesses repository storage directly, never modifies Engineering Objects, never opens transactions, never performs persistence, never calls external AI services): it never re-implements graph traversal — every `AnalysisEngine` algorithm reuses WP-EKE-002's `GraphAlgorithms`/`KnowledgeGraph` directly.

**Public C API / CLI / Studio.** See `platform/api/README.md`'s "Engineering Analysis & Reasoning Engine (WP-EKE-006)" section for the new `oep_analysis_*`/`oep_reasoning_*` functions (`OEP_API_VERSION` 17 → 18) — including the self-validating root-cause routing, the fetch-by-id precedent for conclusions/recommendations, and the deliberately minimal Evidence Graph exposure — and `platform/cli/README.md`'s `oep analysis dependencies|impact|root-cause|reachability` and `oep reasoning execute|report|evidence|recommendations` entries, including the CLI's `oep reasoning recommendations` naming decision (not a bare top-level `oep recommendations`) and its documented process-local, non-persistent limitation. Studio gained Foundation Bridge FFI bindings for exactly the five items this work package's spec named (Analysis Reports, Reasoning Sessions, Evidence Graphs, Engineering Conclusions, Recommendations) — verified via `flutter analyze`/`flutter test` — with **no new UI screens**, consistent with the spec's own explicit "UI implementation remains out of scope" statement and with how WP-EKE-001/WP-EKE-002/WP-EKE-003/WP-EKE-004/WP-EKE-005's Studio integration was scoped above.

## Engineering Intelligence Platform (WP-EKE-007)

WP-EKE-007 adds a seventh and final set of components, still entirely inside `platform/oep_engine`, but at a different altitude from the six before it: where WP-EKE-001 through WP-EKE-006 each added ONE new engine beneath the stack, the Engineering Intelligence Platform (EIP) is the TOP-LEVEL orchestration layer that composes ALL SIX of them (Knowledge Graph, Query, Rules, Validation, Analysis, Reasoning) into one unified engineering runtime, intended for consumption by Studio, Engineering Acquisition, Engineering Exchange, external SDKs, and future Engineering AI systems. `EngineeringIntelligencePlatform`'s constructor takes references to all six lower engines plus `EngineeringContext` — never `RuntimeService`/`FoundationRuntime`/repository storage directly, and it never repeats or reimplements any lower engine's own logic. Three new files, `include/oep/engine/` + `src/`:

- `intelligence_types.hpp/.cpp` — the shared vocabulary: `RuntimeMetrics` (platform-wide counters: query/validation/analysis/reasoning counts, cache hits/misses, active/total session counts, total execution time — runtime-only, never persisted), `SessionStatistics` (the same shape, but per-session), the immutable `KnowledgeSession` (session_id, created_utc, last_active_utc, closed, query/validation/analysis/reasoning history, recommendations, active_objects, active_packages, statistics — see the `EngineeringContext` caveat below), `WorkflowKind`/`WorkflowResult` (the one common shape every Workflow returns), `InspectionTargetKind`/`InspectionReport` (the one common shape `inspect_object`/`inspect_package`/`inspect_context` all return), `EngineeringHealthReport`, `EngineeringSummaryReport`.
- `knowledge_session_manager.hpp/.cpp` — `KnowledgeSessionManager`: pure in-memory bookkeeping (no persistence, no Foundation access, mirroring WP-EKE-004's `RuleRegistry`/WP-EKE-005's `ValidationEngine` session-map pattern) implementing all five lifecycle operations the work package names — Create, Resume (marks `last_active_utc`; fails for an unknown or already-closed session_id), Clone (a new session inheriting the same history/active-set CONTENT as the source session, but a FRESH, zero-valued `SessionStatistics` window — a deliberate choice: cloning duplicates what was already investigated, not how long it took), Close, Export Summary (a short, human-readable text block). `EngineeringIntelligencePlatform` owns the single instance of this class and is the only thing that mutates a session's history/statistics, via a package-private append/touch surface.
- `engineering_intelligence_platform.hpp/.cpp` — `EngineeringIntelligencePlatform`: the top-level façade described above.

**The central architectural decision: nine named responsibilities, only ONE built as its own separate public class — a deliberate reading of the work package's own stated principle, not an oversight.** The work package's Responsibilities section names nine items: Engineering Intelligence Platform, Knowledge Session Manager, Workflow Engine, Service Orchestrator, Unified Engineering API, Context Manager, Shared Cache Manager, Runtime Metrics, and Engine Pipeline. Of these, only the **Knowledge Session Manager** was implemented as its own separately-instantiated public class (`knowledge_session_manager.hpp`), because session bookkeeping is a genuinely independent concern with its own lifecycle (Create/Resume/Clone/Close/Export), independently testable in isolation. Every other responsibility — Workflow Engine, Service Orchestrator, Context Manager, Shared Cache Manager, Runtime Metrics, and the informal "Engine Pipeline" concept — is realized as `EngineeringIntelligencePlatform`'s OWN public methods and private composition, never as a separate public type. This is a deliberate reading of the work package's own Unified Engineering API principle: *"Implement a single façade... Consumers should not know which engine performs the work."* Taken to its logical conclusion, a Workflow Engine/Service Orchestrator/Context Manager/Shared Cache Manager/Runtime Metrics collector that were EACH their own separately-instantiated public class would themselves constitute additional "which engine performs the work" surface area for a consumer to learn — exactly what the Unified API principle argues against. Every one of those five responsibilities remains fully implemented and independently testable via `EngineeringIntelligencePlatform`'s own public methods:

- **Workflow Engine** ("Support: Inspect, Query, Validate, Analyze, Reason, Recommend. Each workflow executes through the platform without exposing internal engines") — six public, session-scoped methods (`inspect`/`query`/`validate`/`analyze`/`reason`/`recommend`, each taking an explicit `session_id`), each returning the one common `WorkflowResult{kind, success, summary, object_ids, execution_time_ms}` shape regardless of which lower engine(s) it internally composed, and each appending a description to the matching session history list (`query_history`/`validation_history`/`analysis_history`/`reasoning_history`) plus incrementing that session's execution-time statistic.
- **Service Orchestrator** ("Compose all lower engines... The caller never invokes multiple engines directly") — eight STATELESS methods (no session required): `inspect_object`/`inspect_package`/`inspect_context` (the one common `InspectionReport` shape, differentiated by `InspectionTargetKind`, each composing a Knowledge Graph membership/index lookup PLUS a fresh Complete-profile Validation Engine pass in one call), `engineering_summary` (Knowledge Graph statistics + validation pass/finding counts in one call), `engineering_health` (see the deterministic formula below), `engineering_dependencies`/`engineering_trace` (direct pass-throughs to the Analysis Engine, exposed here purely so a caller never needs to reach the Analysis Engine directly), `engineering_recommendations` (creates and executes an ephemeral Reasoning Engine session internally in ONE call, returning just the resulting recommendations — the clearest example of hiding a multi-step reasoning workflow behind a single orchestrated call). The Workflow methods `inspect`/`validate`/`analyze`/`reason`/`recommend` call these same orchestrator methods internally, then additionally record session history — this composition (Workflow -> Service Orchestrator -> lower engine(s) -> session history + Runtime Metrics) is the work package's informally-named "Engine Pipeline."
- **Context Manager** ("Manage: Active Engineering Contexts, Loaded Knowledge Sessions, Session Switching, Context Lifetime, Resource Cleanup") — `switch_session`/`current_session_id` (a convenience for a caller like the CLI that wants to avoid re-passing a `session_id` everywhere; every Workflow method still takes an EXPLICIT `session_id` and never implicitly relies on "current"), `cleanup()` (closes every open session and invalidates every cache in one call). **NOTE on "Active Engineering Contexts" (plural):** this platform, like every engine beneath it, operates against exactly ONE `EngineeringContext` per runtime handle — there is no multi-repository/multi-context architecture anywhere in this codebase. A `KnowledgeSession` therefore does NOT own a separate `EngineeringContext` instance; it is a logical grouping of history/active-object/active-package state layered over the single shared `EngineeringContext` every session ultimately reads through. This is documented explicitly in `intelligence_types.hpp`'s own doc comment on `KnowledgeSession`, not silently implied, since the work package's field list names "EngineeringContext" as if each session had its own.
- **Shared Cache Manager** ("Coordinate cache usage across: Query Engine, Graph Engine, Analysis Engine, Reasoning Engine. Provide deterministic invalidation") — `invalidate_caches()` clears the Query Engine's `QueryCache` (WP-EKE-003) — **the ONLY lower engine that maintains an actual cache today**; the Knowledge Graph, Analysis, and Reasoning Engines always compute fresh on each call, so "coordinating" them means this is the ONE call site a caller needs regardless of which lower engines gain their own caches in a future work package. Documented as an honest reflection of the current architecture, not a fabricated multi-cache coordination mechanism.
- **Runtime Metrics** ("Collect: Query Counts, Validation Counts, Analysis Counts, Reasoning Counts, Cache Statistics, Session Statistics, Execution Times. Metrics are runtime-only. No persistence") — a `RuntimeMetrics` struct the platform increments as it dispatches every workflow/orchestrator call, retrievable via `runtime_metrics()`; distinct from each individual `KnowledgeSession`'s own `SessionStatistics` (platform-wide vs. per-session).

**`engineering_health()` — a deterministic 0-100 score, never a probabilistic estimate.** Computed as `100 * passed / (passed + failed)` (defaulting to `100` when nothing was evaluated, since "nothing to report" is not unhealthy) via a Complete-profile Validation Engine pass over the whole context — pure arithmetic over validation pass/fail counts, exactly the same "deterministic arithmetic, never AI-derived" discipline WP-EKE-006's confidence formula already established for this codebase.

**Knowledge Sessions**, `intelligence_types.hpp`'s immutable `KnowledgeSession` — session_id (a UUIDv4 via the same `oep::repository::generate_uuid_v4()` Foundation already uses elsewhere), created_utc, last_active_utc, closed, query/validation/analysis/reasoning history, recommendations, active_objects, active_packages, statistics — exactly the fields the work package names, with the `EngineeringContext` caveat documented above.

**What this component deliberately does not do**, straight from the work package's own "The Engineering Intelligence Platform SHALL" list: it never accesses repository storage directly, never implements persistence, never implements package management, never implements trust verification, never implements dependency resolution, and never calls external AI systems. It consumes only the public APIs of the Engineering Runtime, Knowledge Graph, Query Engine, Rules Engine, Validation Engine, and Analysis Engine, plus the Reasoning Engine.

**Public C API / CLI / Studio.** See `platform/api/README.md`'s "Engineering Intelligence Platform (WP-EKE-007)" section for the new `oep_eip_*` functions (`OEP_API_VERSION` 18 → 19) — including the `engineering_recommendations` message-string-list scope decision and the session-id-buffer convention reuse — and `platform/cli/README.md`'s `oep session create|list|close`, `oep inspect`, `oep summary`, `oep metrics`, and `oep workflow` entries, including the CLI's process-local, non-persistent session limitation and the `oep workflow` single-invocation convenience pattern. Studio gained Foundation Bridge FFI bindings for exactly the five items this work package's spec named (Knowledge Sessions, Runtime Metrics, Engineering Summary, Workflow Execution, Session Management) — verified via `flutter analyze`/`flutter test` — with **no new UI screens**, consistent with the spec's own explicit "No UI work in this package" statement and with how WP-EKE-001 through WP-EKE-006's Studio integration was scoped above.

This closes out the Engineering Knowledge Engine's core architecture as specified across WP-EKE-001 through WP-EKE-007. It does not, by itself, imply that Studio UI screens, Engineering Acquisition/Exchange integration, external SDKs, or "future Engineering AI systems" (all named as EIP consumers in WP-EKE-007's own spec text) are built — those remain future work, consistent with every "no new UI screens" note recorded above.
