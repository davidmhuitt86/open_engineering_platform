# EAM / Reference Vault — Milestone 2 Readiness Assessment (WP-017)

Companion to `EAM_REFERENCE_VAULT_IMPLEMENTATION_AUDIT.md` and `EAM_REFERENCE_VAULT_GAP_ANALYSIS.md`. This document covers testing, failure/recovery behavior, the security/trust boundary, performance, the defects found and fixed during this audit, and the final Milestone-2 readiness decision.

## Security / Trust Boundary Review

- **What is trusted**: nothing is trusted until it has passed Integrity Verification (SHA-256, recomputed) *and* Metadata Extraction (status `Extracted`) *and* the Reference Vault's own final re-hash immediately before publication. A `VaultEntry`'s existence is the platform's actual trust anchor — three independent checks must all agree.
- **What hash establishes integrity**: SHA-256, generated by `hash_file_sha256` (PicoSHA2), recomputed fresh at two separate points (Verification, then again at Vault publication) rather than trusted-and-forwarded — confirmed by direct code reading, not assumed from documentation.
- **Can Vault contents be modified?** No mutating route exists for `/vault` at all (§ implementation audit §7) — structural, not conventional, immutability.
- **Is modification detectable?** Only at publication time (the final re-hash). **There is no ongoing/periodic fixity check** — if the file on disk were altered after publication (e.g. by something outside this service entirely, or bit rot), nothing here would ever notice. This is a real, disclosed gap (already noted in README's own "Future Considerations"; confirmed still true) — classified **M1 GAP**, not blocking M2, but worth a dedicated future work package for long-term archival integrity.
- **Can provenance be falsified?** Not through this API — every provenance field on `reference_vault` is a real foreign key resolved server-side from prior, already-verified records; nothing in the API accepts a client-supplied `source_id`/`verification_id`/etc. that isn't independently re-validated (§ implementation audit §7's seven Validation Rules).
- **Can publication be bypassed?** No — `POST /vault` is the only creation path, and it enforces all seven rules unconditionally; there is no back door (e.g. no direct-insert admin route, no way to mark a `VaultEntry` published without going through `ReferenceVaultService::publish`).
- **Authentication**: **none exists anywhere in this API** — no `Authorization` header handling, no API keys, no session model, confirmed by `grep` across the entire `src/api/`/`include/oep/acquisition/api/` tree (zero matches). This is explicitly out of scope per every WP-002 through WP-009's own "Do NOT implement: Authentication providers," so this is **not** a defect relative to M1's own ratified scope — but it is a real, load-bearing condition for M2 readiness (see Final Recommendation) if this service is ever reachable from anything other than a fully trusted local network.
- **New finding this audit surfaced (see ADR-0003, and implementation audit §4): `HttpConnector` is real, registered, and reachable today, with no destination-host allowlisting against the Official Source Registry.** This is the most significant trust-boundary finding of the whole audit — a live, unauthenticated `POST /downloads` request can direct this process to make an outbound HTTP request to any host reachable from wherever the process runs, including internal/private network addresses (SSRF-shaped). Combined with "no authentication anywhere," this means **anyone who can reach this API today can make it originate arbitrary outbound HTTP requests.** This was not introduced by WP-017; it predates this audit (§ ADR-0003's provenance finding). It is the single largest reason this audit does not recommend an unconditional "READY."

## Performance / Operational Review

- **Large-file behavior**: `hash_file_sha256` streams (confirmed via its own test covering content larger than the streaming buffer) — no full-file memory load. `HttpConnector::fetch` also streams via a content-receiver callback, not buffering the whole response in memory.
- **File-copy behavior**: Vault publication uses `std::filesystem::copy_file`, a single OS-level copy — reasonable for M1's expected artifact sizes (engineering documents, not multi-GB files); no obvious inefficiency found.
- **Hashing cost**: SHA-256 is computed twice per artifact across its lifetime (once at Verification, once again at Vault publication) — a deliberate, disclosed integrity tradeoff (§ implementation audit §5), not an oversight; acceptable for M1's synchronous, low-volume design.
- **Database transactions**: every repository method is one `pqxx::work`, committed once — no long-held transactions found, no obvious lock-contention risk at M1's expected scale.
- **Duplicate publication**: rejected cheaply, at both the Service layer (an indexed `list` filter by `metadata_id`) and the database layer (`UNIQUE` constraint) — no wasted work.
- **Filesystem layout**: two-hex-character sharding keeps any single directory from accumulating unbounded entries — a reasonable, standard content-addressable-storage layout; no scalability concern found at M1's scope.
- **Startup behavior**: a database connection failure is logged as a warning, never fatal (confirmed for every repository construction site in `main.cpp`) — the process degrades gracefully rather than crash-looping.
- **Synchronous API operations**: `POST /downloads`, `/verifications`, `/metadata`, `/vault` are all fully synchronous — acceptable and correctly justified for M1 (`StubConnector` completes in microseconds; even `HttpConnector` against a small artifact would complete in well under typical HTTP client timeouts), **but this becomes a real operational concern the moment `HttpConnector` is used against a large or slow real-world artifact**: the calling HTTP request to `POST /downloads` would block for the full transfer duration, with no way for a client to do anything but wait or hit its own timeout. This is a direct consequence of §"Security/Trust Boundary"'s finding that `HttpConnector` is live — the "no async infrastructure needed yet" reasoning in every prior WP's README section was written when only `StubConnector` existed and no longer fully holds now that a real, potentially-slow connector is registered.
- **Connection pooling**: one `pqxx::connection` held per repository instance for the process's own lifetime (7 repositories → 7 held connections) — already disclosed in README's own "Future Considerations" as a reassess-later item; not a demonstrated problem at M1's expected request volume, so this audit made no change here.

No asynchronous infrastructure was introduced by this audit (per the task's own explicit instruction not to add async infrastructure absent a demonstrated need) — the one place a real need now demonstrably exists (`HttpConnector` under real load) is flagged as a **Milestone-2 readiness condition** below, not fixed here, since building it would be exactly the kind of speculative/out-of-scope engineering this task prohibits without a WP asking for it.

## Defects Found

1. **Reference Vault publication could leave an orphaned file with zero referencing database rows** if the repository insert failed after a fresh filesystem copy (§ implementation audit §8). Root cause: the copy and the insert are not one atomic operation across two different systems (filesystem, PostgreSQL).
2. **`reference_vault`'s three non-unique foreign keys (`verification_id`, `download_session_id`, `source_id`) had no dedicated index**, breaking the pattern every other migration in this codebase established (§ implementation audit §10).
3. **`HttpConnector` performs real network communication, contradicting WP-005/WP-006's explicit Milestone-1 exclusion, and `README.md`'s own claims** (§ implementation audit §4, ADR-0003). Not a code defect in the traditional sense — the connector itself is well-implemented and tested — but a genuine scope/documentation defect with real security implications (see below).
4. **`HttpConnector`'s `fetch` does not validate the requested host against the Official Source Registry's `base_url` for the resolving Job's source**, and follows redirects unconditionally — an SSRF-shaped gap (§ Security/Trust Boundary, above).
5. **Two pre-existing test fixtures were not actually repeatable across separate process runs, and this audit demonstrated it by actually running them (per this task's own "do not report tests pass without execution" instruction) rather than trusting the README's test-suite description.** `tests/test_download_service.cpp`'s `make_workspace()` and `tests/test_reference_vault_service.cpp`'s new orphan-cleanup test both built their scratch paths from a purely sequential, in-process counter with no real-time or random component. The OS temp directory these paths live under is never cleaned up between separate invocations of the compiled test binary, and Catch2 registers/executes test cases in a fixed, deterministic order — so the *same* destination path was computed on every single run of the binary. For `test_download_service.cpp`, a prior run's own leftover placeholder file was still there on the next run, and `StubConnector::fetch` **correctly and safely** refused to overwrite it (`overwrite` defaults `false`), which `DownloadService` then correctly recorded as a `Failed` download — a real, reproducible test failure (`DownloadService.start_download completes successfully end to end`, confirmed failing in both a full-suite run and in isolation) caused entirely by test-fixture non-idempotency, not by any product defect. This is exactly the class of thing "run the tests, don't just read about them" is meant to catch.

## Defects Fixed (this audit)

- **#1 fixed**: `ReferenceVaultService::publish` now tracks whether it performed a fresh copy and removes that file if the subsequent repository insert throws, without ever touching a file a different, already-committed `VaultEntry` legitimately owns (a dedup hit). Two new regression tests added (`test_reference_vault_service.cpp`).
- **#2 fixed**: additive migration `V9__reference_vault_fk_indexes.sql` adds the three missing indexes; `V1`–`V8` left untouched. One new regression test added (`test_vault_migration.cpp`); test fixture (`vault_test_support.cpp`) updated to apply `V9`.
- **#5 fixed**: both `make_workspace()` (`test_download_service.cpp`) and the new orphan-cleanup test's own scratch content (`test_reference_vault_service.cpp`) now fold a real-time (`std::chrono::steady_clock`) nonce into their paths/content, so every run of the binary is guaranteed a fresh, never-before-seen path regardless of how many times the binary has run before. No production code was touched for this fix — it is purely a test-fixture correction, verified by running the full suite twice in direct succession afterward with identical, fully-passing results both times (see Test Results).

## Defects NOT Fixed (deliberately — require a decision, not code)

- **#3 and #4** are documented in `ADR-0003-HTTPCONNECTOR-SCOPE-DISCREPANCY.md` rather than fixed unilaterally. Neither "silently remove `HttpConnector`" nor "silently add SSRF protection and call it done" is something this audit's own scope authorizes without a decision from whoever owns Milestone-1/M2 scope — see that ADR's three options (A/B/C). This is the single biggest open item blocking an unconditional "READY."

## Remaining Gaps

See `EAM_REFERENCE_VAULT_GAP_ANALYSIS.md`'s full capability table. Summarized:
- No Acquisition Record entity matching SDD-R015's rich chain-of-custody model (workstation, DNS, TLS fingerprint, HTTP headers, redirect chain) — **M2 REQUIRED**, the largest architecture-vs-implementation gap found.
- No descriptive Vault metadata (title, author, keywords, revision, product family, industry, technology) — **M1 GAP / M2 REQUIRED**.
- No version history / related-Vault-Object linking — **M2 REQUIRED**.
- No search/indexing — **M2 REQUIRED** (depends on the above).
- No periodic fixity/re-hash checking — **M1 GAP**, an operational job, not necessarily a new work package.
- No raw-artifact-bytes retrieval route (`GET /vault/{id}` returns metadata, not the file itself) — **M1 GAP**, small, worth closing before external tooling needs it.
- `PUT /jobs/{id}` still bypasses the Execution Engine's state-machine validation (a pre-existing, disclosed WP-004-era gap, not newly found) — **DEFERRED**, needs an explicit decision (intentional admin override, or should it be restricted).
- ADR-0008's actual ratified text is unverifiable from this repository (§ gap analysis) — **traceability gap**, not a code defect.

## Test Results

The full suite was built from a clean CMake/MSVC configuration (Visual Studio 18 Build Tools, `CMAKE_PREFIX_PATH` pointed at the local PostgreSQL 18 install) and run via `ctest` against a real, reachable local PostgreSQL 18 instance (`OEP_TEST_DB_*` env vars set to the working `oep_acquisition`/`oep123` credentials already present in this environment) — not merely read about in the README, per this task's own "do not report tests pass without execution" instruction.

**Final, confirmed result — identical across two independent, consecutive full-suite runs (different Catch2 random seeds each time, `2806615947` and `1098549392`):**

```
All tests passed (981 assertions in 221 test cases)
```

- **221 / 221 test cases passed**
- **981 / 981 assertions passed**
- **0 skipped** (all DB-backed tests executed for real once real credentials were supplied — the first exploratory run before credentials were set showed most DB tests "Skipped" with `fe_sendauth: no password supplied`, which is expected, correct behavior for missing credentials, not a defect)
- **0 failed**
- Exit code `0` both times.

This is *after* fixing the two test-fixture defects (#5, above) discovered by actually running the suite — the first full run (before those fixes) genuinely failed one test (`DownloadService.start_download completes successfully end to end`) for the demonstrated, reproducible reason documented under Defect #5, and the Vault orphan-cleanup regression test failed twice for two different, sequentially-discovered reasons before its own fixture bug was fully corrected. Re-running the exact same binary twice in a row with the fixes in place, rather than running it once, is what established these results as stable rather than a fluke.

Test categories present, confirmed via direct file listing of `tests/` (25 source files): configuration parsing, database connection failure path, a real `GET /health` end-to-end test; per work package (WP-002 through WP-009), validation / Service-layer (in-memory fakes) / Repository-layer (real Postgres) / REST API (real Postgres + real HTTP server) / migration-schema-shape tests; Connector Framework factory/registry/`StubConnector`/`HttpConnector` tests (all in-memory or local-network-only, no external dependency); this audit's own two new Vault-service regression tests and one new migration regression test.

## Architecture Validation

- Every fix made in this audit (V9 migration, `ReferenceVaultService` cleanup) preserves every existing public contract — no repository interface, REST route, or JSON shape changed.
- No second Vault, provenance system, artifact-identity system, hashing system, or repository abstraction was introduced.
- No Knowledge functionality was moved into EAM; no Engineering Object was created in the Vault.
- No OCR, AI interpretation, semantic search, licensing, cloud storage, distributed replication, or enterprise authentication was implemented.
- The one capability this audit found that **does** exceed ratified scope (`HttpConnector`) was not introduced by this audit and was not silently normalized into the documentation — it is flagged, in an ADR, for an actual decision.

## M2 Readiness Assessment

Milestone-1's own, narrowly-scoped pipeline (WP-001 through WP-009) is **substantively complete and correctly built** — the core evidence-acquisition trust chain (Source → Job → Connector → Download → Verify → Metadata → Vault) is real, tested, immutable where it needs to be, and free of the kind of silent-integrity-gap defects this audit specifically hunted for (the one found, the orphaned-file race, is now fixed). The architecture-vs-SDD gap analysis found the expected, disclosed kind of gap (M2-scope capabilities simply not built yet — search, versioning, licensing, derived artifacts) and one significant, previously-undocumented one (no Acquisition Record entity matching SDD-R015's richer model).

The one finding that changes this from a clean "ready" to a conditional one is `HttpConnector`: Milestone-1 was designed and reviewed on the premise that no real external network communication existed yet, but it does, unreviewed for its own trust-boundary implications, and already wired into the Studio's primary acquisition wizard as the default connector.

## Recommended Next Work Packages

1. **Resolve ADR-0003** (`HttpConnector` scope/security decision) — must precede any M2 connector work, to avoid two independent real-HTTP implementations and to close the SSRF gap either way the decision goes.
2. **Acquisition Record entity** (SDD-R015) — the largest architecture gap; a dedicated work package to design and ratify its actual M2 schema (reconciling R013 vs. R015's differing field taxonomies, per the gap analysis).
3. **Descriptive Vault metadata + search** — natural M2 pairing once the Acquisition Record work above settles what's actually captured at acquisition time.
4. **Periodic fixity/re-hash job** for the Vault — smaller, operational, could precede or run alongside the above.
5. **Raw-artifact retrieval route** for `/vault/{id}` — small, low-risk, useful before external tooling needs direct file access.
6. Decide and document a real answer for `PUT /jobs/{id}`'s bypass of Execution Engine state validation (a leftover WP-004-era item, unrelated to this audit's own findings but worth resolving before M2 adds more execution-adjacent functionality).

## Final Recommendation

**READY WITH CONDITIONS.**

Conditions, in priority order:
1. **ADR-0003 must be resolved** (ratify, gate off, or explicitly accept `HttpConnector` with its SSRF gap closed) before any Milestone-2 work package that touches connectors, downloading, or external network access begins.
2. `README.md`'s connector-related claims must be corrected to match reality regardless of which option ADR-0003 resolves to — the current text is simply false and should not ship to a reader (including a future work package's own author) as authoritative.
3. The Acquisition Record / chain-of-custody gap (SDD-R015) should be scoped as an explicit early-M2 work package, not discovered mid-implementation the way `HttpConnector`'s scope creep was discovered mid-audit.

None of these conditions require re-doing Milestone-1's own work — WP-001 through WP-009's actual deliverables are sound. They require one architectural decision, one documentation correction, and one scoping decision before M2 begins.
