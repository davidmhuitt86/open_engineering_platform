# ARCHITECTURAL_REVIEW.md

Findings only — no code changed as part of this review.

## Layer violations

**None found in the core dependency graph.** `repository` has zero internal dependencies; every module's `#include`s and CMake `target_link_libraries` were read directly and form a clean DAG (`repository → {search, validation, packages, installer, archive} → runtime → oep_engine → api`). No lower-layer module includes a higher-layer one. No module reaches into another module's private (`src/`) headers — all cross-module includes go through public `include/oep/<module>/` paths.

**One documented, deliberate exception**: `cli` links `repository`/`search`/`validation`/`packages` directly in addition to `runtime`/`oep_engine`, rather than exclusively through `runtime` as the `api` module's README states all non-CLI consumers should. This is explicitly called out as a CLI-specific exception in the codebase's own documentation — not a silent violation — but it does mean the CLI has two aggregation points into Foundation rather than one, which is worth revisiting if the CLI's surface keeps growing.

## Circular dependencies

None found. Verified via direct grep of `#include` statements across every module plus every `CMakeLists.txt`'s `target_link_libraries`.

## Duplicate implementations

- **Test fixture duplication**: an in-memory stored-ZIP builder (`build_stored_zip`/`append_u32`) is reimplemented from scratch in 11 separate test `.cpp` files across `tests/api`, `tests/cli`, `tests/engine`, `tests/installer`, `tests/runtime` rather than factored into one shared test-utility header. Low risk (test-only) but a real maintenance cost — any change to the synthetic archive format must be replicated 11 times.
- **`KnowledgeGraphEngine::build_graph()` / `refresh_graph()`** — identical implementations kept as two distinct public method names, apparently only because a work-package spec named both operations separately. Not a functional duplication risk, but unnecessary API surface.
- **Two full-word "install" concepts**: `PackageManager`/`PackageManifest` (in `platform/packages`, a "local package metadata concept") vs. `PackageInstaller`/`OepPackageManifest` (in `platform/installer`, the actual archive-installation manifest) — two differently-named but conceptually adjacent manifest types living in two different modules. This is disclosed in `packages`' own module documentation as intentional, but it is a naming trap for anyone new to the codebase, and worth flagging as a duplicate-sounding concept even though the implementations differ.
- **Sibling top-level `oep_engine` repository** vs. `oep_foundation/platform/oep_engine` — a separate git repository exists at `platform/oep_engine` (sibling to `oep_foundation`) that is NOT the built C++ module; the actual built module lives at `oep_foundation/platform/oep_engine`. Two different things share the exact same name at two different tree depths. This is a significant discoverability/confusion risk, not proven code duplication — but it should be resolved by renaming one of the two.

## Naming inconsistencies

- **C API prefix inconsistency**: subsystem prefixes mix full words (`oep_runtime_`, `oep_validation_`, `oep_reasoning_`) with acronyms (`oep_kge_` for Knowledge Graph Engine, `oep_eqe_` for Query Engine, `oep_eip_` for Intelligence Platform), and the Rules Engine splits into `oep_rule_*` (per-rule ops) vs. `oep_rules_*` (engine-wide ops) rather than one consistent stem.
- **C API ownership-convention inconsistency**: four different, non-interoperable patterns coexist for returning data across the C boundary — (1) per-type `*_list_t` structs with matching `*_release` functions (24+ of these, internally consistent), (2) a single generic `oep_string_release(char*)` for heap strings, (3) fixed caller-supplied output buffers for session IDs specifically, (4) `const char*` into static, never-freed storage for enum-to-string helpers. Each pattern is internally consistent in its own use, but a caller has to know which of four conventions applies to any given function — there is no way to infer it from the function name alone.
- **CLI command near-collisions**: `package` vs `packages` (two independently registered top-level commands differing only by pluralization — the only singular/plural pair in the CLI), and `validate` vs `evalidate` (near-identical names for genuinely different validation paths — the least self-explanatory naming choice in the CLI).
- **Method name reuse with different contracts**: `AnalysisEngine::analyze_root_cause(symptom_id, finding_ids)` vs. `ReasoningEngine::analyze_root_cause(symptom_id)` — same class-method name, different arity, different behavior (the latter runs its own validation pass internally). A caller reading only the method name has no way to know which overload they're calling without checking the class.
- **`EngineeringIntelligencePlatform` introduces a second naming layer** on top of the engines beneath it — `inspect_object`/`inspect_package`/`inspect_context` (stateless) alongside `inspect` (session-scoped workflow method) with different signatures and return types; `engineering_summary`/`engineering_health`/`engineering_dependencies`/`engineering_trace`/`engineering_recommendations` all prefixed with `engineering_` where no other class in the stack uses that prefix. This is a genuine drift point for anyone reading the facade cold.
- **Error-handling convention drift within the Runtime API**: `RuntimeService` uses immutable `{success, error}` Response structs everywhere with no exceptions; `EngineeringContext` uses mutable-default result structs; `RulesEngine`/`ValidationEngine`/`ReasoningEngine` use `std::optional<T>`; `KnowledgeGraphEngine` mixes plain `bool`, `void`, raw unwrapped `std::string`, and `{success, error}` structs all within the same class. No individual class is internally inconsistent in a way that breaks correctness, but there is no single, class-independent convention a new engineer could learn once and apply everywhere.

## Areas of unnecessary complexity

- **Reference-chain growth**: each layer of the Engineering Knowledge Engine takes one more constructor reference than the layer below it, culminating in `EngineeringIntelligencePlatform`'s 7-reference constructor. There is no shared context/DI container — every consumer that wants to build the top of the stack must construct and hold all 7 lower objects itself, in the correct order, for the object's entire lifetime. This works (it is exercised correctly in the end-to-end test) but is a real ergonomic and onboarding cost, and a source of subtle lifetime-ordering bugs if any layer is ever reordered.
- **`ReasoningEngine` breaks the reference-only pattern it otherwise establishes** by owning an `AnalysisEngine` by value internally, while `EngineeringIntelligencePlatform` takes an `AnalysisEngine&` by reference to what is presumably a different, externally-owned instance — meaning two different `AnalysisEngine` instances may exist and be used interchangeably depending on which entry point a caller uses, with no documentation clarifying whether this is intentional.
- **`EngineeringIntelligencePlatform`'s stateless "Service Orchestrator" methods duplicate its own session-scoped "Workflow" methods** in function, under different names, with different return types, for what appear to be the same underlying operations (e.g. `validate` vs. reaching validation through `inspect_context`). This dual entry-point design is not wrong, but it doubles the facade's public surface without a clearly documented reason to prefer one path over the other.

## Future scalability concerns

- **`platform/api/src/oep_api.cpp` at 6,673 lines** is by a wide margin the largest single file in the codebase (nearly the size of the next four largest files combined) and is the sole implementation file backing a 3,277-line, 166-function public header that has grown by purely-additive increments 19 times. Left as one translation unit, this file will keep growing indefinitely; splitting it by subsystem (mirroring the `oep_<subsystem>_*` prefix families) before it becomes materially harder to navigate is a reasonable near-term investment.
- **No caching/invalidation event system anywhere in the stack.** Every cache (`QueryCache`, the Knowledge Graph itself) is explicitly caller-driven — a caller that mutates the repository through one path (e.g. direct `RuntimeService` calls) and queries through another (e.g. a stale `KnowledgeGraphEngine`) will silently get stale results unless it remembers to call the right invalidation method itself. This is honestly documented everywhere it occurs, but it is an architectural limitation that will get harder to reason about as more consumers (Studio, Acquisition, Exchange, future AI systems) begin operating against the same runtime concurrently.
- **`GraphStatistics::compute_statistics()`'s maximum-depth calculation is O(V·(V+E))** (BFS from every node) — explicitly documented as a known, accepted exception to the engine's otherwise-deterministic O(V+E)/O(V log V) profile. Fine at today's object counts; worth a benchmark before any repository of meaningfully large scale relies on this path.
- **Studio's FFI mutation gap** (no update/delete/batch-create bindings for objects/relationships) is not itself a scalability problem, but if it remains unaddressed while more Studio features are layered on top of the read-only surface that does exist, it becomes an architecture debt that compounds — future Studio features will be built assuming read-only object interaction, making a later retrofit of full CRUD harder.

## Technical debt

See `TECHNICAL_DEBT.md` for the full ranked list. Headline items: the GraphML export is a shipped public C API function (`oep_kge_export_graphml_placeholder`) that is explicitly self-documented as incomplete ("node/edge identity only, no attribute schema") across 7 files spanning header/impl/CLI/C-API layers — this is a genuine, non-trivial gap in a *frozen* v1.0 public surface, not a test stub. Studio's placeholder surface is considerably larger than the backend's: two entire feature pages (Graph, Packages) and most of the Knowledge Studio dialog set render placeholder widgets rather than real functionality.

## Suggested refactoring (reporting only — not applied)

1. Rename the top-level sibling `platform/oep_engine` repository to remove the name collision with `oep_foundation/platform/oep_engine`.
2. Extract the 11-times-duplicated ZIP-builder test helper into one shared test-utility header.
3. Split `oep_api.cpp` into per-subsystem translation units before its next growth cycle.
4. Pick one C-API ownership convention (or explicitly document the decision tree for which of the four applies when) rather than leaving four competing patterns to be learned function-by-function.
5. Reconcile `package`/`packages` and `validate`/`evalidate` CLI naming — rename or alias one of each pair.
6. Either implement full GraphML export or explicitly demote it from the frozen v1.0 API surface / relabel it clearly as v2-scope in the public specification, rather than shipping a "placeholder" as a stable, versioned public function.
7. Close the Studio FFI mutation gap (object/relationship update/delete, batch-create) before building further Studio features on top of the current read-only assumption.
