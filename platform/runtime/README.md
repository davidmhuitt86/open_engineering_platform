# Runtime

Status: Foundation (Foundation Runtime + Runtime Service & Repository Events + Package Uninstall & Update + Merge Engine)

Purpose: The single entry point through which applications interact with Foundation, per OEP-SPEC-011-FOUNDATION_RUNTIME. Coordinates lifecycle and service access for Repository, Search, Graph, Validation, Package Manager, and Archive without reimplementing any of them.

## Architecture

- `include/oep/runtime/foundation_runtime.hpp` — public `FoundationRuntime` (`initialize` / `open_repository` / `close_repository` / `shutdown`, Repository Context accessors, Service Registry accessors, `export_repository` / `import_repository`, `create_template` / `list_templates` / `instantiate_template`, `execute_batch_create` / `execute_batch_delete` / `validate_batch_create`, — per Work Package 014 — `create_object` / `update_object` / `delete_object`, `create_relationship` / `update_relationship` / `delete_relationship`, `begin_transaction` / `commit_transaction` / `rollback_transaction` / `transaction_active`, `batch_create_objects` / `batch_create_relationships`, and — per WP-REP-001 (Repository Runtime) — `install_package` / `list_installed_packages` / `package_registry`) and `RuntimeState`
- `src/foundation_runtime.cpp` — deterministic state transitions and subsystem construction/registration

`open_repository` establishes where an opened repository's Engineering Objects, Relationships, and Audit Events live on disk: `repository/objects/`, `repository/relationships/`, and `repository/audit/` beneath the repository root, with packages discovered under the repository's existing top-level `packages/` directory. This convention is not yet wired into `oep init`/the Foundation Generator.

Only one repository may be open at a time. Every service accessor (`object_store`, `relationship_store`, `audit_store`, `search_engine`, `graph_engine`, `validator`, `package_manager`) returns `nullptr` unless a repository is currently open — before initialization, before opening, after closing, and after shutdown all behave identically in this respect. `export_repository` and `create_template` require an open repository (they capture *the* open one); `import_repository`, `list_templates`, and `instantiate_template` do not — they target a destination/template-store directory to create or read, not one to open — but all five remain exposed on `FoundationRuntime` and delegate entirely to `oep::archive` (renamed from `oep::exchange` in WP-REP-002 — see `platform/archive/README.md`), so every repository-touching operation executes through the Runtime. `execute_batch_create`, `execute_batch_delete`, and `validate_batch_create` all require an open repository and delegate entirely to `oep::repository::BatchProcessor`.

`platform/api`'s Public C API (Work Package 012: Engineering Object Enumeration, Repository Statistics; Work Package 013: Engineering Relationship Enumeration, Repository Search) added no new surface to `FoundationRuntime` itself — every function those work packages exposed was built entirely from the existing `object_store()`/`relationship_store()`/`search_engine()`/`current_metadata()`/`current_package_set()` accessors already described above, translated into fixed-layout C structures at the API boundary. Work Package 013's search functions, in particular, read the same `SearchEngine` instance `search_engine()` already returns — the one built by `build_index` during `open_repository` — rather than constructing or indexing anything new.

**Work Package 014** is the first to extend `FoundationRuntime`'s own interface for the Public C API's benefit: `create_object`/`update_object`/`delete_object` and `create_relationship`/`update_relationship`/`delete_relationship` were added because `object_store()`/`relationship_store()` are read-only-oriented accessors (they return `const ObjectStore*`/`const RelationshipStore*`) and Work Package 014's architectural guidance requires "every Public C API mutation function shall delegate through Foundation Runtime" — the Public API must never reach a store directly, so Runtime needed its own mutation entry points to delegate through. Each new method is a thin orchestration layer over the corresponding `ObjectStore`/`RelationshipStore` method; no validation logic is duplicated.

Also new in Work Package 014: `begin_transaction`/`commit_transaction`/`rollback_transaction`/`transaction_active`, and `batch_create_objects`/`batch_create_relationships` built on top of them. A transaction is implemented as an in-memory, per-`FoundationRuntime`-instance undo log (`TransactionLogEntry`, private) — `ObjectStore`/`RelationshipStore` gained no new persistence concept; every mutation still writes to disk immediately, transaction or not. `rollback_transaction` replays the log in reverse using the stores' own `remove`/`update`/`restore` methods (the same `restore` path Import and Templates already use to reconstruct exact prior state). `reset_repository_context()` (called by both `close_repository()` and `shutdown()`) now rolls back an active transaction first, so a repository is never left with a transaction stranded open when it closes.

## Package Installation (WP-REP-001, Repository Runtime)

`install_package(const std::filesystem::path& archive_path)` is the first vertical slice of the Foundation Repository Runtime: it opens a `.oep` archive via `oep::installer::extract_package` (built on `oep::installer::ZipReader`, which supports only the ZIP "Stored"/uncompressed entry method — DEFLATE is rejected), then, for every Repository Fragment object and relationship the archive contains, calls the existing `ObjectStore::create`/`RelationshipStore::create` unchanged — archive-declared IDs are preserved rather than remapped, since both stores already keep a caller-supplied ID when one is present. On completion it rebuilds the Search and Graph indexes (`search_->build_index`/`graph_->build_graph`, the same calls `open_repository` itself makes) and records one entry via the new `oep::installer::PackageRegistry` (`package_registry()` accessor; persisted at `<repository>/packages/<packageId>/registry.json`, which the pre-existing `oep::packages::PackageManager` never matches — it only discovers files literally named `package.json`, so the two "package" concepts coexist without collision, per OEP-ARCH-002 §4.1).

**`install_package` is atomic since WP-REP-003 (Repository Transaction Engine)** — superseding WP-REP-001/002's deliberately-non-transactional behavior: the whole install runs inside one Repository Transaction; any failure rolls back every create performed so far (covered by `test_a_failure_partway_through_is_rolled_back` in `tests/runtime/package_installation_tests.cpp`, the inversion of the earlier no-rollback test) and the transaction is journaled either way. See "Repository Transaction Engine" below.

`list_installed_packages()` returns every Repository Registry record for the currently open repository, delegating entirely to `RepositoryRegistry::list_installed()`.

Both methods require an open repository, following the same precondition every other repository-touching `FoundationRuntime` method already enforces; `registry_` (the `RepositoryRegistry` instance) is constructed in `open_repository()` alongside the other per-repository services and reset in `reset_repository_context()`, matching the lifecycle of `object_store_`/`relationship_store_`/etc. exactly.

## Package Lifecycle Queries (WP-REP-002)

WP-REP-002 renamed WP-REP-001's minimal Package Registry to the **Repository Registry** (`oep::installer::RepositoryRegistry`, accessor `repository_registry()`), expanded its per-package record to the full WP-REP-002 §4 field set (manifest metadata, publisher, installation date/source/path, SHA-256 package hash, runtime state, contribution IDs), and added four read-only lifecycle query services — none of which mutate anything, since update/uninstall/activation remain explicitly out of scope:

- `get_installed_package(package_id)` — the full Repository Registry entry; "not installed" is a normal result, not an error.
- `find_package_owner(entity_id)` — which installed package contributed a given Engineering Object or Relationship.
- `verify_package(package_id)` — confirms every recorded contribution still exists in the open repository's own stores, and (when the source archive still exists at its recorded path) that its bytes still hash to the recorded SHA-256. A deleted archive is a reported condition, not a failure — the archive is transport, not the installed content.
- `search_installed_packages(query)` — case-insensitive substring match over registry metadata plus the *live* names of each package's installed Engineering Objects (cross-referenced against `ObjectStore` at query time — object names are never duplicated into the registry, per CLAUDE.md's "Never duplicate Engineering Object data").

`install_package` now also records the archive's absolute path and SHA-256 hash and sets `runtime_state = "Installed"` at install time. The hash is an integrity fingerprint only, not a trust mechanism — signature verification is PKG-005 / a future work package.

## Repository Transaction Engine (WP-REP-003)

WP-REP-003 upgraded Work Package 014's transaction primitives (`begin_transaction`/`commit_transaction`/`rollback_transaction`/`transaction_active` — every signature unchanged) into the Repository Transaction Engine, implementing the install-scope subset of PKG-003:

- **Identity and journaling** — every transaction has a UUIDv4 id and, on close, writes one permanent record (`TransactionRecord`: state, description, open/close timestamps, and one `JournalEntry` per operation with its target and previous/new state) to the Transaction Journal (`transaction_journal.hpp/.cpp`, persisted under `<repository>/logs/transactions/` — inside the `logs/` directory OEP-SPEC-002 §5 already reserves). The journal records what happened; Work Package 014's in-memory compensating-action undo log — reused unchanged — is what performs a rollback.
- **Every write executes through a transaction** — a mutation called outside an explicit transaction runs inside an *implicit* one, begun and committed automatically around the single operation, so it is journaled like any other write. `install_package` is atomic: one transaction per install, rolled back completely on any failure (including a failed Repository Registry write), journaled Committed or RolledBack. An install inside a caller's explicit transaction is rejected (no nesting, per Work Package 014).
- **States** — `Opened`/`Committed`/`RolledBack`/`Failed` (a rollback whose undo could not fully complete), a deliberate subset of PKG-003 §5; the full lifecycle (Planning/WaitingForApproval/Indexing/Activating/...) belongs to capabilities this Work Package excludes (dependency resolution, previews, activation).
- **One documented behavior change** — `commit_transaction` can now fail in exactly one new way: the journal record could not be written. The mutations are already persisted in that case; the error exists so the caller knows the audit trail is incomplete, never to signal data loss. A journal problem never prevents a rollback from restoring repository state — restoring data always outranks recording history.
- **Queries** — `current_transaction_info()` (active transaction's id/description/entry count), `transaction_history()` (every journaled record, sorted), `get_transaction_record(id)`.
- **Documented boundaries** — `execute_batch_create`/`execute_batch_delete` (OEP-SPEC-020's `BatchProcessor`) retain their own validate-everything-then-execute atomicity and do not flow through this engine; `import_repository`/`instantiate_template` construct *new* repositories rather than writing to the open one, so there is no open-repository state for a transaction to protect. Crash-recovery/repair from the journal is PKG-003 §21 territory, deferred alongside update/uninstall.

The CLI's `oep object create|delete` and `oep relationship create|delete` were migrated in this Work Package from direct `ObjectStore`/`RelationshipStore` access to the Runtime's own mutation methods, so CLI writes are journaled exactly like Public-C-API writes.

## Trust & Signing (WP-REP-004)

`FoundationRuntime` gained a `TrustStore` accessor (`trust_store()`) and six pass-through methods — `trust_add_certificate`/`trust_get_certificate`/`trust_list_certificates`/`trust_revoke_certificate`/`trust_get_policy`/`trust_set_policy` — over `oep::installer::TrustStore` (WP-REP-004, PKG-005). These are local, offline, user-directed writes to `<repository>/settings/trust/`, not Repository writes, so they never open a Repository Transaction.

**`install_package` now verifies trust BEFORE any Repository Transaction begins** (this Work Package's explicit, load-bearing requirement): immediately after confirming the package isn't already installed, and strictly before `open_transaction_internal` is ever called, `oep::installer::verify_package_trust` runs against the repository's `TrustStore`. A `Tampered`, `InvalidSignature`, `UnknownPublisher`, `ExpiredCertificate`, or `RevokedCertificate` result rejects the install immediately — no archive content is extracted, no transaction is opened, nothing is journaled. Proven by a dedicated test (`test_signed_but_untrusted_publisher_is_rejected` in `tests/runtime/trust_integration_tests.cpp`) that asserts `transaction_history()` is empty after a trust-rejected install. An `Unsigned` archive proceeds exactly as in WP-REP-001–003, unless the Trust Store's policy requires signatures.

On a successful install, the resolved `TrustState` and (when a certificate matched) its fingerprint are recorded on the `RepositoryRegistryEntry` (`trust_status`/`trust_fingerprint`) and returned via `RuntimeInstallResult::trust_status` — queryable afterward without re-verifying (PKG-005 §16's "revalidate at any time" is deferred; `oep package verify`'s existing WP-REP-002 hash/contribution checks are unrelated to trust and untouched).

## Dependency Resolution (WP-REP-005)

`install_package`'s pipeline gains a new gate: **extract -> already-installed check -> trust-verify -> dependency-resolve -> open-transaction -> create objects/relationships -> record registry -> commit.** Dependency resolution runs strictly after trust verification and strictly before `open_transaction_internal` is ever called, so — exactly like a trust rejection — a dependency-resolution failure opens no transaction and writes no journal record; nothing is extracted into the repository.

`oep::installer::resolve_dependencies` is called against the candidate package's parsed manifest `dependencies` and every already-installed package's own `dependencies` (now carried on `RepositoryRegistryEntry`, so the full installed-dependency graph is visible without re-opening any archive). The resulting `DependencyResolutionReport` classifies each declared dependency (`Satisfied`/`Missing`/`Optional`/`Conflicting`/`Cyclic`/`Unknown`) and produces a deterministic topological `install_order`. `install_package` rejects the install when the report contains any required `Missing` dependency, any `Conflicting` version, an `Unknown` (malformed) constraint, or a `Cyclic` chain; an `Optional` missing dependency never blocks the install.

`resolve_package_dependencies(archive_path)` is a new, dry-run, side-effect-free `FoundationRuntime` method: it opens the archive, parses its manifest, and runs the same resolution pass against the currently open repository's registry, returning a `RuntimeDependencyResolutionResult` without installing anything or requiring the caller to attempt (and possibly roll back) a real install just to find out whether it would succeed. It requires an open repository, following the same precondition every other repository-touching method already enforces, and performs no writes of any kind — no transaction, no registry mutation, no archive extraction into the repository.

This module does not download, fetch, or otherwise resolve a missing dependency from anywhere — resolution operates solely on local repository metadata (the candidate's own manifest plus the Repository Registry's existing entries). A missing dependency is reported, never fetched.

## Runtime Service & Repository Events (WP-REP-006)

`platform/runtime/include/oep/runtime/runtime_service.hpp` (+ `src/runtime_service.cpp`) introduces `RuntimeService`, a new orchestration layer that sits **in front of** `FoundationRuntime`, not inside it: `FoundationRuntime` itself is unchanged by this Work Package — zero lines touched — every business rule (validation, transaction journaling, trust verification, dependency resolution) stays exactly where it already lived. `RuntimeService` owns **sequencing only**: each of its methods (`install_package`, `resolve_dependencies`, `create_object`/`update_object`/`delete_object`, `create_relationship`/`update_relationship`/`delete_relationship`, `begin_transaction`/`commit_transaction`/`rollback_transaction`) makes exactly one direct call into the identically-named `FoundationRuntime` method, then — on success only — publishes exactly one `RepositoryEvent`. It reinterprets no error, retries nothing, and adds no validation of its own; a permanent regression test (`test_runtime_service_preserves_foundation_runtime_error_text` in `tests/runtime/runtime_service_tests.cpp`) pins `FoundationRuntime`'s error text passing through byte-for-byte unmodified, guarding against `RuntimeService` ever growing business logic of its own.

`RuntimeContext` (`include/oep/runtime/runtime_context.hpp`) is a small, pure reference-holding dependency-injection container — `RuntimeContext(FoundationRuntime&, EventBus&)`, no logic of its own — passed into `RuntimeService`'s constructor so `RuntimeService` never constructs its own `FoundationRuntime` or `EventBus` instance.

Every `RuntimeService` Request/Response type is **immutable**: public `const` fields set once by a single constructor, no setters. This is deliberate — a `RuntimeService` request is meant to be built once, passed down, and never mutated in place while sequencing is in flight.

## Repository Events (WP-REP-006, Infrastructure Only)

`include/oep/runtime/repository_events.hpp` (+ `src/repository_events.cpp`) adds an `EventType` enum (`ObjectCreated`/`ObjectUpdated`/`ObjectDeleted`, `RelationshipCreated`/`RelationshipUpdated`/`RelationshipDeleted`, `TransactionBegun`/`TransactionCommitted`/`TransactionRolledBack`, `PackageInstalled`/`PackageInstallFailed`, `DependencyResolutionCompleted`), an immutable `RepositoryEvent` (type/subject id/detail/UTC occurrence time/sequence number, all read through `const` getters, no setters), and `EventBus` — an in-memory, bounded (default 1000 events, oldest discarded first), single-process event log: `publish(type, subject_id, detail)`, `recent_events(limit = 0)`, `published_count()`.

**This Work Package deliberately adds infrastructure only — there is no subscribe/callback mechanism.** `EventBus` has no `subscribe`, no observer registration, nothing a caller can attach a handler to; it is a queryable log, not a notification system. Nothing in Foundation reacts to a published event yet. Wiring actual subscribers (e.g. cache invalidation, external notification, telemetry) is explicitly deferred to a future work package.

`RuntimeService` is the only component that publishes events in this Work Package, and it publishes exactly one event per successful mutating call — nothing is published on failure.

## Package Uninstall & Update (WP-REP-007)

Two new package lifecycle operations, each following the same **impact-report-then-atomic-transaction** pattern `install_package` already established: a dry-run analysis method that performs no writes, and a second, separate method that performs the real mutation inside one Repository Transaction — never the other way around, and never merged into a single "just do it and tell me what happened" call.

**Uninstall.** `FoundationRuntime::analyze_uninstall_impact(package_id)` looks the package up in the Repository Registry and reports whether it was `found`, how many objects/relationships it contributed (`objects_affected`/`relationships_affected`), any other installed package that declares a REQUIRED dependency on it (`blocking_dependents`), and whether it is therefore `removable`. It writes nothing and opens no transaction. `FoundationRuntime::uninstall_package(package_id)` re-runs that same blocking check and, if clear, removes every Object and Relationship the package contributed plus its Repository Registry record — all inside **one** Repository Transaction, reusing the exact same Transaction Engine WP-REP-003 built (the same journal, the same UUIDv4 transaction identity, the same rollback-on-failure guarantee). If a blocking dependent exists, `uninstall_package` refuses outright: no transaction is opened, nothing is journaled, exactly mirroring how a trust or dependency rejection short-circuits `install_package` before `open_transaction_internal` is ever called.

**Update.** `FoundationRuntime::analyze_update_impact(archive_path)` verifies trust and resolves dependencies for the **candidate** version — reusing Trust (WP-REP-004's `verify_package_trust`) and the Dependency Resolution Engine (WP-REP-005's `resolve_dependencies`) exactly as `install_package` already does for a fresh install — and additionally checks whether any *other* installed package's required dependency constraint on this package would become unsatisfied by the candidate version, reported as `broken_dependents`. The report's `updatable` flag reflects all of these checks combined. It performs no writes. `FoundationRuntime::update_package(archive_path)` re-verifies and, if updatable, removes the old version's contributions and installs the new version's — **all inside one Repository Transaction** — so a failure at any point leaves neither version installed twice nor neither installed at all; the previous version is always restored on any failure, the same all-or-nothing guarantee the Transaction Engine already gives `install_package`.

**Architectural point worth stating plainly:** neither operation introduces a second transactional mechanism, a second trust pipeline, or a second dependency resolver. Uninstall's atomicity and Update's atomicity are the *same* Transaction Engine WP-REP-003 built for `install_package`, reused unchanged; Update's trust/dependency checks are the *same* Trust Store and Dependency Resolution Engine WP-REP-004/WP-REP-005 built, reused unchanged. This is the direct, concrete satisfaction of the user's requirements to reuse the existing Transaction Engine and the existing Dependency Resolution Engine rather than reimplementing either.

`RepositoryRegistry::remove_record(package_id)` (`platform/installer`) is a small new helper backing uninstall: it deletes a package's `registry.json`, the inverse of the write `install_package` already performs.

**RuntimeService-exclusive by design.** `RuntimeService` gains `analyze_uninstall_impact`/`uninstall_package`/`analyze_update_impact`/`update_package`, each with immutable Request/Response/Report types (`UninstallImpactReport`/`UpdateImpactReport`: public `const` fields, constructor-only, no setters, satisfying "produce immutable Impact Reports"). Unlike `install_package`, which remains dual-exposed on both `FoundationRuntime` and `RuntimeService` for backward compatibility, uninstall and update are **RuntimeService-only** at the API/CLI boundary — the Public C API's four new functions and the CLI's four new subcommands all route exclusively through `runtime->service`, never `FoundationRuntime` directly. This is a deliberate, concrete satisfaction of the requirement that all lifecycle operations execute exclusively through `RuntimeService`, applied more strictly here than WP-REP-006 applied it to `install_package`. Two new `EventType`/`oep_event_type_t` values, `PackageUninstalled`/`PackageUpdated`, are published on success exactly like every other `RuntimeService` mutation.

**Explicitly out of scope through WP-REP-007**, superseded in part below: merge engine — **implemented in WP-REP-008, see "Merge Engine" below.** Ownership policies, enterprise permissions, distributed repositories, repository federation, synchronization, and telemetry remain out of scope.

## Merge Engine (WP-REP-008)

`install_package` handles one package's Repository Fragment installed in isolation — merge generalizes that into an explicit **plan-then-apply** pipeline that tolerates content another package (or a prior install) already contributed, per the first satisfaction of PKG-006's cross-package merge/ownership logic.

**`oep::installer::RepositoryChangeSet`** (`platform/installer/include/oep/installer/repository_change_set.hpp`) is the new canonical, **immutable** representation of a set of Repository mutations: a `ChangeKind` enum (`Create`/`Update`/`Delete` — this work package's planner only ever produces `Create` entries; `Update`/`Delete` exist in the vocabulary now so a future planner never needs a breaking schema change), immutable `ObjectChange`/`RelationshipChange` value types (const-getter only, no setters) each carrying `source_repository_id`/`source_object_id` provenance fields, and `RepositoryChangeSet` itself, which holds the change vectors plus a `source_repository_id` and `description`. Every mutation this work package's merge path performs is described by one of these change sets before it is ever applied.

**`oep::installer::plan_merge()`** (`platform/installer/include/oep/installer/merge_engine.hpp`) is a **pure, side-effect-free function**: it diffs a source's objects/relationships against a target's and returns a `MergePlan` — the `RepositoryChangeSet` of genuinely new content, plus a **deterministically-ordered** list of `MergeConflict`s (`ObjectContentConflict`/`RelationshipContentConflict`/`RelationshipMissingEndpoint`) for anything that exists with *different* content. Conflicts are always reported in source-declaration order, never target-iteration or hash order, so replanning the same input twice produces identical conflict ordering — the direct implementation of deterministic conflict detection. Content that already exists identically is a benign no-op, not a conflict: unlike `install_package`'s hard "already installed" rejection, a merge is idempotent and safe to retry.

**`FoundationRuntime::plan_merge(archive_path)`** is read-only and side-effect-free: it sequences Trust verification then Dependency Resolution — reusing WP-REP-004/WP-REP-005 exactly as `install_package`/`update_package` already do — against the currently installed set, then calls `plan_merge`, always computing the diff regardless of the trust/dependency verdict, so a caller can inspect what a blocked plan *would* have done. A `package_id` already present in the Repository Registry also blocks mergeability (`already_registered`) — merge is not update.

**`FoundationRuntime::execute_merge(archive_path)`** re-derives the same plan, refuses to open any transaction unless `mergeable` is true, then applies the change set inside **one** Repository Transaction — reusing the exact same Transaction Engine WP-REP-003 built, not a second mechanism — recording only the objects/relationships this merge actually created as the new package's own registry ownership. Pre-existing identical content is not re-claimed, preserving accurate provenance.

**Architectural point worth stating plainly:** the Merge Engine introduces no second transactional mechanism, no second trust pipeline, and no second dependency resolver. Its atomicity is the same Transaction Engine `install_package`/`uninstall_package`/`update_package` already use; its trust/dependency checks are the same Trust Store and Dependency Resolution Engine WP-REP-004/WP-REP-005 built. This is the concrete satisfaction of the user's requirement to preserve Trust-before-Dependency-before-Merge sequencing and reuse existing subsystems rather than reimplementing any of them.

**RuntimeService-exclusive, like uninstall/update.** `RuntimeService::plan_merge`/`execute_merge` are the only entry points the C API and CLI call — never `FoundationRuntime::plan_merge`/`execute_merge` directly. `execute_merge` publishes a new `RepositoryMerged` event on success; `plan_merge` publishes nothing, since it is side-effect-free.

**Explicitly out of scope**, unchanged from prior work packages: repository federation, distributed synchronization, networking, enterprise permissions, licensing, cloud services.

## Engineering Knowledge Runtime Read Support (WP-EKE-001)

WP-EKE-001 is the first work package outside the WP-REP series — it begins a new architectural layer, `platform/oep_engine` (the Engineering Knowledge Runtime, EKR), that sits above Foundation rather than extending it, per the Architectural Position `Foundation Repository -> Engineering Knowledge Runtime -> Knowledge Graph -> Reasoning -> Engineering Intelligence`. The EKR is responsible for engineering *semantics* (graph queries, traversal, relationship classification); Foundation continues to own persistence, transactions, trust, and package installation, entirely unchanged by this work package.

`RuntimeService` (this module) gained exactly three new, read-only methods so the Engine — and any future RuntimeService-exclusive consumer — never needs `FoundationRuntime`'s storage accessors directly:

- `get_object(GetObjectRequest{object_id})` — a single Engineering Object lookup by id.
- `list_objects()` — every Engineering Object currently in the open repository.
- `list_relationships()` — every Relationship currently in the open repository.

Each simply calls through to `FoundationRuntime`'s own already-public `object_store()`/`relationship_store()` accessors — no storage logic is duplicated, no new persistence capability is introduced, and each is a purely read-only sequencing wrapper following exactly the pattern every other `RuntimeService` method already established (WP-REP-006): immutable Request/Response types, one direct call into the underlying accessor, nothing more. Unlike every prior `RuntimeService` mutation method, these three publish no `RepositoryEvent` — they are pure reads, and `EventBus` publication remains reserved for successful mutations only.

`FoundationRuntime` itself gained no new surface for this work package — `object_store()`/`relationship_store()` already existed and were already public; WP-EKE-001 only needed `RuntimeService` to expose a RuntimeService-native path to them so `platform/oep_engine`'s `ObjectLoader`/`EngineeringContext` could remain RuntimeService-exclusive, matching WP-REP-007/WP-REP-008's established RuntimeService-exclusivity pattern for newer capabilities. See `platform/oep_engine/README.md` for the full Engineering Knowledge Runtime this read support was built for.

## Knowledge Graph Engine Read Support (WP-EKE-002)

`RuntimeService` gained one more new, read-only method for the same reason WP-EKE-001 added its three: `find_package_owner(request)` — which installed package (if any) contributed a given Engineering Object or Relationship ID. It is a thin sequencing wrapper over `FoundationRuntime::find_package_owner` (the WP-REP-002 Package Lifecycle Query already documented above under "Package Lifecycle Queries (WP-REP-002)") — no ownership-resolution logic is duplicated, and `FoundationRuntime` itself gained no new surface for this work package either.

This method exists specifically for `platform/oep_engine`'s new `KnowledgeGraphEngine::build_graph()`/`refresh_graph()` (WP-EKE-002): resolving each Engineering Object's/Relationship's package/publisher ownership when constructing the canonical Knowledge Graph requires exactly this lookup, and per the EKR's RuntimeService-exclusivity rule, the Engine may not call `FoundationRuntime::find_package_owner` directly. The documented call chain is `KnowledgeGraphEngine -> EngineeringContext::find_owner() -> RuntimeService::find_package_owner -> FoundationRuntime::find_package_owner`, with no layer skipped. Like `get_object`/`list_objects`/`list_relationships`, this method publishes no `RepositoryEvent` — it is a pure read. See `platform/oep_engine/README.md`'s "Engineering Knowledge Graph Engine (WP-EKE-002)" section for the full Knowledge Graph Engine this read support was built for.
