# Engineering Reference Package Format (ERPF)

**Document ID:** SDD-R004  
**Repository:** oep_reference  
**Status:** Draft 1.0  
**Classification:** Architecture  
**Owner:** Divad Technology Group, LLC.

---

# 1. Purpose

This specification defines the Engineering Reference Package Format (ERPF).

Engineering Reference Packages are the distribution mechanism for Engineering Knowledge Objects.

Every Engineering Reference Library, whether distributed by Divad Technology Group, a manufacturer, an educational institution, or a Marketplace publisher, shall use this package format.

The package format is designed for:

- Offline operation
- Digital signing
- Versioning
- Marketplace distribution
- Incremental updates
- Long-term archival
- Cross-platform compatibility

---

# 2. Philosophy

Engineering knowledge shall not exist as loose files.

Engineering knowledge shall be distributed as immutable packages.

Packages become installable engineering libraries.

The runtime consumes packages.

Developers author source files.

---

# 3. Package Types

Initial package types include:

```
Core Library

Manufacturer Library

Industry Library

Educational Library

Simulation Library

Standards Library

Marketplace Library

Private Library
```

Future package types are additive.

---

# 4. Package Identity

Every package shall contain:

```
Package ID

Display Name

Publisher

Version

Release Date

Package Type

Language

License

Compatibility
```

---

# 5. Package Structure

Every package shall contain:

```
Manifest

Engineering Knowledge Objects

Relationships

Indexes

Assets

Localization

Metadata

Digital Signature
```

---

# 6. Runtime Format

The runtime package shall use the `.oerp` extension.

Example

```
core_reference.oerp

automotive_reference.oerp

iec_symbols.oerp

ti_power_management.oerp
```

---

# 7. Physical Format

An `.oerp` package shall be a deterministic ZIP archive.

Contents:

```
manifest.json

reference.db

search.idx

graph.idx

assets/

localization/

signature/

license/
```

The archive shall be byte-for-byte reproducible.

---

# 8. Manifest

The manifest defines package metadata.

Example fields:

```
Package Name

Package ID

Version

Publisher

Dependencies

Minimum OEP Version

Target Domains

Object Count

Relationship Count

Asset Count

Build Date
```

---

# 9. Reference Database

The package contains a compiled runtime database.

The database is generated by the Reference Compiler.

The runtime never consumes editable source files.

The schema remains internal to the compiler/runtime.

---

# 10. Search Index

Each package contains a precompiled search index.

The runtime shall never build indexes during installation.

Indexes include:

```
Names

Aliases

Keywords

Technologies

Standards

Properties

Relationships
```

---

# 11. Graph Index

The package contains a precompiled graph index.

Purpose:

- Fast traversal
- Relationship lookup
- AI retrieval
- Simulation dependency analysis

---

# 12. Assets

Assets may include:

```
SVG Symbols

Icons

3D Models

Images

Example Diagrams

Documentation

Animations
```

Assets are optional.

---

# 13. Localization

Packages may contain multiple languages.

Example

```
English

French

German

Spanish

Japanese
```

Engineering identifiers remain language independent.

---

# 14. Dependencies

Packages may depend upon other packages.

Example

```
Automotive Library

↓

depends upon

↓

Core Library
```

Circular dependencies are prohibited.

---

# 15. Digital Signatures

Every official package shall be digitally signed.

Signing shall use the same platform signing infrastructure adopted by OEP package specifications.

Unsigned packages may be installed only when explicitly permitted by user policy.

---

# 16. Versioning

Semantic Versioning shall be used.

```
Major

Minor

Patch
```

Object compatibility shall be maintained whenever possible.

---

# 17. Incremental Updates

Packages may distribute update packages.

Example

```
Core Library

↓

Update

↓

Version 1.2.3
```

Only modified objects shall require redistribution.

---

# 18. Installation

Installation shall:

- Verify signature
- Verify compatibility
- Verify dependencies
- Register package
- Register indexes
- Make objects available immediately

Installation shall never modify existing packages.

---

# 19. Removal

Package removal unregisters:

- Objects
- Relationships
- Search indexes
- Assets

Removal shall not affect unrelated packages.

---

# 20. Marketplace

Marketplace distributes `.oerp` packages.

The Marketplace never distributes loose engineering objects.

Packages remain the unit of licensing, installation, and updates.

---

# 21. Private Packages

Users may create private packages.

Private packages support:

- Internal company knowledge
- Proprietary standards
- Internal components
- Customer libraries

Private packages follow the same format.

---

# 22. Compiler

Authoring files are compiled into `.oerp`.

Compiler responsibilities include:

- Validation
- Relationship verification
- Duplicate detection
- Index generation
- Graph generation
- Package signing
- Manifest generation

---

# 23. Runtime

The runtime shall:

- Load packages
- Resolve dependencies
- Merge indexes
- Merge graphs
- Expose APIs
- Support hot-loading where practical

The runtime shall never modify installed packages.

---

# 24. Architectural Rules

The following rules are permanent.

1. Packages are immutable.
2. Runtime consumes compiled packages only.
3. Source files are never runtime dependencies.
4. Packages are digitally signed.
5. Packages are versioned.
6. Packages are installable.
7. Packages are removable.
8. Packages are Marketplace-ready.
9. Packages remain offline capable.
10. Engineering Knowledge Objects are the only engineering content stored inside packages.
