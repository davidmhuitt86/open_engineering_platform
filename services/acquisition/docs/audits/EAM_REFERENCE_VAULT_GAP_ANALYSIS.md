# EAM / Reference Vault — Architecture Gap Analysis (WP-017)

Compares the actual Milestone-1 implementation (`services/acquisition`) against the ratified SDDs (`SDD-R013` through `SDD-R019`) and the Work Package specifications (WP-001–009) that authorize the current build. Source: direct reading of all 7 SDDs, both ADRs, and all 9 WPs (see the companion implementation audit for code-level verification).

## Important preliminary finding: ADR-0008 could not be verified from this repository

`README.md` and several source-code comments state that `IConnector::fetch` implements "ADR-0008 (Connector Content Retrieval Interface)," ratified in a repository named `oep_architecture`, superseding this repo's own `docs/decisions/ADR-0002-PROPOSED-CONNECTOR-CONTENT-RETRIEVAL.md`. **A repository or directory named `oep_architecture`, and any file named `ADR-0008*`, do not exist anywhere in this monorepo** (confirmed by an exhaustive recursive search). ADR-0002 itself only names ADR-0007 as a precedent and states its own status as "pending ratification in `oep_architecture`" — it never mentions "ADR-0008" at all.

This is not evidence the decision was fabricated — the implemented `fetch` signature matches ADR-0002's own proposed design closely (with only casing/type deviations the README itself discloses as "left to this repository's own conventions"), which is exactly what you'd expect if a sibling repository really did ratify it. But it means **this specific claim is unverifiable from within this codebase**, and any future audit or work package that needs the actual ratified text of ADR-0008 will need access to that separate repository. Documented here rather than either accepted uncritically or flagged as fraudulent — neither extreme is supported by the evidence available.

## Entity-model discrepancies found across the SDD set (not introduced by, and not fixed by, this audit)

These are pre-existing inconsistencies **between ratified architecture documents themselves**, independent of the M1 implementation. Per this task's own instruction, they are documented, not silently resolved:

1. **"Engineering Artifact" as a distinct entity (R015) vs. absent (R016).** SDD-R015 §7 describes a three-tier chain `Acquisition Record → Engineering Artifact → Vault Object`; SDD-R016 never defines "Engineering Artifact" as a first-class entity at all — it treats the Vault Object as the artifact itself. The M1 implementation follows R016's simpler two-tier model (no `Engineering Artifact` table/concept anywhere) — a reasonable, but unreconciled, choice.
2. **Registry-ownership ambiguity (R013 vs. R014).** SDD-R013 §15 assigns "maintain a registry of trusted providers" to the EAM itself; SDD-R014 presents the Official Source Registry as its own subsystem that EAM only consumes. The M1 implementation resolves this in practice — `official_sources` lives in the same database/process as everything else, with no separate OSR service — but the *architectural* documents never formally reconciled which owns it.
3. **Acquisition Record field-taxonomy drift (R013 §10 vs. R015 §8–10).** R013 gives one flat metadata list; R015 splits the same data into three categories (Acquisition Metadata / Integrity Metadata / Source Verification) with additional fields (Organization, Source Registry Identifier, Endpoint Identifier, Original Filename, Content Encoding, Subscription, ETag, Last Modified) R013 never mentions. Neither shape is what M1 actually implements (see next point).
4. **No M1 table corresponds to "Acquisition Record" as SDD-R015 defines it at all.** R015's central entity — an immutable, event-based record of *how* an artifact was acquired (workstation, DNS, TLS cert fingerprint, HTTP headers, redirect chain, etc.) — has no equivalent table in M1. `acquisition_jobs` (WP-003) and `download_sessions` (WP-006) together capture a *subset* (source, timestamps, connector, status) but not the rich chain-of-custody/source-verification metadata R015 specifies. **This is the largest single gap between ratified architecture and M1 implementation** — classified **M2 REQUIRED**, since SDD-R015 is a parent spec of SDD-R016 and neither WP-002 through WP-009 nor this audit's own scope authorizes inventing it now.
5. **Search capability defined redundantly, three times, with non-identical field sets** (R014 §15 Registry search, R016 §11 Vault search, R018 §15 Workspace search) — no document states whether these are one shared index or three independent ones. Moot for M1 (none of the three are implemented yet), but should be resolved before M2 builds any of them, to avoid building three.
6. **Publication-automation conditional (R018 §14) vs. R013's unconditional pipeline (§8).** R018 allows organizational policy to skip explicit engineer confirmation before publication ("unless organizational policy permits automation"); R013 states flatly "No stage may be bypassed" with no such carve-out. M1's own `POST /vault` is unconditionally synchronous and confirmation-free at the API level regardless — Studio's Wizard is where any "explicit engineer confirmation" would actually live, and this audit did not find a Studio-side gate enforcing it either way (see implementation audit §12).

## What M1 legitimately does not need to solve yet

Per WP-002 through WP-009's own explicit Out-of-Scope lists, all consistently reaffirmed by the SDDs' own "Future Extensions" sections (never phrased as binding milestones — see the SDD-reading agent's own note that no SDD uses "Milestone 1"/"M2" language; phasing is entirely a WP-series convention): OCR, AI/semantic analysis, engineering knowledge object creation, search indexing, licensing, lifecycle management, version comparison, duplicate detection beyond content-hash, replication, archival, encryption, authentication. None of these were implemented by this audit, and none should be — consistent with the task's own explicit prohibition list.
