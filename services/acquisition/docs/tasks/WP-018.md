# Objective

Establish the missing Acquisition Record entity WP-017's audit identified as the largest single architecture-vs-implementation gap in the EAM/Reference Vault pipeline: SDD-R015 describes a canonical, durable "Acquisition Record" tying an acquisition event to its Official Source, Job, Execution, Download, Verification, Metadata, and eventual Reference Vault publication -- and no table or entity in the M1 implementation corresponded to it. Provenance existed, but only as an implicit graph reachable by four sequential GET requests, never as an explicit, queryable identity.

This WP implements the smallest correct version of that entity supported by SDD-R015 and the existing M1 implementation -- not SDD-R015's full future vision (licensing, chain-of-custody events, DNS/TLS capture, digital signatures), which remain explicitly out of scope.

---

# Scope

Implement:

- Acquisition Record domain model, repository (Postgres + in-memory fake), and Service
- `acquisition_records` PostgreSQL table (additive migration, V10)
- Best-effort provenance bookkeeping wired into the existing `/downloads`, `/verifications`, `/metadata`, `/vault` REST handlers
- `GET /acquisition-records`, `GET /acquisition-records/{id}`, `GET /acquisition-records/{id}/provenance` REST routes
- Full provenance chain traversal (Vault Entry -> Acquisition Record -> Source / Job / Execution History / Download / Verification / Metadata) via existing foreign keys and repository filters -- no duplicated columns
- Unit tests (Service layer, fakes), Repository tests (real Postgres), migration tests, REST/integration tests (real Postgres + real HTTP server, full pipeline)

Do NOT implement (per the governing prompt's explicit scope control, and confirmed unnecessary by the audit below):

- Reference Vault search engine, indexing, OCR, AI interpretation, semantic classification, embeddings, knowledge graph
- Engineering Knowledge Object creation, Reference Library ingestion
- Distributed storage, cloud storage, licensing platform, enterprise authentication
- Arbitrary web crawling, a new connector framework, a new hashing system, a second provenance/artifact-identity/repository-abstraction system
- Resolution of ADR-0003 (HttpConnector scope/SSRF decision) -- referenced as context, explicitly not touched
- Chain-of-custody event log (SDD-R015 Sections 12-13), licensing metadata (Section 11), rich per-fetch metadata (DNS/TLS/redirect chain, Section 8/10), revision detection (Section 16) -- all classified FUTURE, not required to establish the missing identity/relationship this WP targets

# Functional Requirements

The Acquisition Record & Provenance Foundation shall support:

- Automatic creation of one Acquisition Record per Download Session, at download-attempt time
- Advancing that record's status (Acquired -> Verified -> Published, or -> Failed) as a best-effort side effect of the existing Download/Verification/Metadata/Vault REST handlers, never as a new precondition on any of their existing contracts
- Retrieve Acquisition Record
- List Acquisition Records (filterable by status)
- Reconstruct the full provenance chain for one Acquisition Record in a single request

---

# Domain Model

Each Acquisition Record shall contain:

- UUID (permanent Acquisition Identifier, SDD-R015 Section 6)
- Download Session ID (the record's one identity-defining relationship; UNIQUE)
- Status (`pending`, `acquired`, `verified`, `published`, `failed`, `archived`)
- Error Message (nullable; set only on a Failed transition)
- Created At / Updated At

No other relationship (Source, Job, Execution History, Verification, Metadata, Vault Entry) is stored as a column -- each is reachable by traversing an existing foreign key or repository filter starting from Download Session ID. See `docs/audits/ACQUISITION_RECORD_IMPLEMENTATION_AUDIT.md` for the full justification of this anchor choice and every field's provenance.

---

# REST API

Implement:

GET

    /acquisition-records

GET

    /acquisition-records/{id}

GET

    /acquisition-records/{id}/provenance

No creation or mutation route exists -- an Acquisition Record's lifecycle is entirely a side effect of the pre-existing `/downloads`, `/verifications`, `/metadata`, `/vault` POST routes (see Architecture Validation).

Responses use JSON, matching every existing route's conventions (UUID strings, ISO-8601 UTC timestamps, `{"error", "message"}` error bodies, `{"error": "validation_failed", "violations": [...]}` for validation failures).

acquisition_records (V10, additive; V1-V9 untouched)

# Validation Rules

Exactly one Acquisition Record exists per Download Session (enforced by a UNIQUE constraint).

Download Session shall exist (enforced by a foreign key).

A record's `download_session_id` and `created_at` never change after creation -- only `status`/`error_message`/`updated_at` do, and only via `IAcquisitionRecordRepository::update_status`.

Provenance bookkeeping failures never cause the pre-existing `/downloads`, `/verifications`, `/metadata`, `/vault` requests to fail.

# Architecture Validation

Did implementation require architectural changes to WP-001 through WP-009's existing services, repositories, or REST contracts?

No. `DownloadService`, `IntegrityVerificationService`, `MetadataExtractionService`, and `ReferenceVaultService` are unmodified -- their constructors, public methods, and existing tests are untouched. The new `AcquisitionRecordService` is called from the API/route layer (`server.cpp`), the one place that already assembles every pipeline stage together, as a best-effort side effect. `reference_vault` (V8) is unmodified. See `docs/audits/ACQUISITION_RECORD_IMPLEMENTATION_AUDIT.md` for the full reasoning.

Architecture validated. No ADR was required for this WP's own design choices (anchor on Download Session ID, route-layer integration, no historical backfill) -- each is a bounded implementation decision directly justified by SDD-R015's text, the existing codebase's own precedents, or this WP's own minimalism instructions, not an open architectural tradeoff requiring a decision from a human stakeholder the way ADR-0003 was.
