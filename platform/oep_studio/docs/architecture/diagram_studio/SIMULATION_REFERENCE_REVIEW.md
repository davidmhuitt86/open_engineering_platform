# Simulation Reference Review

**Architecture Phase:** AP-DS-005. Mandatory review of `platform/reference/legacy_simulation_engine_v2/` performed before any Simulation Engine code was written, per the governing spec's explicit gate. This document is a knowledge-extraction record, not a design document — it evaluates what the legacy project actually contains, honestly, with no obligation to adopt anything it describes. All findings below trace to a full, independent, read-only review of the legacy codebase (Node.js/vanilla-JS, unrelated in architecture to this platform).

## What the legacy project actually is (important context for every judgment below)

`legacy_simulation_engine_v2` is **two largely disconnected implementations plus a separate OCR/extraction subsystem**, not one coherent simulator:

1. **The browser simulator** (`apps/simulator/js/*`) — a real, working, single-vehicle (1988 Honda TRX300) wiring-diagram simulator: a graph builder, BFS/DFS/path-finding, a flood-fill-style voltage/ground propagator, a continuity/resistance solver, fault injection, a virtual multimeter, static graph validators, and an SVG/DOM renderer with automotive wire-color conventions.
2. **A second, thinner "knowledge engine" skeleton** (`core/graph/*`, `reasoning/*`) — a parallel graph/FSM/rule-engine implementation, exercised only by manual test scripts, never connected to the browser simulator, with shallower diagnostics and fault injection that doesn't actually affect electrical state.
3. **A Python OCR/extraction pipeline** (`diagram-extractor/*`) — for turning scanned wiring diagrams into graph data; a distinct concern from simulation itself.

Both JS engines independently reimplement the same graph-traversal algorithms (BFS/shortest-path/reachability) — the project's own architecture documentation states "the graph owns the truth" as a rule its own structure violates. This project is a **working single-vehicle prototype**, not a finished or integrated product — stated honestly here because the traceability matrix and the new engine's design both depend on knowing which parts are real, working code versus aspirational documentation.

## Concepts retained

These generalize cleanly and are genuinely useful engineering ideas, independent of the legacy implementation:

- **Power and ground modeled as two independent reachability passes**, combined as `functional = powered && grounded`, rather than merged into one "net" concept. This is a real, deliberate design choice (not aspirational) that maps directly onto how automotive/industrial electrical systems are actually reasoned about — worth keeping conceptually.
- **A dedicated dependency-tracing layer distinct from raw connectivity** (`dependenciesOf`/`dependentsOf`/`whatFailsIf`) — "what does this component need to function" and "what breaks if this component fails," including a redundant-path-aware variant (`whatFailsIf`) that only reports true single-point-of-failure dependents. The redundancy-awareness idea is worth retaining even though the legacy implementation of it had a real bug (only checked the first power source — see Concepts Rejected).
- **Behavioral (not just wiring) dependency for stateful components** — a relay's contacts depend on its coil being energized, modeled as a distinct behavioral rule layered on top of raw connectivity. This is exactly the kind of engineering-real concept worth preserving: a relationship's *effect* on propagation can depend on another component's *state*, not just on whether a wire exists.
- **Path-finding as a first-class diagnostic primitive** — "trace how power/ground reaches this specific point" as a named, reusable operation (not just an internal detail of the propagator), consumed independently for both diagnosis and diagram highlighting.
- **A distinct "floating" concept for ground reachability** (`GroundPropagator.floatingNodes()`), even though the legacy voltage side collapsed "floating" and "legitimately at 0V" into the same value — the ground side's cleaner is/isn't-reachable boolean is the better pattern of the two, worth generalizing to every signal type, not just ground.
- **Fault injection as an overlay, not a graph mutation** — faults are tracked as a separate conditions map consulted during propagation, never mutating the underlying graph. This keeps the base graph pristine and fault scenarios trivially resettable — a good, retainable pattern.
- **Static graph validators independent of simulation** (orphan wire, missing terminal, duplicate wire, floating ground, disconnected circuit/island detection) run once at load time, separate from runtime propagation — the "verify the design is sound" concern kept distinct from "simulate its behavior."
- **A named vocabulary worth keeping terminology-compatible with**: Terminal, Connector (paired halves), Wire, Harness, Continuity, Key Position, Pickup/Dropout Voltage (relay hysteresis) — standard automotive/industrial wiring-diagram terms, independent of any implementation.
- **Deriving regression test scenarios from real prior test scripts** — `tests/simulator-test.js`'s state-transition + fault-injection + re-diagnose sequence, and `tests/fault-reasoner-test.js`'s multi-symptom diagnosis scenarios, are concrete, re-derivable regression cases (see `SIMULATION_TRACEABILITY_MATRIX.md` and the new test suite).

## Concepts rejected

Explicitly not carried forward, with reasoning:

- **Two competing, non-interoperating graph/traversal implementations in one project.** The legacy project's own documentation states this as an anti-pattern its own structure violates. The new Simulation Engine has exactly one graph/propagation core, reusing `oep_engine`'s existing `EngineeringGraph`/`KnowledgeGraphEngine` — never a second, parallel graph representation.
- **One-voltage-per-node (not per-terminal) electrical modeling**, self-flagged in the legacy code's own comments as a simplification that breaks down for multi-terminal components like relays and connectors. Rejected as a modeling choice — but see Concepts Improved below for what replaces it.
- **Global-scope, non-module shared-window-object architecture.** Irrelevant to a Dart/Flutter target and a real source of implicit coupling in the legacy code even within its own JS context — not applicable here at all.
- **Two competing sources of truth for the same measurement** (a live solver and a static-JSON fallback, reconciled only by a code comment describing a "priority order" that the two files didn't even agree on with each other). Rejected outright — the new engine has exactly one measurement computation path.
- **Hand-tuned, fixed "confidence"/"probability" numeric literals presented as calibrated values** (e.g. `0.9`/`0.8`/`0.85`/`0.5` confidence literals with no derivation). Rejected as a pattern — not because confidence scoring itself is bad, but because presenting arbitrary constants as if they were measured probabilities is misleading. Where the new Diagnostics Engine ranks findings, it will do so with an explicitly-documented, honestly-described heuristic ordering, not invented decimal precision.
- **A `nets`/`Net` concept that exists in schema/documentation but has zero real implementation anywhere in the legacy codebase.** Not carried forward as unused surface area — if a true electrical-net/equivalence-class concept is needed later, it should be designed properly from the start, not inherited as dead schema.
- **SPICE-style or physics-based analog simulation.** Never present in the legacy project to begin with (it never modeled real voltage division, current, or resistive networks — the "voltage propagation" was flood-fill, not Kirchhoff's laws), and explicitly out of scope for AP-DS-005 regardless.
- **No automated test framework — an entire "test suite" of manually-run console-log scripts with no CI wiring, and a genuinely-planned real test suite that was simply never written** (`apps/simulator/tests/` contains only a README of "planned" tests, zero actual test files). Rejected as a practice, not a concept — the new Simulation Engine has a real, automated test suite from the start (see Testing below).

## Concepts improved

Ideas worth keeping but implementing more rigorously than the legacy version did:

- **Per-terminal (not per-node) signal state.** `oep_engine`'s existing `Port`/`EngineeringNode` model already has per-node ports with `id`/`name`/`direction`/`type` — the new Simulation Engine's signal-state model should key state by `(nodeId, portId)` where ports are declared, not collapse an entire multi-pin component to one state value. This directly fixes the legacy model's own self-acknowledged weakness.
- **Redundant-path-aware dependency analysis, fixed.** The legacy `whatFailsIf` only checked paths from the *first* power source found, under-reporting redundancy on multi-source graphs. The new implementation must check paths from every power source in the relevant domain, not just one.
- **A single canonical graph-traversal core, reused by verification, propagation, and diagnostics alike** — instead of three independent BFS reimplementations (one per subsystem, as the legacy project had), the new engine's propagation, verification, and diagnostics all call into the same `oep_engine` graph-traversal primitives (`GraphAlgorithms`, already built for WP-EKE-002), extended only where genuinely new traversal semantics are needed (e.g. state-gated propagation), never duplicated.
- **Deterministic, disclosed-heuristic diagnostic ranking** instead of decimal-precision "confidence" literals — findings are ranked by an explicit, documented rule (e.g. "no power path" ranks above "upstream dependency guess"), described honestly as an ordering, not fabricated as a calibrated probability.
- **Incremental-update awareness**, even if full-graph re-simulation is the correct starting implementation at this platform's stated scale target (100,000 Engineering Objects is far larger than the legacy project's few-dozen-node prototype) — the new engine's session/state model is designed so a future incremental-update pass is an additive optimization, not a rearchitecture, unlike the legacy project's from-scratch-every-time design which had no such seam.

## Concepts superseded by Foundation Runtime

- **Graph persistence and the underlying object/relationship model.** The legacy project's `Component`/`Terminal`/`Wire`/`Relationship` classes and its flat vehicle-JSON schema are entirely superseded by Foundation's `EngineeringObject`/`Relationship` model (already the platform's single source of truth since WP-REP-001 onward) — the new Simulation Engine executes against Engineering Objects/Relationships directly, never a parallel data model.
- **Vehicle/manufacturer/system reference data storage** (`database/vehicles/*.json`, `database/manufacturers/*.json`) — superseded by the Repository/Package model (WP-REP series, AP-DS-002's repository integration) as the place engineering reference data lives.

## Concepts superseded by Engineering Engine

- **The graph builder, connectivity model, and node/edge representation** (`GraphBuilder`, `CircuitGraph`, `GraphTraversal`) — superseded entirely by `oep_engine`'s existing `EngineeringGraph`/`EngineeringNode`/`EngineeringRelationship`/`Port` model and `KnowledgeGraphEngine`'s `GraphAlgorithms` (connected components, shortest path, reachability — already built for WP-EKE-002). The new Simulation Engine consumes these directly rather than reimplementing graph construction or traversal.
- **Static graph validators** (orphan wire, missing terminal, duplicate wire, floating ground, disconnected circuit) — conceptually retained (see Concepts Retained) but their *implementation* is superseded: the new Engineering Verification checks are built as part of the Simulation Engine's Verification module (per AP-DS-005's own architecture), operating on the same `EngineeringGraph` the rest of the platform already uses, not a bespoke validator set bolted onto a separate graph representation.
- **The diagram renderer's category/wire-color styling conventions** — the visual *ideas* (color-code by category, distinct wire-color table, striped-wire rendering) are worth keeping as reference for Diagram Studio's own overlay styling, but the renderer *implementation* is entirely superseded by Diagram Studio's existing `GraphViewPanel`/painter architecture (frozen since AP-DS-001) — Diagram Studio adds simulation-state overlays to its existing rendering pipeline, it does not adopt any legacy rendering code.

## Concepts superseded by Engineering Intelligence Platform

- **`FaultReasoner`'s symptom-to-cause matching and `FaultLocator`'s root-cause explainer.** The general *idea* — rank likely causes, explain why a component lacks power/ground, produce a test plan — is retained conceptually, but the actual reasoning/ranking logic is superseded by the Engineering Intelligence Platform's `ReasoningEngine`/`AnalysisEngine` (WP-EKE-006), which already provides deterministic, evidence-referenced conclusions and recommendations. The new Simulation Engine's Diagnostics module produces simulation-specific facts (which nodes lost power, which fault is active, which path is broken); *reasoning about* those facts to produce ranked recommendations is EIP's job, consumed through `EngineeringIntelligencePlatform`/`DiagramIntelligenceService`, never reimplemented inside the Simulation Engine.
- **`reasoning/systems/*` (System Recognizer) and `reasoning/topology/*` (Topology Recognizer)** — pattern-matching a graph against known system/topology templates to answer "what kind of system is this." This class of reasoning belongs to EIP's `AnalysisEngine`/`ReasoningEngine`, not the Simulation Engine, which is scoped to deterministic execution and logical propagation only, per AP-DS-005's own Architectural Principles.
- **`DiagnosticEngine`'s flat isolated-component/active-fault scan** — conceptually the simplest form of "produce findings from graph state," now superseded by EIP's `ValidationEngine`/rule system (WP-EKE-004/005), which already provides a real, data-driven rule evaluation framework far more capable than the legacy flat scan.

## Summary judgment

The legacy project's genuine engineering value is in its **conceptual vocabulary and problem decomposition** (power/ground as independent propagations, dependency tracing, path-finding as a diagnostic primitive, fault-as-overlay, behavioral dependencies for stateful components) — not in its code, which the project's own architecture documentation self-critiques for exactly the kind of duplication a fresh implementation must avoid. Every concept judged worth retaining above is retained as an *idea*, reimplemented from scratch inside `oep_engine`'s existing architecture, consuming Engineering Objects/Relationships directly, never by porting, copying, or migrating any legacy code or data structure.
