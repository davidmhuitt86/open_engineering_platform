# CLI

Status: Foundation (v0.1.0)

Purpose: The `oep` executable — the primary developer interface for Foundation, per OEP-SPEC-012-CLI_COMMAND_FRAMEWORK. Every command that touches a repository goes through `FoundationRuntime`; the CLI never constructs Repository/Search/Validation/Package services directly.

## Architecture

- `include/oep/cli/` — public command interfaces (`Command`, `CommandRegistry`)
- `src/commands/` — individual command implementations
- `src/generator/` — Foundation Generator (repository scaffolding used by `init`)
- `src/foundation_version.hpp` — the single `kFoundationVersion` constant shared by `version`, the generator, and every Runtime-backed command
- `src/main.cpp` — thin entry point: registers commands and dispatches

Command logic is built as a static library, `oep_cli_core` (see `CMakeLists.txt`), which the `oep` executable links against. This lets `tests/cli` unit-test commands directly, without spawning the built executable as a subprocess.

## Commands

- `oep --help` / `oep -h` — display available commands (Name/Syntax/Description for each)
- `oep version` — display the CLI version
- `oep init <repository-name>` — generate a Standard Repository per OEP-SPEC-002-FOUNDATION_REPOSITORY
- `oep open <repository>` — open a repository through the Foundation Runtime
- `oep validate [repository]` — run Repository Validation and report health
- `oep packages [repository]` — list discovered packages and their state
- `oep status [repository]` — show Runtime state, current repository, repository ID, and loaded package count
- `oep object create|list|show|delete` — create, list, show, and delete Engineering Objects (`--repository <path>` optional, defaults to the current working directory)
- `oep relationship create|list|show|delete` — create, list, show, and delete Relationships (`--repository <path>` optional, defaults to the current working directory)
- `oep search [objects|relationships] <query>` — search Engineering Objects and/or Relationships, with `--type`/`--author`/`--tag` filters applied after the Search Engine runs
- `oep graph neighbors|traverse|path` — explore Engineering Objects through their Relationships (BFS/DFS traversal, path existence)
- `oep export <output-file>` — export the repository to a single deterministic archive (`--include-packages` optional)
- `oep import <archive-file>` — reconstruct a repository from an archive (`--destination`/`--overwrite` optional)
- `oep template create|list|instantiate` — capture, list, and instantiate reusable Repository Templates (`--templates-dir` optional, defaults to the current working directory)
- `oep batch create|delete|validate <input-file>` — execute or validate a batch of object/relationship operations from a JSON file (`--repository` optional, defaults to the current working directory)
- `oep package install <archive.oep>` — install a valid `.oep` package into the repository: verify its trust (WP-REP-004; rejected outright if `Tampered`/`InvalidSignature`/`UnknownPublisher`/`ExpiredCertificate`/`RevokedCertificate`), resolve its dependencies (WP-REP-005; rejected outright on a required `Missing` dependency, a `Conflicting` version, a malformed constraint, or a `Cyclic` chain), then extract its Repository Fragment, register its Engineering Objects and Relationships, update the Search/Graph indexes, and record the install in the Repository Registry (`--repository` optional, defaults to the current working directory). Atomic since WP-REP-003 — a failed install rolls back completely and nothing is journaled if trust verification or dependency resolution rejects the package.
- `oep package resolve <archive.oep>` — dry-run dependency resolution (WP-REP-005): reports each declared dependency's state (Satisfied/Missing/Optional/Conflicting/Cyclic/Unknown), the deterministic install order, any detected cycle chain, and any errors/warnings — without installing anything (`--repository` optional, defaults to the current working directory)
- `oep package list` — list every package recorded in the Repository Registry (ID, version, title, publisher, runtime state, contribution counts, install time)
- `oep package info <package-id>` — the full Repository Registry record: manifest metadata, publisher, engineering domains, runtime state, installation path, and SHA-256 package hash (WP-REP-002)
- `oep package contents <package-id>` — the Engineering Objects and Relationships the package installed, with their live names/types loaded from the repository
- `oep package verify <package-id>` — verify every recorded contribution still exists and the source archive (if still present) still matches its recorded hash; exits nonzero on a failed verification
- `oep package locate <entity-id>` — which installed package contributed a given Engineering Object or Relationship
- `oep package search <query>` — search installed packages by ID, title, summary, category, version, publisher, engineering domain, or installed-object name
- `oep package uninstall-impact <package-id>` — dry-run uninstall analysis (WP-REP-007): reports whether the package is found, the object/relationship counts that would be removed, and any OTHER installed package's blocking required dependency on it, without uninstalling anything; exits nonzero unless removable
- `oep package uninstall <package-id>` — uninstall an installed package; refuses (nonzero exit, nothing changed) if another installed package has a required dependency on it — see `uninstall-impact`
- `oep package update-impact <archive.oep>` — dry-run update analysis (WP-REP-007): reports current/candidate version, trust status, and any OTHER installed package's required dependency that the candidate version would break, without updating anything; exits nonzero unless updatable
- `oep package update <archive.oep>` — replace an installed package with the candidate version in the given archive; refuses (nonzero exit, nothing changed) if the package isn't installed, trust verification blocks it, its dependencies can't be resolved, or the update would break another installed package's required dependency — see `update-impact`
- `oep package merge-plan <archive.oep>` — dry-run merge analysis (WP-REP-008): reports package/version, trust status, whether the package is already registered, the object/relationship counts that would be created, and any conflicts (an existing object/relationship with different content) without merging anything; exits nonzero unless mergeable
- `oep package merge <archive.oep>` — merge a package archive's objects/relationships into the currently open repository, generalizing `install` to tolerate pre-existing, identical content as a no-op; refuses (nonzero exit, nothing changed) if the resulting plan is not mergeable (trust, dependency resolution, or any conflict) or the package_id is already registered — see `merge-plan`
  (all `package` subcommands take `--repository <path>`, defaulting to the current working directory; `install` is atomic since WP-REP-003 — a failed install rolls back completely; `uninstall`/`update`/`merge` are routed exclusively through RuntimeService since WP-REP-007/WP-REP-008)
- `oep transaction list` — every journaled Repository Transaction (WP-REP-003): id, state (Committed/RolledBack/Failed), description, operation count, open time
- `oep transaction show <transaction-id>` — one journaled transaction in full, including each operation's target and previous/new state
- `oep trust trust <publisher-id> --key <hex> [--name <name>] [--expires <utc>] [--issuer <name>]` — trust a publisher's Ed25519 public key (WP-REP-004); the fingerprint is always computed locally, never taken from input
- `oep trust list` — every certificate in this repository's Trust Store, trusted and revoked alike
- `oep trust revoke <publisher-id>` — revoke a publisher's certificate (the record is kept, marked revoked; does not uninstall anything already installed from that publisher)
- `oep trust policy [show|require|allow-unsigned]` — view or change whether this repository's `oep package install` rejects unsigned packages (default: allowed)
- `oep runtime events [--limit N]` — read back the Repository Events log (WP-REP-006): one line per event (sequence, UTC timestamp, event type, subject id, detail), oldest first, published by `oep object create|delete`, `oep relationship create|delete`, and `oep package install`. Process-scoped, in-memory only — not persisted, not repository-scoped, so it only reflects commands run in the same `oep` process (`--limit N` caps output to the N most recent events, default unlimited)
- `oep engine load [--repository <path>]` — loads the Engineering Knowledge Runtime's Runtime Graph (WP-EKE-001) from the currently open repository and reports the object/relationship counts loaded
- `oep engine stats [--repository <path>]` — builds the Knowledge Graph (WP-EKE-002) and reports its full `GraphStatistics`: object/relationship/connected-component counts, density, maximum depth, average degree, and the relationship-type/domain distributions
- `oep engine inspect <object-id> [--repository <path>]` — loads the Runtime Graph, then prints one Engineering Object's fields (id, type, name, author, version, description, tags) plus its directly related objects
- `oep engine query --id <object-id> | --type <ObjectType> | --domain <tag> | --relationship <RelationshipType> [--repository <path>]` — loads the Runtime Graph, then runs one Graph Query (Find by ID/Type/Domain/Relationship) and prints the matching object ids; exactly one selector flag is required. **Unchanged since WP-EKE-001** — see the WP-EKE-003 `--category` mode described below for the newer, richer alternative
- `oep engine query --category <object|relationship|domain|type|dependency|neighborhood|path|reference|metadata|composite> [--id <object-id>] [--secondary-id <object-id>] [--type <ObjectType>] [--domain <tag>] [--relationship <RelationshipType>] [--publisher <id>] [--package <id>] [--tags <tag1,tag2>] [--depth <n>] [--direction out|in|both] [--repository <path>]` — WP-EKE-003 mode: builds the Knowledge Graph, plans and executes one of the Engineering Query Engine's ten query categories via `EngineeringQueryEngine::execute_query`, and prints the matching object ids, relationship ids, result count, and traversal summary. `--id`/`--secondary-id` supply `QueryRequest`'s primary/secondary object ids (secondary is only meaningful for `path`); every other flag sets one `QueryFilter` field (`--tags` is comma-separated and ANDed, per `QueryFilter::tags`' documented all-must-match rule). Triggered only by the presence of `--category`, so it never changes the behavior of the original `--id`/`--type`/`--domain`/`--relationship` form above
- `oep engine traverse <start-object-id> [--order bfs|dfs] [--relationship <RelationshipType>] [--max-depth N] [--repository <path>]` — loads the Runtime Graph, then traverses it from `<start-object-id>` (breadth-first by default), optionally following only relationships of one type and/or stopping past `N` edges from the start, printing the visited object ids in traversal order
  (every `engine` subcommand is self-sufficient — since a fresh `oep` invocation has no persistent Engine state, each one opens the repository and calls `load_graph()` internally before doing anything else, per WP-EKE-001's Public Runtime API: load_object/load_graph/query/traverse/related_objects/dependency_graph, exposed here as `oep engine`'s command surface plus a `--repository`-only `oep_engine_load_object` equivalent reachable through `inspect`. Named `engine` rather than `graph` deliberately: `oep graph` (WP-016, neighbors/traverse/path) already names the Repository Graph Engine, a lower-level primitive over Relationships directly; WP-EKE-001's Runtime Graph is a distinct, higher-level in-memory index with its own domain-by-tag and relationship-filtered/depth-limited traversal semantics)
- `oep engine build [--repository <path>]` — builds the canonical Knowledge Graph (WP-EKE-002, `KnowledgeGraphEngine::build_graph`) from the currently open repository and reports the object/relationship counts built
- `oep engine validate [--repository <path>]` — builds the Knowledge Graph, then validates it (`GraphValidationReport`) and prints `Valid: yes`/`Valid: no` plus one line per issue (kind, relationship id when applicable, detail); exits 0 iff valid, 1 otherwise
- `oep engine components [--repository <path>]` — builds the Knowledge Graph, then prints its connected component count and one line per component (its object ids, space-separated)
- `oep engine export --format json|graphml [--repository <path>]` — builds the Knowledge Graph, then prints its export to stdout: `json` is a complete `{"objects": [...], "relationships": [...]}` document; `graphml` is a minimal, well-formed GraphML PLACEHOLDER document (correct node/edge counts and ids, not the full GraphML attribute/key schema — see `graph_serialization.hpp`)
  (`build`/`validate`/`stats`/`components`/`export` are the WP-EKE-002 additions to this same `engine` command group; each is self-sufficient exactly like the WP-EKE-001 subcommands above, calling `KnowledgeGraphEngine::build_graph()` internally rather than `EngineeringContext::load_graph()`. These subcommands talk to `KnowledgeGraphEngine` directly in C++, not through the Public C API's `oep_kge_*` functions — so `stats` can show the full relationship-type/domain distributions that the C API's `oep_graph_statistics_t` deliberately omits (see `oep_api.h`'s WP-EKE-002 section for that scope decision))
- `oep engine explain --category <...> [--id <object-id>] [...same flags as `query --category`...] [--repository <path>]` — builds the Knowledge Graph, then plans (never executes) the query via `EngineeringQueryEngine::plan_query` and prints the resulting `QueryPlan`: category, traversal strategy, estimated cost, indexes used, and an execution-order preview
- `oep engine profile --category <...> [--id <object-id>] [...same flags...] [--repository <path>]` — builds the Knowledge Graph, executes the query, and prints its full `QueryStatistics`: execution time (ms), objects/relationships examined, traversal depth, result count, indexes used, and the traversal summary
- `oep engine cache [--repository <path>]` — builds the Knowledge Graph and prints the Engineering Query Engine's current `QueryCache` occupancy (cached plan count, cached result count). Since each `oep` invocation is a fresh process with no engine state left over from an earlier command, a bare `oep engine cache` reports an empty cache — its value is mainly diagnostic/scripting (e.g. confirming `clear-cache`'s effect within one longer invocation)
- `oep engine clear-cache [--repository <path>]` — builds the Knowledge Graph, then calls `EngineeringQueryEngine::clear_query_cache()` and confirms. Same self-contained-per-invocation caveat as `cache` above; the Runtime API's own documented invalidation contract is "callers MUST call this after rebuilding/refreshing the Knowledge Graph if subsequent queries should reflect it" — this subcommand is that call, exposed directly
  (`explain`/`profile`/`cache`/`clear-cache` are the WP-EKE-003 additions to this same `engine` command group, alongside the `--category` mode added to `query` above, all backed by `EngineeringQueryEngine` — constructed from `KnowledgeGraphEngine` only, never bypassing it. Every one of these subcommands is self-sufficient exactly like the WP-EKE-001/WP-EKE-002 subcommands above)
- `oep rules list [--repository <path>]` — prints every registered rule id, split into enabled/disabled
- `oep rules register --id <rule-id> --name <name> --category <RuleCategory> --severity <RuleSeverity> --scope-type <AllObjects|ByObjectType|ByDomain|ByPackage|SingleObject> [--scope-value <value>] --condition-kind <RuleConditionKind> [--relationship-type <RelationshipType>] [--tag <tag>] [--count <n>] --message <message> [--recommendation <text>] [--description <text>] [--evaluate] [--repository <path>]` — constructs and registers a **single-condition** `EngineeringRule` (WP-EKE-004) from flags — a deliberate subset of the full data model, which supports multiple conditions per rule; there is no general-purpose multi-condition rule-authoring CLI. Pass `--evaluate` to also build the Knowledge Graph and evaluate the rule immediately in the same process, printing its status/message/affected objects/diagnostics
- `oep rules enable <rule-id> [--repository <path>]` / `oep rules disable <rule-id> [--repository <path>]` — enables/disables a registered rule
- `oep rules evaluate <rule-id> [--repository <path>]` — builds the Knowledge Graph and evaluates one registered rule, printing status/message/affected objects/diagnostics; exits 0 iff `Passed`
- `oep rules info <rule-id> [--repository <path>]` — prints a registered rule's full definition (id, name, description, category, severity, scope kind, condition kinds, message, recommendation)
  (**process-local registry, not persisted**: exactly like `oep engine`'s Runtime Graph/Knowledge Graph, every `rules` subcommand opens the repository and constructs a fresh, empty `RulesEngine`/Rule Registry, then exits — there is no cross-invocation state and no rule-loading/persistence mechanism yet (a future work package's job). This means a bare `oep rules list`/`enable`/`disable`/`evaluate`/`info` against a rule_id registered by an EARLIER, separate `oep rules register` invocation will always fail not-found — this is documented, not a bug. The one subcommand that is genuinely useful standalone is `register --evaluate`, which registers and evaluates a rule end to end within a single process. Every function goes through `oep::engine::RulesEngine`, itself constructed from `EngineeringContext`/`KnowledgeGraphEngine`/`EngineeringQueryEngine` only, never bypassing those layers. Programmatic callers wanting a persistent rule set across calls should register rules via the Public C API's `oep_rules_register` once per long-lived process handle)
- `oep evalidate profiles` — lists the five Validation Profiles (WP-EKE-005): `Structural`, `Connectivity`, `Documentation`, `Metadata`, `Complete`. Static data; no repository needed
- `oep evalidate object <object-id> [--profile <name>] [--repository <path>]` / `oep evalidate package <package-id> [--profile <name>] [--repository <path>]` / `oep evalidate context [--profile <name>] [--repository <path>]` — build the Knowledge Graph, start a `ValidationSession` for `--profile` (default `Complete`), validate the given scope, and print the report: rules evaluated, pass/warning/error/critical counts, execution time, and each finding (finding id, rule id, severity, category, message, recommendation). Exit code is 0 iff the report has zero Error- and zero Critical-severity findings (Info/Warning findings do not fail the exit code)
- `oep evalidate report <session-id> [--repository <path>]` — prints the most recent report for a session_id. Because `ValidationSession`s are held in-memory and process-local (see below), this can only ever find a session created earlier in the SAME invocation — a separate `oep evalidate report` call can never see a session from an earlier `oep evalidate object/package/context` call, and this subcommand documents that honestly rather than pretending to look it up
  (**process-local, no persistence**: exactly like `oep rules` above, every `evalidate` subcommand opens the repository and constructs a fresh, empty `RulesEngine` plus a fresh `ValidationEngine` over it, then exits. With zero rules ever registered in that same process, `object`/`package`/`context` always validate against zero rules and trivially "pass" (`rules_evaluated == 0`) — this is the same honest limitation `oep rules` already documents for its own subcommands, not a new one. Note the command group is named `evalidate` rather than `validate`: `oep validate [repository]` already exists in this CLI as a long-standing, unrelated command (Repository Validation via `FoundationRuntime::validator()`); reusing that name for the Engineering Validation Engine would shadow or break it, so this new WP-EKE-005 group uses `evalidate` (Engineering VALIDATE) instead, keeping every subcommand name — `object`/`package`/`context`/`report`/`profiles` — exactly as named elsewhere. Every function goes through `oep::engine::ValidationEngine`, itself constructed from `EngineeringContext`/`KnowledgeGraphEngine`/`EngineeringQueryEngine`/`RulesEngine` only, never bypassing those layers. Programmatic callers wanting meaningful validation against a real, persistent rule set should register rules via the Public C API's `oep_rules_register` and drive `oep_validation_*` in a long-lived process handle)
- `oep analysis dependencies <object-id> [--repository <path>]` / `oep analysis impact <object-id> [--repository <path>]` — build the Knowledge Graph and run the WP-EKE-006 Analysis Engine's stateless dependency/impact closures over `object-id`, printing the object id, max depth, dependency/affected object and relationship id lists, and the evidence string naming which algorithm produced the report
- `oep analysis reachability <source-id> <target-id> [--repository <path>]` — builds the Knowledge Graph and reports whether `target-id` is reachable from `source-id` (any relationship type, either direction) plus the shortest path if so; exits 0 iff reachable
- `oep analysis root-cause <symptom-object-id> [--repository <path>]` — builds the Knowledge Graph, routes through `ReasoningEngine::analyze_root_cause` (which runs its own Complete-profile validation internally against this invocation's fresh, empty Rule Registry — see the process-local note below), and prints candidate root causes (ordered closest-first) plus the failure chain to the symptom
- `oep reasoning execute <object-id> [<object-id> ...] [--objective <text>] [--repository <path>]` — builds the Knowledge Graph, creates a `ReasoningSession` for `--objective` scoped to the given starting objects, immediately executes it (dependency/impact/root-cause analysis plus validation per starting object, building the session's Evidence Graph and deriving `EngineeringConclusion`s/`EngineeringRecommendation`s), and prints the session id, objective, execution time, and every conclusion/recommendation — all in ONE invocation, since sessions are process-local (see below)
- `oep reasoning report <session-id> [--repository <path>]` / `oep reasoning evidence <session-id> [<evidence-id>] [--repository <path>]` / `oep reasoning recommendations <session-id> [--repository <path>]` — inspect a session's most recent `ReasoningReport` (full report / one Evidence Graph node or the whole node list / just the recommendations). Because `ReasoningSession`s are process-local (see below), these can only ever find a session created earlier in the SAME invocation as `oep reasoning execute` — they exist for completeness and single-process testing, not cross-invocation lookup, and document that honestly rather than pretending to look it up
  (**process-local, no persistence**: exactly like `oep evalidate` above, every `analysis`/`reasoning` subcommand opens the repository and constructs a fresh `ReasoningEngine` over a fresh, empty `RulesEngine`/`ValidationEngine`, then exits — `analysis root-cause` therefore always reports zero candidate root causes unless rules were registered via the Public C API in a longer-lived process. `oep recommendations` (the work package's own literal top-level spelling) is deliberately exposed as `oep reasoning recommendations` instead of a new bare top-level command, keeping the `oep <noun> <verb>` shape every other command group in this CLI already follows, since Recommendations are a convenience view of a `ReasoningReport` that otherwise lives entirely under `oep reasoning`. Every function goes through `oep::engine::ReasoningEngine`, itself constructed from `EngineeringContext`/`KnowledgeGraphEngine`/`EngineeringQueryEngine`/`RulesEngine`/`ValidationEngine` only, never bypassing those layers)
- `oep session create [--repository <path>]` / `oep session list [--repository <path>]` / `oep session close <session-id> [--repository <path>]` — the WP-EKE-007 Knowledge Session Manager lifecycle: `create` opens the repository, creates one `KnowledgeSession` via `EngineeringIntelligencePlatform::create_session`, and prints its session_id; `list` prints every session_id known to THIS invocation (always empty on a fresh process, since sessions are process-local — see below); `close` closes a session_id, failing not-found if it was never created in this same invocation. None of these require a built graph
- `oep inspect [--type object|package|context] <target-id> [--repository <path>]` — builds the Knowledge Graph and runs the WP-EKE-007 Service Orchestrator's stateless `inspect_object`/`inspect_package`/`inspect_context` (selected by `--type`, default `object`), printing the target kind, object id list, validation pass/finding counts (from an internal Complete-profile Validation Engine pass), and summary. `<target-id>` may be omitted only when `--type context` is used
- `oep summary [--health-only] [--repository <path>]` — builds the Knowledge Graph and runs the Service Orchestrator's `engineering_summary`/`engineering_health` in one invocation, printing object/relationship/connected-component counts and validation pass/finding counts, followed by the deterministic 0-100 health score (`100 * passed / (passed + failed)`, defaulting to 100 when nothing was evaluated) plus its passed/failed/warning/error/critical breakdown. `--health-only` skips the `engineering_summary` half and prints only the health report
- `oep metrics [--repository <path>]` — prints this invocation's Runtime Metrics snapshot (query/validation/analysis/reasoning counts, cache hits/misses, active/total session counts, total execution time). No built graph required — a fresh handle simply reports all zeros, which is exactly what this always prints in a single-shot CLI invocation (see below)
- `oep workflow inspect|query|validate|analyze|reason|recommend [--target <id>] [--type object|package|context] [--category <...>] [--profile <name>] [--objective <text>] [<object-id> ...] [--repository <path>]` — the single-invocation convenience entry point: builds the Knowledge Graph, creates ONE session internally, runs exactly one of the six Workflow Engine methods against it, and prints the `WorkflowResult` (kind, success, execution time, summary, object ids) plus the session_id it used — the same "create-and-run in one call" convenience pattern `oep rules register --evaluate` (WP-EKE-004) already established. `reason` takes one or more starting object ids as trailing positional arguments instead of `--target`
  (**process-local, in-memory sessions — the same limitation every prior WP-EKE session-based feature (`oep evalidate`/WP-EKE-005, `oep reasoning`/WP-EKE-006) already carries**: every `session`/`inspect`/`summary`/`metrics`/`workflow` invocation opens the repository, constructs a fresh `EngineeringIntelligencePlatform` over fresh lower engines, does its work, and exits — a session_id printed by `oep session create` or `oep workflow ...`'s trailing "Session: ..." line cannot be resolved by any LATER, separate CLI invocation; `oep session list`/`oep metrics` on a fresh invocation always report zero/empty, and `oep session close <id>` against an id from an earlier invocation always fails not-found. This is documented at each command's own help text, not silently implied. `oep workflow` is the primary single-invocation entry point for actually exercising a workflow from the shell; `oep session create/list/close` exist for completeness and scripting (e.g. verifying the lifecycle in isolation) rather than as a practical multi-step CLI session flow. `oep session`/`oep inspect`/`oep summary`/`oep metrics`/`oep workflow` are new top-level command names with no collision against any pre-existing command — unlike WP-EKE-001's `engine` (chosen over `graph` to avoid colliding with the pre-existing WP-016 `oep graph`) or WP-EKE-005's `evalidate` (chosen over `validate` to avoid colliding with the pre-existing Repository Validation command), none of these five names were already in use, so no disambiguation was needed. Every function goes through `oep::engine::EngineeringIntelligencePlatform`, itself constructed from `EngineeringContext` plus all six lower engines only, never bypassing those layers)

See [platform/runtime/CLI_USAGE.md](../runtime/CLI_USAGE.md) for build instructions, example sessions, and troubleshooting.

New commands are added by implementing `oep::cli::Command` (overriding `usage()` if the command takes arguments) and registering an instance in `main.cpp`. No other part of the CLI needs to change.
