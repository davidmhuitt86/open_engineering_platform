REMAINING GAPS:
- `@oep-exchange/exchange-client`'s real `ExchangeApiClient`/`ExchangeApiError` implementation was never committed anywhere and remains unimplemented (TASK-EXC-0007's own original scope, never completed upstream). This blocks `publisher-portal`'s own build/typecheck and causes its 12 test failures. Not a WP-EXC-011 defect — a pre-existing, confirmed-unrecoverable gap, correctly left to a future, explicitly-scoped work package.
- The five originally-scaffold-only packages (`dependency_resolver`, `update_service`, `licensing`, `payments`, `reviews`) remain exactly that — scaffolds, not implementations. This is unchanged from their historical state and was never this WP's job to change (§4 Out of Scope).
- `package-lock.json` still carries a residual, npm-flagged-`extraneous` metadata entry for the never-implemented `package-cli`; harmless, left as npm's own automatic bookkeeping rather than manually pruned.

WP-EXC-010 READINESS:
READY WITH CONDITIONS — the workspace foundation WP-EXC-010 needs to build on now exists and is verified (13/14 packages + 2/3 apps fully green). The one condition: whoever picks up WP-EXC-010 (or a dedicated smaller work package first) must resolve the `exchange_client`/TASK-EXC-0007 gap before `publisher-portal`'s own feature work can proceed cleanly — `exchange-api` and `exchange-admin` have no such blocker.

FINAL RECOMMENDATION:
Accept this restoration as the new Exchange workspace baseline. Do not attempt to implement the missing `exchange_client` API as a side effect of any future WP without first explicitly scoping it (it is real, non-trivial API-client work, not a restoration task). WP-EXC-010 may proceed against `exchange-api`/`exchange-admin`/the 14 restored packages immediately; `publisher-portal`-specific feature work should wait for that scoped follow-up.
