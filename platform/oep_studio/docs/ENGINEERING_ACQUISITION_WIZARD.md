# Engineering Acquisition Wizard

The primary way engineers bring knowledge into OEP. Opened from the
**Acquire Engineering Knowledge** button at the top of Engineering
Acquisition Studio.

## Why it exists

Before the Wizard, acquiring a document meant understanding OEP's own
internal architecture: register an Official Source, create an Acquisition
Job, advance that job's state machine by hand, start a Download, request
a Verification, request Metadata Extraction, then publish to the Vault --
seven distinct concepts and at least eight button presses, in an order
nothing on screen explained.

The Wizard replaces that with one guided flow that *teaches while it
works*: what is happening, why OEP asks for each piece of information,
how Engineering Chain of Custody works, and what happens next. The
backend concepts still exist and are unchanged -- they are now
implementation details rather than the user's workflow.

## Flow

| Step | Screen | What it does |
| --- | --- | --- |
| 1 | Knowledge Type | Classifies the material (Standard, Datasheet, Wiring Diagram, ...) so it can later be interpreted correctly. |
| 2 | Official Source | Pick an existing trusted publisher, search them, or register a new one inline -- immediately selectable on Save. |
| 3 | Chain of Custody | Collects Original URL, Publisher, Publication Date, Revision, License, Language, Acquisition Method, Engineer -- each with an explanation of *why* OEP needs it. |
| 4 | Acquisition Scope | Entire Document / Pages / Chapters / Sections. The complete artifact is **always** stored in the Vault regardless; scope describes what should later be *extracted*. |
| 5+6 | Acquire & Live Progress | One press. Runs the entire backend chain automatically, then automatically ingests the published artifact into a real Knowledge Session, and streams a live log of every stage. |
| 7 | Candidate Preview | Real Knowledge Candidates/Relationship Candidates/Evidence generated by ingestion, grouped by category -- read-only. |
| 8 | Engineering Review | The real Knowledge Studio `EngineeringReviewPanel`, hosted directly: Accept / Reject / Edit / Duplicate / Delete. |
| 9 | Publish (Commit) | Status summary of what already happened automatically, plus the real `CommitPreviewPanel` for an explicit, engineer-confirmed Repository Commit. |

## What the Wizard automates

One press of **Acquire Engineering Knowledge** (Step 5) drives the whole
Acquisition -> Reference Vault -> UIF -> Knowledge Session chain
automatically, stopping immediately with a real error message if any
Acquisition stage fails:

```
POST /jobs                 create the Acquisition Job
POST /jobs/{id}/execute    created -> queued
POST /jobs/{id}/execute    queued  -> running
POST /downloads            real HTTP/HTTPS retrieval via the `http-source` connector
POST /verifications        real SHA-256 integrity verification
POST /metadata              file-type detection + document inspection
POST /vault                publish into the permanent, content-addressable Reference Vault
POST /jobs/{id}/execute    running -> completed
-> AcquisitionRuntimeNotifier.ingestVaultArtifact()
     -> ReferenceVaultIngestionWorkflow.ingest()   (unmodified WP-INGEST-004 pipeline)
     -> FoundationRuntimeNotifier.loadKnowledgeSessionRecord()
```

Every one of those is an existing, already-tested endpoint or service --
**no backend or ingestion architecture was changed by WP-EAM-003.** The
Wizard is purely an orchestrator: it calls
`AcquisitionRuntimeNotifier.ingestVaultArtifact` (the same method the
Reference Vault panel's own "Ingest into Knowledge Studio" action already
used) and `FoundationRuntimeNotifier.loadKnowledgeSessionRecord` -- it
never touches `IngestionOrchestrator`, `ReferenceVaultAdapter`,
`IngestionKnowledgeSessionBridge`, `CommitTransactionService`, or
`FoundationBridge` write APIs directly.

### Repository context (WP-EAM-003 §5)

Ingestion requires a target `KnowledgeSession.repositoryName`. Rather
than asking the engineer to retype something OEP already knows, the
Wizard derives it from whichever Foundation Repository is currently open
(`FoundationServiceState.repositoryStatus?.repositoryName`). If no
Repository is open when acquisition finishes, ingestion is deliberately
deferred (never bound to a guessed or empty name) -- Candidate Preview
shows a "Retry Ingestion" action once a Repository is opened. The
artifact itself is never at risk either way: it is already permanently
stored in the Reference Vault by the time ingestion is even attempted.

### Candidate Preview, Engineering Review, Publish are now real

- **Step 7 (Candidate Preview)** reads the real
  `FoundationServiceState.candidates`/`relationshipCandidates`/
  `evidenceRegions` the ingestion run just produced -- reusing the
  existing `KnowledgeCandidate`/`RelationshipCandidate` models directly,
  never a second candidate model, and never a fabricated one. If
  ingestion FAILED, this step shows the real failure and a retry action
  instead of a fake candidate list.
- **Step 8 (Engineering Review)** hosts the real `EngineeringReviewPanel`
  widget verbatim -- the same widget Knowledge Studio's own "Engineering
  Review" tab uses. Accept/Reject/Edit/Duplicate/Delete remain entirely
  human-controlled; the Wizard performs no automatic acceptance.
- **Step 9 (Publish)** distinguishes Reference Vault **publication**
  (already happened automatically, back at Step 5/6) from Foundation
  Repository **Commit** (a separate, consequential, explicitly
  engineer-confirmed action) -- it hosts the real `CommitPreviewPanel`
  widget verbatim, backed by the real `CommitPlanService`/
  `CommitTransactionService`/`FoundationRuntimeNotifier.commitToFoundation()`.
  Nothing is committed to the Repository until the engineer explicitly
  confirms it here.

## Honestly disclosed gaps

These are visible in the UI itself, not hidden in code comments:

- **Step 9's destination package selector is informational.** The
  Reference Vault is a single flat content-addressable store; it has no
  package/collection concept at the backend. The artifact is stored in
  the shared Vault regardless of the selection, and the UI says so.
- **Step 4's scope is recorded, not enforced.** The backend always
  acquires the complete artifact -- there is no partial-retrieval
  capability at the connector layer. The selection is preserved in the
  Chain of Custody record so intent survives until ingestion can act on
  it.
- **Chain of Custody is stored locally.** `oep_acquisition` has no schema
  fields for publisher/license/revision/etc. Since this work explicitly
  must not modify the backend, records are persisted to
  `%APPDATA%/oep_studio/chain_of_custody.json`, keyed by Vault Entry id.
  Migrating this to real server-side columns is the natural next backend
  work package.
- **The connector is not selectable.** `oep_acquisition` ships
  `example-stub` (fabricates a placeholder file) and `http-source` (real
  HTTP/HTTPS). The Wizard always uses `http-source`, since asking the
  engineer to choose would contradict the whole point of the Wizard.
- **Merge/Link Existing are not on `EngineeringReviewPanel`.** That
  narrower Accept/Reject/Edit/Duplicate/Delete vocabulary (vs.
  SDD-020's fuller set) is `EngineeringReviewPanel`'s own existing,
  documented scope -- unchanged by WP-EAM-003, which only hosts that
  panel rather than modifying it.

## Tests

`test/acquisition/acquisition_wizard_controller_test.dart` covers the
Acquisition/Reference Vault orchestration logic the Wizard owns, against
a faked `AcquisitionRuntimeNotifier` (no network, no running backend, no
writes to the real settings directory):

- the full chain runs in the correct order from a single press
- a failed download stops the chain -- verify/metadata/publish are never attempted
- a failed verification stops before metadata and publish
- every stage appears in the live log (no silent operations)
- step gating blocks advancing past a step with missing required input
- `run()` is not re-entrant -- a second press while running is ignored
- an API exception surfaces its curated message, not a raw error

`test/acquisition/eam_003_wizard_orchestration_test.dart` (TEST-EAM-003-001
through 018, plus a full-chain test) covers the WP-EAM-003 orchestration
this document describes above: automatic ingestion after Vault
publication, Repository-context derivation, real Candidate Preview/
Engineering Review/Commit Preview reuse, FAILED/PARTIAL ingestion
handling, and the Reference Vault panel's own "Ingest into Knowledge
Studio" entry point remaining unaffected.
`test/acquisition/eam_003_wizard_native_commit_test.dart` adds a real
(non-mocked) Foundation Repository Commit acceptance test against the
real `oep_foundation_bridge.dll`, for the one boundary (Foundation
Commit) the fully-faked suite above cannot exercise for real --
documented in that file's own header exactly which stage is real and
which is substituted.

`test/acquisition/eam_002_wizard_ingestion_boundary_test.dart` still
verifies the boundary that remains after WP-EAM-003 reopened WP-EAM-002's
original "never touches ingestion" decision: the Wizard may call the
existing public `ingestVaultArtifact`/`loadKnowledgeSessionRecord` entry
points, but must never reach past them into `IngestionOrchestrator`,
`ReferenceVaultAdapter`, `IngestionKnowledgeSessionBridge`,
`CommitTransactionService`, or `FoundationBridge` object/relationship
creation directly -- see that file's own updated header for the full
history.
