# WP-EXC-013A

Title:
Foundation Bridge Artifact Synchronization & Integration Test Gate

Status:
Complete

Milestone:
Infrastructure/test-hardening follow-up to WP-EXC-013 (Exchange → Repository Install Bridge). Makes WP-EXC-013's real-Foundation integration test reproducible from a normal checkout/build, not a manually swapped binary.

Dependencies:

- WP-EXC-013 (established `ExchangeInstallBridge` and `test/exchange_foundation_install_integration_test.dart`, and identified the stale-DLL problem this WP resolves)
- `platform/oep_studio/docs/FOUNDATION_BRIDGE.md` (documents the canonical `flutter build windows` pipeline this WP relies on, unchanged)

---

# 1. Objective

Eliminate the need to manually swap `platform/oep_studio/oep_foundation_bridge.dll` in order for the real Exchange → Foundation integration test to pass, and make its failure modes honest: a genuinely unavailable environment skips; a stale or incompatible bridge artifact fails loudly instead of masquerading as "not built here."

# 2. Original problem (from WP-EXC-013)

`dart:ffi`'s `DynamicLibrary.open('oep_foundation_bridge.dll')` (bare filename, `platform/oep_studio/lib/core/foundation/oep_api_bindings.dart:19`, unchanged by this WP) resolves via the OS's default DLL search order, which includes the current working directory — the package root when `flutter test` runs. A copy of `oep_foundation_bridge.dll` has lived at that root since the single commit that imported Studio's history (`d27ef35`, 2026-08-15). Nothing has ever kept it in sync with the canonical build output, so it silently drifted out of date; WP-EXC-013's integration test could only be made to pass once, by manually copying a fresh build over it and then reverting that change so the working tree stayed clean.

# 3. Root cause

Two independent facts compounded:

1. **The tracked root-level DLL was never part of any build pipeline.** The canonical, documented build (`docs/FOUNDATION_BRIDGE.md` § "Native DLL") is `flutter build windows`, which — via `windows/CMakeLists.txt` → `native/foundation_bridge/CMakeLists.txt` → `windows/runner/CMakeLists.txt`'s `POST_BUILD copy_if_different` step — produces and places `oep_foundation_bridge.dll` at `build/windows/x64/runner/{Debug,Release}/`, next to `oep_studio.exe`. That directory is git-ignored (`/build/` in `platform/oep_studio/.gitignore`). The package-root copy is a completely separate file that no build step ever touches.
2. **The Foundation API moved on after the root copy was committed, and the build was briefly broken.** Commit `1ef6fd6` (2026-08-27, "Add Foundation diagram identity/membership and bridge scoped graph load," `OEP_API_VERSION` 20 → 21) corrected `native/foundation_bridge/CMakeLists.txt`'s Foundation module list — its own commit message records that the list had silently drifted (`exchange` referenced a module directory that was never real; `archive`/`installer` were missing) and that "this DLL had not been successfully rebuilt in some time" before that fix. The Aug 15 root-level copy predates all of this. The exact symptom WP-EXC-013 hit — `Failed to lookup symbol 'oep_runtime_get_state'` (Windows error code 127, "the specified procedure could not be found") — is what a `dart:ffi` lookup produces against a DLL from before a function was exported, not a missing-file error (which is error code 126, "the specified module could not be found," and is a different, legitimate "not built here" condition — see §6).

# 4. Artifact ownership / tracking decision

**Decision: A — remain tracked, and keep it regenerated by an explicit, documented sync step.**

Evidence considered:

- The repository already established the precedent of tracking this exact binary (the Aug 15 import). Reversing that now would be a broader repository-policy change ("should generated native artifacts ever be committed for test reproducibility?") well beyond this WP's scope to decide unilaterally.
- A tracked, working copy lets `flutter test` exercise the real native Foundation surface without every contributor (or CI runner) needing a full C++/CMake/MSVC toolchain able to build Foundation from source — a real, legitimate reason to check in a prebuilt artifact in this specific case, not merely convenience.
- The actual defect was never "it's tracked" — it was "nothing regenerates it." Fixing the regeneration gap (§5) resolves the reproducibility problem without forcing a tracking-policy decision this WP has no mandate to make.

If a future WP decides differently (e.g. moving to a `.gitattributes`-managed LFS artifact, or removing it in favor of a mandatory native build step in CI), that remains an open, separately-scoped decision — not forced here.

# 5. Canonical build path (established, unmodified)

```
flutter build windows --debug     (or --release)
  -> windows/CMakeLists.txt adds native/foundation_bridge/ as a subdirectory
  -> native/foundation_bridge/CMakeLists.txt builds oep_foundation_bridge.dll
     by compiling oep_foundation's own CMake modules unmodified and linking
     oep_api into a shared library (exports listed in oep_foundation_bridge.def)
  -> windows/runner/CMakeLists.txt's POST_BUILD step copies the result to
     build/windows/x64/runner/{Debug,Release}/oep_foundation_bridge.dll
```

This WP added exactly one new step after that, to close the reproducibility gap:

```
dart run tool/sync_foundation_bridge_dll.dart [--release]
  -> copies build/windows/x64/runner/{Debug,Release}/oep_foundation_bridge.dll
     over platform/oep_studio/oep_foundation_bridge.dll (the tracked root copy),
     only if the bytes actually differ
```

No new build system was introduced; no CMake file was modified; no Foundation source was touched.

# 6. API/ABI compatibility

Verified directly from `platform/oep_foundation/platform/api/include/oep/api/oep_api.h`:

```
#define OEP_API_VERSION 21
#define OEP_ABI_VERSION 1
```

Matches the expected values. The freshly built/synced `oep_foundation_bridge.dll` (5,554,688 bytes, produced by `flutter build windows --debug` in this session) exports `oep_runtime_get_state` and every other symbol the current bindings require — confirmed by the real integration test now passing without a manual swap (§8).

# 7. Real integration test — failure-mode hardening

`test/exchange_foundation_install_integration_test.dart`'s `setUp` used to catch any `FoundationBridge.create()` exception and unconditionally skip. It now classifies the `dart:ffi` failure by its exact shape:

| Failure | Windows error | Classification | Test outcome |
|---|---|---|---|
| `DynamicLibrary.open` itself fails ("Failed to load dynamic library ... The specified module could not be found") | 126 | Foundation genuinely not built in this environment | **SKIP** (legitimate — e.g. a CI runner with no native Windows toolchain) |
| `open` succeeds, then a symbol lookup fails ("Failed to lookup symbol ...") | 127 | A DLL exists but is stale/incompatible with the current API | **FAIL**, with a message naming the exact two commands to fix it |

Verified both paths directly in this session (§8) — including confirming the *old* stale DLL now fails loudly instead of silently skipping, and that removing the DLL entirely still produces a legitimate skip.

# 8. Verification performed this session

1. `flutter build windows --debug` — clean, canonical build. Output DLL content-identical to a prior same-day build (Foundation source unchanged since), confirming determinism.
2. `dart run tool/sync_foundation_bridge_dll.dart` — synced the tracked root copy from that build output (5,554,688 bytes, up from the stale 1,748,480-byte Aug 15 copy).
3. `flutter test test/exchange_foundation_install_integration_test.dart` — **all 4 tests passed**, with zero manual file manipulation between the sync step and this test run.
4. Simulated the old stale DLL (restored from this session's own backup) — confirmed all 4 tests now **FAIL** (not skip) with the new, actionable error message.
5. Restored the synced DLL — confirmed all 4 tests **pass** again.
6. Removed the DLL entirely (simulating a truly Foundation-not-built environment) — confirmed all 4 tests **skip** with the distinct "not present in this environment" message, then restored it.

This is the reproducibility proof the WP required: `flutter build windows` → `dart run tool/sync_foundation_bridge_dll.dart` → `flutter test` passes the real Foundation integration test, with no manual binary copy step, and the test gate correctly distinguishes the two failure modes it must distinguish.

# 9. CI

No CI configuration exists anywhere in this repository (`.github/workflows/` is absent at the repository root; the only `.github/workflows` directories found are vendored inside third-party dependency source trees under `services/acquisition/build/_deps/` and `services/exchange/node_modules/`, unrelated to this repository's own pipeline). Building a CI pipeline is explicitly out of this WP's scope. Documented for whoever adds one: running the real Foundation integration test in CI requires a Windows runner with the MSVC/CMake toolchain needed to build both `oep_foundation` and `native/foundation_bridge/`, plus the `flutter build windows --debug` + `dart run tool/sync_foundation_bridge_dll.dart` sequence before `flutter test`; without that toolchain, the test's own new skip path (§7) already degrades gracefully rather than failing a CI run that legitimately cannot build Foundation.

# 10. Scope discipline

No Foundation source changed. No `ExchangeInstallBridge`/`applyFoundationInstall` logic changed. No CMake file changed — `windows/CMakeLists.txt`, `windows/runner/CMakeLists.txt`, and `native/foundation_bridge/CMakeLists.txt` were inspected, not modified; the existing `POST_BUILD copy_if_different` step already does exactly what it should for its own target directory. The only source changes are: one new standalone Dart script (`tool/sync_foundation_bridge_dll.dart`), one test file's failure-classification logic (`test/exchange_foundation_install_integration_test.dart`), and the tracked binary artifact itself (refreshed content, not architecture).

# 11. Out of scope

WP-EXC-014, Exchange RC1, publisher UI, dependency resolution, authentication, a new CI pipeline, cross-platform (Linux/Android/macOS) bridge builds, any Foundation installer/trust/package-format change, any change to `ExchangeInstallBridge`'s own architecture.

# 12. Known limitations / exit criteria

- The sync step is manual (a developer or CI job must run it after building) — it is not wired into `flutter test` itself, since Dart's test runner has no pre-test-run hook in this repository's existing tooling, and adding one would be a bigger change than this WP's scope. This is a deliberate, documented limitation, not an oversight.
- The DLL-tracking policy question (§4) is resolved pragmatically for this WP (keep tracking, add a sync step) but is not declared a permanent repository-wide policy; a future WP could revisit it with a broader mandate.
- Exit criteria: root cause established, ownership/tracking decision made with evidence, canonical build path confirmed, current API/ABI verified (21/1), real integration test passes without manual DLL swap (verified 3 ways: pass, fail, skip), no Foundation/bridge-architecture source changed, existing Exchange/Studio/publisher-portal tests unaffected, one dedicated commit, nothing pushed.
