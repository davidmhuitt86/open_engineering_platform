# Sprint Name

Repository Templates & Batch Operations (Work Package 010)

---

# Sprint Objective

Implement Repository Graph CLI Commands per OEP-SPEC-016-GRAPH_COMMANDS: `oep graph neighbors|traverse|path`, backed exclusively by Foundation Runtime and the existing `GraphEngine`.

The goal is not to build graph visualization, shortest-path algorithms, or interactive exploration.

The goal is to make the connections between Engineering Objects navigable from the CLI, while all graph algorithms stay owned by the Repository subsystem.

---

# Primary Deliverable

`GraphCommand` + `FoundationRuntime::graph_engine()`

`FoundationRuntime` gains a sixth registered service (`GraphEngine`, built the same way `SearchEngine` already is); `GraphCommand` is a thin layer over it.

# Work Package 011 (Task 000021 + Task 000022) — Verified Complete

**Task 000021 — Public C API.** Created the `platform/api` subsystem (previously an unspecified placeholder module), per OEP-SPEC-021-PUBLIC_C_API: a pure C ABI (`include/oep/api/oep_api.h`, `extern "C"`, no C++ classes, no STL types) wrapping `oep::runtime::FoundationRuntime`. Opaque handle `OEP_Runtime`; lifecycle functions `oep_runtime_create/destroy/initialize/open_repository/close_repository/shutdown`; `oep_runtime_get_state` mirroring the five `RuntimeState` values; `oep_runtime_get_repository_status` returning a fixed-layout `oep_repository_status_t`; versioning via `oep_foundation_version`/`oep_api_version`/`oep_abi_version`. Every function returns `oep_result_t` (success flag, error code, error category, fixed error-message buffer) rather than throwing; every exported function wraps its body in `try`/`catch (...)` so no native exception ever crosses the boundary, satisfying the spec's ABI-safety requirement directly rather than by convention. **TASK-000029 — Public Transaction API.** Added `oep_transaction_begin`/`_commit`/`_rollback`/`_is_active`. The key design decision, made once `FoundationRuntime` was found to have no staged-write concept at all (every `ObjectStore`/`RelationshipStore` write is immediate and independently atomic, but nothing before this work package grouped multiple writes into one reversible unit): rather than inventing a second, parallel persistence mechanism, a transaction is an in-memory compensating-action log (`FoundationRuntime::TransactionLogEntry`, private) recorded alongside each immediate write while a transaction is active. `commit_transaction` discards the log (every mutation is already durable); `rollback_transaction` replays it in reverse using the same `remove`/`update`/`restore` methods a normal mutation already uses — `restore()` in particular is the exact mechanism Import and Templates (Work Package 009) already established for reconstructing an object/relationship's exact prior identity, reused here rather than re-invented. Only one transaction may be active per handle (no nesting). Per the spec's explicit "Failures shall: Abort transaction, Roll back changes," any mutation failure while a transaction is active triggers automatic rollback and deactivation before the failure is returned to the caller. `FoundationRuntime::reset_repository_context()` (shared by `close_repository()` and `shutdown()`) now rolls back an active transaction first, so closing a repository can never strand one open.

**TASK-000030 — Public Batch Mutation.** Added `oep_batch_create_objects`/`oep_batch_create_relationships`, deliberately implemented as a thin convenience layer over the transaction primitives from TASK-000029 rather than a separate rollback mechanism: every spec is created in array order (the required deterministic execution order) inside a transaction — begun and committed automatically if the caller had none active, or participating in the caller's existing transaction otherwise, in which case a failure rolls back everything in that transaction, not just the batch's own entries. `oep_batch_create_objects_result_t`/`oep_batch_create_relationships_result_t::created` are deliberately left in execution order rather than sorted by ID (unlike `oep_object_store_list`/`oep_relationship_store_list`), since preserving that order is exactly the guarantee this task requires.

All new mutation error classification (duplicate/missing-object/invalid-relationship/etc.) flows through one new shared helper, `classify_mutation_error` (private to `oep_api.cpp`), pattern-matching the small, stable set of message substrings `ObjectStore`/`RelationshipStore` actually produce — the same substring-classification approach already established for `oep_runtime_open_repository` in Work Package 011, applied consistently rather than inventing a second classification style.

**Six new components in `platform/oep_engine`.** `RuntimeGraph` (`runtime_graph.hpp/.cpp`) — the Engine's own in-memory graph, built from a snapshot fetched via `RuntimeService`, deliberately separate from the pre-existing `oep::repository::GraphEngine` (same shape, different layer, different owner, no shared code); supports type/tag indexes, with "find by domain" a documented mapping onto Engineering Objects' existing `tags` field (CLAUDE.md's Five Primitive Rule forbids adding a dedicated "domain" field without architectural approval). `ObjectLoader` (`object_loader.hpp/.cpp`) — lazy `load_object` (cached) and batch `load_all`, exclusively through `RuntimeService`. `RelationshipEngine` (`relationship_engine.hpp/.cpp`) — classifies a `RuntimeGraph`'s edges into parents/children (`Contains`, directional)/neighbors (any edge)/references (`References`, outgoing)/dependencies (`DependsOn`, outgoing). `QueryEngine` (`query_engine.hpp/.cpp`) — find by id/type/domain/relationship, BFS shortest path, connected component, induced subgraph. `traverse()` (`traversal_engine.hpp/.cpp`) — deterministic BFS/DFS, optional relationship-type filter, optional max-depth, cycle-safe via a visited-set. `EngineeringContext` (`engineering_context.hpp/.cpp`) — the top-level facade exposing the work package's six-method Public Runtime API (`load_object`/`load_graph`/`query`/`traverse`/`related_objects`/`dependency_graph`); `dependency_graph()` walks Engineering Object `DependsOn` *relationships* — an entirely different thing, in name only, from Foundation's WP-REP-005 package-manifest Dependency Resolution Engine.

**RuntimeService-exclusive, matching WP-REP-007/WP-REP-008's pattern.** `ObjectLoader` and `EngineeringContext` are constructed from a `RuntimeService&` and never touch `FoundationRuntime`'s storage accessors, never open a Repository Transaction, never touch `ObjectStore`/`RelationshipStore` directly. `RuntimeService` (`platform/runtime`) gained exactly three new, minimal, read-only methods — `get_object`, `list_objects`, `list_relationships` — thin sequencing wrappers over `FoundationRuntime`'s already-public `object_store()`/`relationship_store()` accessors, adding no new persistence capability and duplicating no storage logic. `FoundationRuntime` itself is otherwise unchanged.

# Work Package WP-EKE-006 (Task 000044) — Verified Complete, Awaiting Review

**Six work packages into the WP-EKE series** (WP-EKE-001 built the Runtime core, WP-EKE-002 the canonical Knowledge Graph, WP-EKE-003 the deterministic Query Engine, WP-EKE-004 the data-driven Rules Engine, WP-EKE-005 the composition-based Validation Engine), each one built strictly on top of the one before it without ever skipping a layer or reaching around `EngineeringContext`/`RuntimeService` into Foundation directly — WP-EKE-006 is the sixth and, so far, most architecturally involved installment, turning validated engineering knowledge into explainable, evidence-referenced conclusions and recommendations.

Engineering Knowledge Runtime, Vertical Slice 6: the **Engineering Analysis & Reasoning Engine (EARE)** — built entirely inside `platform/oep_engine`, consuming `EngineeringContext`, the Knowledge Graph, the Query Engine, the Rules Engine, and the Validation Engine only. It analyzes engineering knowledge, derives deterministic conclusions, explains those conclusions, and produces reusable engineering analyses. Never communicates with the Repository directly, never persists, never modifies Engineering Objects, never opens a transaction, never calls external AI services.

**Four new files in `platform/oep_engine`.** `analysis_types.hpp` — four immutable Report classes: `DependencyReport`, `ImpactReport`, `ReachabilityReport`, `RootCauseReport`, each carrying an `evidence()` string naming exactly which algorithm/traversal produced it. `analysis_engine.hpp/.cpp` — `AnalysisEngine`, four PURE, deterministic structural algorithms over the Knowledge Graph, reusing WP-EKE-002's `GraphAlgorithms`/`KnowledgeGraph` directly rather than reimplementing graph traversal: `analyze_dependencies` (transitive outgoing `DependsOn` closure, BFS), `analyze_impact` (transitive incoming `DependsOn` closure — the reverse direction, "what would be affected if this object changes"), `analyze_reachability` (shortest path via `GraphAlgorithms::shortest_path`), `analyze_root_cause` (ranks a symptom's own transitive dependencies that appear in a caller-supplied finding set by ascending BFS depth — closest first — as root-cause candidates, plus the shortest `DependsOn` path from the top candidate as the failure chain). `reasoning_types.hpp/.cpp` — immutable `ReasoningSession` (session_id — a UUIDv4 via the same `oep::repository::generate_uuid_v4()` Foundation already uses elsewhere, start_time_utc, end_time_utc, objective, starting_objects, queries_executed, rules_applied, validation_results, conclusions, evidence), a TEMPORARY, session-scoped **Two analysis/reasoning primitives split across two classes — worth explaining clearly why.** `AnalysisEngine`'s four public methods alone satisfy the work package's 8-item "Analysis Engine" responsibilities list (Dependency Analysis, Impact Analysis, Reachability Analysis, Change Propagation [= Impact Analysis's affected-object set], Root Cause Analysis, Failure Chain Analysis [= `RootCauseReport`'s own `failure_chain` field], Dependency Tree Generation [= `DependencyReport`'s own flattened closure], Affected Object Discovery [= `ImpactReport`'s own `affected_object_ids`]) — the 8 items map onto the 4 public methods+report fields, not 8 separate API entries, matching the work package's own Runtime API section, which names only `analyze_dependencies`/`analyze_impact`/`analyze_root_cause`/`analyze_reachability` (4 entries). `ReasoningEngine` is the deeper, evidence-based apparatus where "every conclusion must reference its supporting evidence" is actually enforced. `ReasoningEngine::analyze_root_cause(symptom_object_id)` is a DIFFERENT, self-validating overload from `AnalysisEngine`'s two-argument version — it runs its own validation pass internally via `ValidationEngine`, then delegates to `AnalysisEngine`, so callers don't need to pre-compute the finding set themselves.

**The central design of `execute_reasoning` — the most architecturally interesting part of this work package.** For each starting object: (1) runs `analyze_dependencies`/`analyze_impact`, recording each as a "query executed"; (2) validates the starting object PLUS its full transitive dependency set in ONE shared `ValidationEngine` pass (Complete profile — avoiding redundant re-validation per object); (3) builds a temporary, session-scoped `EvidenceGraph` where every `EvidenceNode` names exactly where its content came from, deduplicating object-evidence nodes across the session via a small id-keyed map so the same object referenced by multiple conclusions gets exactly one evidence node; (4) derives `EngineeringConclusion`s (a dependency-count conclusion, an impact conclusion if non-empty, and — if any validation findings touch the object or its dependencies — a findings/root-cause conclusion), each with a NON-EMPTY `supporting_evidence_ids` list, enforced as an invariant and verified directly in the C++ test suite by checking that every referenced evidence id resolves to a real node in that session's own `EvidenceGraph`; and (5) derives `EngineeringRecommendation`s of all 5 kinds the work package names (`SimilarComponent`, `ConnectedSystem`, `RelatedProcedure`, `FollowUpValidation`, `AdditionalInspection`), each ALSO carrying non-empty evidence.

**Confidence is deterministic arithmetic, never probabilistic/AI-derived.** The exact documented formula, defined in `reasoning_engine.cpp`'s own doc comment: `confidence = min(1.0, 0.5 + 0.1 * evidence_count)`. Since every conclusion has at least one piece of evidence, confidence is always >= 0.6.

**Public C API: three deliberate scope decisions.** `oep_analysis_dependencies`/`_impact`/`_reachability`/`_root_cause` and `oep_reasoning_create_session`/`_execute`/`_report`/`_get_conclusion`/`_get_recommendation`/`_get_evidence_node`, plus `oep_dependency_report_t`/`oep_impact_report_t`/`oep_reachability_report_t`/`oep_root_cause_report_t`/`oep_reasoning_summary_t`/`oep_engineering_conclusion_t`/`oep_engineering_recommendation_t`/`oep_evidence_node_t`. **Self-validating root-cause routing:** `oep_analysis_root_cause` and every root-cause CLI/API path route through `ReasoningEngine::analyze_root_cause`, never `AnalysisEngine`'s two-argument version directly — the C API boundary only ever exposes the "just works" version. **Fetch-by-id, not index:** `oep_reasoning_get_conclusion`/`_get_recommendation` take `conclusion_id`/`recommendation_id`, mirroring the precedent `oep_rules_evaluate` (WP-EKE-004) already established. **Deliberately minimal Evidence Graph exposure:** only `oep_reasoning_get_evidence_node` (fetch one node by id) — no enumeration of all nodes, no `EvidenceRelationship` edge exposure. `oep_reasoning_report`/`_execute` both return `oep_reasoning_summary_t` (scalar-only) plus TWO `oep_package_id_list_t` outputs (conclusion_ids, recommendation_ids) — the established "scalar summary + id-list, fetch detail separately by id" pattern from WP-EKE-004/WP-EKE-005. **One honestly-disclosed ambiguity:** `ReasoningEngine::reasoning_report` cannot distinguish "session_id was never created" from "session was created but `execute_reasoning` was never called" (both return `std::nullopt`) — a genuine new manifestation of this pattern, since (unlike `ValidationEngine`, which finalizes its session within a single `validate_*` call) `ReasoningEngine` has an explicit two-step create-then-execute flow;
